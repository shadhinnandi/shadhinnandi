## 1(a) [5]
**Topics:** 01

### Question
A startup company creates a proprietary encryption system and refuses to disclose its design, claiming that secrecy makes it more secure. The system is also highly complex, requiring many interdependent modules.

Which security principles are violated in this scenario? How do these approaches increase security risk rather than reducing them?

### Solution
**Principles violated:**

1. **Open design.** Security should depend only on keeping the **key** secret, not the design (Kerckhoffs's principle). The company relies on keeping the algorithm secret, which is "security through obscurity".
2. **Economy of mechanism.** A security design should be as **simple and small** as possible. Their system is highly complex with many interdependent modules.

**Why secrecy increases risk:**
- A secret design is never reviewed by outside experts, so its weaknesses stay hidden until an attacker finds them.
- Designs leak or can be reverse engineered. Once that happens, every customer is broken at once, and it cannot be fixed by simply changing a key.
- Customers cannot judge how secure the product really is, giving false confidence.

**Why complexity increases risk:**
- More code and more interactions between modules mean more bugs and more places for vulnerabilities.
- Complex systems are hard to test, audit and configure correctly.
- A flaw in one module can spread to the others because they depend on each other.

**Better approach:** use a public, well-studied algorithm (such as AES or RSA), keep only the keys secret, and keep the design simple.

## 1(b) [5]
**Topics:** 11

### Question
How does botnets work? Explain with a figure. What types of attacks can be launched using botnets? List few countermeasures

### Solution
A **botnet** is a network of compromised computers (**bots** or **zombies**) controlled by an attacker (the **botmaster**) through **Command and Control (C&C)** servers.

```text
              Botmaster
                  |  commands
             C&C server(s)
            /     |      \
         Bot     Bot     Bot     ... thousands of zombies
            \     |      /
          Target (victim server, email users, ad sites)
```

**How a botnet works:**
1. **Infection:** computers are infected with bot malware, spreading like worms and viruses (phishing, infected downloads, unpatched flaws).
2. **Rally:** each bot quietly connects to the C&C server and waits. The owner usually does not notice.
3. **Command:** the botmaster sends one command to the C&C server.
4. **Action:** all bots carry it out together, and may report results back.

**Attacks launched using botnets:**
- Distributed Denial of Service (DDoS)
- Spam and phishing email forwarding
- Click fraud on online ads
- Keystroke logging and theft of passwords and bank details
- Spreading further malware

**Countermeasures:**
- Keep systems patched and use anti-virus so computers do not become bots.
- Firewalls and intrusion detection to spot C&C communication and unusual outgoing traffic.
- Take down C&C servers with ISPs and law enforcement.
- Use honeypots to study botnets (passive and active monitoring).
- Rate limiting, traffic filtering and DDoS protection services to reduce attack impact.

### Question
Perform encryption and decryption of the plaintext 9 using RSA algorithm for p = 5, q = 11 and e = 3.

### Solution
**Given values**

```calc
M = 9
p = 5
q = 11
n = p × q = 5 × 11 = 55
z = (p − 1)(q − 1) = 4 × 10 = 40
e = 3
```

**Private key d**

```calc
d = e^{−1} mod z
  = 3^{−1} mod 40
  = (1 + 40 × k) / 3 mod 40
  = (1 + 40 × 2) / 3 mod 40   [k = 1 gives 41, not divisible by 3; k = 2 gives 81]
  = 81 / 3 mod 40
  = 27
∴ d = 27
```

Check: 3 × 27 = 81 = 2 × 40 + 1.

**Encryption**

```calc
C = M^{e} mod n
  = 9^{3} mod 55
  = 729 mod 55
  = 14
∴ C = 14
```

**Decryption: M = 14<sup>27</sup> mod 55 by square and multiply**

27 = 16 + 8 + 2 + 1. Square repeatedly, reducing mod 55:

```calc
14^{1} mod 55 = 14
14^{2} mod 55 = 196 mod 55 = 31
14^{4} mod 55 = 31^{2} mod 55 = 961 mod 55 = 26
14^{8} mod 55 = 26^{2} mod 55 = 676 mod 55 = 16
14^{16} mod 55 = 16^{2} mod 55 = 256 mod 55 = 36
```

Multiply the rows for 16, 8, 2 and 1:

```calc
M = C^{d} mod n
  = 14^{27} mod 55
  = 14^{16} × 14^{8} × 14^{2} × 14^{1} mod 55
  = 36 × 16 × 31 × 14 mod 55
  = 14 × 31 mod 55 × 16 × 36 mod 55
  = 49 × 16 × 36 mod 55   [434 mod 55 = 49]
  = 784 mod 55 × 36 mod 55
  = 14 × 36 mod 55   [784 mod 55 = 14]
  = 504 mod 55
  = 9
∴ M = 9, the original plaintext
```

```seq
Receiver | Sender
Receiver: n = 55, z = 40, e = 3, d = 27
Receiver -> Sender: public key (3, 55)
Sender: C = 9^{3} mod 55 = 14
Sender -> Receiver: C = 14
Receiver: M = 14^{27} mod 55 = 9
```

## 2(b) [5]

### Question
Explain the philosophy behind Diffie-Hellman key exchange protocol.

In the Diffie-Hellman key exchange protocol, let the prime number be 353 and one of its prime root is 3. Let the users A and B select their secret keys 97 and 233, respectively. Compute the public keys of A and B and also their common secret key.

### Solution
**Philosophy:**
- Two users want a shared secret key for symmetric encryption, but they can only talk over a public channel, so the key must **never be sent**.
- Each user keeps a private number and sends only g<sup>private</sup> mod p. Each one raises the other's public value to its own private number, and both get the same value g<sup>ab</sup> mod p.
- An eavesdropper sees p, g and both public keys, but cannot find the private numbers, because the **discrete logarithm problem** is very hard for large p.

**Given:** p = 353, g = 3, X<sub>A</sub> = 97, X<sub>B</sub> = 233.

**Powers of 3 mod 353 (repeated squaring)**

```calc
3^{1} mod 353 = 3
3^{2} mod 353 = 9
3^{4} mod 353 = 81
3^{8} mod 353 = 81^{2} mod 353 = 6561 mod 353 = 207
3^{16} mod 353 = 207^{2} mod 353 = 42849 mod 353 = 136
3^{32} mod 353 = 136^{2} mod 353 = 18496 mod 353 = 140
3^{64} mod 353 = 140^{2} mod 353 = 19600 mod 353 = 185
3^{128} mod 353 = 185^{2} mod 353 = 34225 mod 353 = 337
```

**Public key of A** (97 = 64 + 32 + 1)

```calc
Y_A = g^{X_A} mod p
    = 3^{97} mod 353
    = 3^{64} × 3^{32} × 3^{1} mod 353
    = 185 × 140 × 3 mod 353
    = 420 mod 353 × 185 mod 353   [140 × 3 = 420]
    = 67 × 185 mod 353
    = 12395 mod 353
    = 40
∴ Y_A = 40
```

**Public key of B** (233 = 128 + 64 + 32 + 8 + 1)

```calc
Y_B = g^{X_B} mod p
    = 3^{233} mod 353
    = 3^{128} × 3^{64} × 3^{32} × 3^{8} × 3^{1} mod 353
    = 337 × 185 × 140 × 207 × 3 mod 353
    = 621 mod 353 × 140 × 185 × 337 mod 353   [207 × 3 = 621]
    = 268 × 140 × 185 × 337 mod 353
    = 37520 mod 353 × 185 × 337 mod 353
    = 102 × 185 × 337 mod 353   [37520 mod 353 = 102]
    = 18870 mod 353 × 337 mod 353
    = 161 × 337 mod 353   [18870 mod 353 = 161]
    = 54257 mod 353
    = 248
∴ Y_B = 248
```

**Common secret key at A:** K = Y<sub>B</sub><sup>X<sub>A</sub></sup> mod p = 248<sup>97</sup> mod 353

```calc
248^{1} mod 353 = 248
248^{2} mod 353 = 61504 mod 353 = 82
248^{4} mod 353 = 82^{2} mod 353 = 6724 mod 353 = 17
248^{8} mod 353 = 17^{2} mod 353 = 289
248^{16} mod 353 = 289^{2} mod 353 = 83521 mod 353 = 213
248^{32} mod 353 = 213^{2} mod 353 = 45369 mod 353 = 185
248^{64} mod 353 = 185^{2} mod 353 = 34225 mod 353 = 337
```

```calc
K = 248^{97} mod 353
  = 248^{64} × 248^{32} × 248^{1} mod 353
  = 337 × 185 × 248 mod 353
  = 45880 mod 353 × 337 mod 353   [185 × 248 = 45880]
  = 343 × 337 mod 353   [45880 mod 353 = 343]
  = 115591 mod 353
  = 160
```

**Check at B:** K = Y<sub>A</sub><sup>X<sub>B</sub></sup> mod p = 40<sup>233</sup> mod 353

```calc
40^{1} mod 353 = 40
40^{2} mod 353 = 1600 mod 353 = 188
40^{4} mod 353 = 188^{2} mod 353 = 35344 mod 353 = 44
40^{8} mod 353 = 44^{2} mod 353 = 1936 mod 353 = 171
40^{16} mod 353 = 171^{2} mod 353 = 29241 mod 353 = 295
40^{32} mod 353 = 295^{2} mod 353 = 87025 mod 353 = 187
40^{64} mod 353 = 187^{2} mod 353 = 34969 mod 353 = 22
40^{128} mod 353 = 22^{2} mod 353 = 484 mod 353 = 131
```

```calc
K = 40^{233} mod 353
  = 40^{128} × 40^{64} × 40^{32} × 40^{8} × 40^{1} mod 353
  = 131 × 22 × 187 × 171 × 40 mod 353
  = 6840 mod 353 × 187 × 22 × 131 mod 353   [171 × 40 = 6840]
  = 133 × 187 × 22 × 131 mod 353   [6840 mod 353 = 133]
  = 24871 mod 353 × 22 × 131 mod 353
  = 161 × 22 × 131 mod 353   [24871 mod 353 = 161]
  = 3542 mod 353 × 131 mod 353
  = 12 × 131 mod 353   [3542 mod 353 = 12]
  = 1572 mod 353
  = 160
∴ Public keys: Y_A = 40, Y_B = 248. Common secret key K = 160
```

```seq
A | B
A: X_A = 97; Y_A = 3^{97} mod 353 = 40
B: X_B = 233; Y_B = 3^{233} mod 353 = 248
A -> B: Y_A = 40
B -> A: Y_B = 248
A: K = 248^{97} mod 353 = 160
B: K = 40^{233} mod 353 = 160
```

## 3(a) [5]

### Question
What would be the financial advantage for a malware designer to create lots of different malicious code instances that all exploit the same vulnerability yet have different malware signatures?

### Solution
Most anti-virus products use **signature-based detection**: they recognise malware by a byte pattern stored in a signature database. Each new variant with a different signature must be found, analysed and added to the database before it is detected.

**Financial advantages for the malware designer:**
1. **Longer undetected life:** every new variant is a "new" malware to scanners, so it keeps infecting computers until its own signature is released. One signature update blocks only one variant, not all of them.
2. **More infected machines:** many variants exploiting the same vulnerability can reach many more victims before patches and signatures catch up. More victims means more money from stolen bank details, ransom payments, spam and click fraud.
3. **Bigger and longer-living botnets:** infected machines stay infected longer and can be rented out to others for DDoS or spam, a steady income.
4. **Cheap to produce:** mutation, encryption and polymorphic engines create variants automatically, while the defenders' cost of analysing each variant is high.
5. **Selling the toolkit:** the designer can sell variant-generating malware kits to other criminals.

This is why defenders also use **heuristic and behaviour-based detection** and **patch the vulnerability itself**, which stops all variants at once.

## 3(b) [5]
**Topics:** 13

### Question
A university network experiences a sudden surge in traffic as hundreds of machines begin scanning and infecting other unpatched systems automatically.

Using the worm propagation model, explain how the values of susceptible hosts (S(t)) and infected hosts (I(t)) change over time.

### Solution
This is a **worm**: it spreads automatically by scanning for and infecting unpatched systems. Its spread follows the **classic epidemic model**.

**Terms:**
- N = total number of vulnerable (unpatched) hosts
- I(t) = number of infected hosts at time t
- S(t) = number of susceptible (not yet infected) hosts at time t
- β = infection rate

```calc
I(t) + S(t) = N
dI/dt = β × I(t) × S(t)
```

The rate of new infections depends on both how many hosts are infected (spreading it) and how many are still susceptible (can be infected). Every new infection increases I(t) by one and decreases S(t) by one, so the total stays N.

**How the values change over time:**
1. **Start (slow spread):** very few hosts are infected, I(t) is small and S(t) ≈ N. The product I × S is small, so infections grow slowly.
2. **Middle (rapid spread):** as I(t) grows, more machines scan and infect others; growth becomes almost exponential. This is the "sudden surge" in the scenario. Spread is fastest when I(t) = S(t) = N/2.
3. **End (saturation):** S(t) becomes very small because few unpatched machines are left, so new infections slow down. I(t) approaches N and S(t) approaches 0.

```text
Hosts
  N |                        ___________  I(t) infected
    |                    __/
N/2 |- - - - - - - - - -X- - - - - - - -   fastest spread
    |               /  \
  0 |____________/       \_____________   S(t) susceptible
    +------------------------------------> time
       slow start   rapid spread   saturation
```

So I(t) follows an **S-shaped (logistic) curve** rising to N, and S(t) is its mirror image falling to 0. Patching hosts early reduces N and S(t), which slows the worm before the rapid phase.

**Topics:** 10

### Question
What is the difference between SYN flood attack and Smurf attack? Explain the process to defend against SYN flooding attack using SYN cookie.

### Solution
**Difference:**

| Point | SYN flood | Smurf attack |
|---|---|---|
| Protocol | TCP (three-way handshake) | ICMP echo (ping) |
| Idea | Many SYNs sent, handshake never completed | Pings sent to a broadcast address with the victim's spoofed IP |
| Resource exhausted | Server memory (half-open connection queue) | Victim's network bandwidth |
| Traffic source | Directly from the attacker (spoofed IPs) | Reflected by many hosts on broadcast networks |
| Amplification | No | Yes, one request causes many replies |
| Main defence | SYN cookies | Disable directed broadcasts |

**Defence with SYN cookies:**
1. When a SYN arrives, the server does **not** allocate memory or save the connection state.
2. It computes a special initial sequence number, the **SYN cookie**, using HMAC of a **secret key**, the **source and destination IP addresses and ports**, and a **time value**.
3. It sends the SYN-ACK with this cookie as its sequence number.
4. A genuine client replies with an ACK whose acknowledgement number is cookie + 1.
5. The server recomputes the cookie from the ACK's addresses, ports and time, and checks it.
6. Only if it is valid does the server allocate memory and establish the connection.

Spoofed SYNs never return a valid ACK, so they use no server memory and cannot fill the backlog queue.

```seq
Client | Server
Client -> Server: SYN
Server: cookie = HMAC(key, IPs, ports, time); nothing stored
Server -> Client: SYN-ACK, seq = cookie
Client -> Server: ACK, ack = cookie + 1
Server: recompute and check cookie; if valid, open connection
```

## 4(b) [5]
**Topics:** 15

### Question
Distinguish between Click-jacking and Cross Site Scripting(XSS) attacks. How can XSS lead to Session Hijacking ?

### Solution
**Click-jacking vs XSS:**

| Point | Click-jacking | Cross-Site Scripting (XSS) |
|---|---|---|
| Idea | Tricks the user into clicking a hidden element: the real site is loaded in an invisible frame over a harmless-looking page | Injects malicious script into a trusted site's pages, which then runs in users' browsers |
| Code injected into target site? | No | Yes |
| What the attacker controls | The user's **click** | **Script** running in the user's browser |
| User action needed | User must click | Runs when the page loads or a crafted link is opened |
| Typical damage | Unwanted actions (buy, delete, allow permissions) | Cookie theft, account takeover, page changes |
| Defence | X-Frame-Options or CSP frame-ancestors (block framing) | Output encoding, input validation, CSP, HttpOnly cookies |

**How XSS leads to session hijacking:**
1. After login, the website identifies the user by a **session cookie**.
2. Through an XSS flaw, the attacker's script runs inside the victim's browser **on the real site**, so the browser lets it access that site's cookies.
3. The script sends the victim's session cookie to the attacker.
4. The attacker adds the stolen cookie to their own browser and the site treats them as the logged-in victim. The session is hijacked without needing the password.

**Prevention:** mark session cookies **HttpOnly** (scripts cannot read them) and **Secure**, encode output and validate input to stop XSS, use a Content Security Policy, and use short session timeouts.
