# Web Attacks

## SQL injection

<figure class="csec-figure csec-figure--image"><img src="figures/sql-normal-query.webp" alt="The web browser sends a username and password to the web server; the web server sends the query SELECT passwd FROM USERS WHERE uname IS 'smith' to the database and returns the result." width="738" height="329" loading="lazy" decoding="async"><figcaption>A normal login query, from the class notes. SQL injection abuses the step where the server builds this query from user input.<a href="figures/sql-normal-query.webp" target="_blank" rel="noopener">Open full size</a></figcaption></figure>

**Definition:** SQL injection is an **input validation** vulnerability. Untrusted user input is placed directly inside an SQL query, so input that contains SQL syntax is treated as part of the **command** instead of as plain data. It is a type of **command injection**.

**In one line:** when a program builds a query by gluing user input into SQL text, specially crafted input (for example a quote followed by an always-true condition) changes the query's logic, such as skipping the password check or reading other tables.

**The vulnerable pattern vs the safe pattern:**

```java
// Vulnerable: input becomes part of the SQL text
String sql = "SELECT * FROM users WHERE username = '" + user + "' AND password = '" + pass + "'";

// Safe: a parameterized query keeps input as data only
PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE username = ? AND password = ?");
ps.setString(1, user);
ps.setString(2, passwordHash);
```

**Consequences:** login bypass, theft of usernames, passwords and personal data, changing or deleting records, and in some setups control of the database server. If passwords are stored in **plain text**, a leak exposes every account at once.

**Prevention:**

- **Parameterized queries / prepared statements** (the main fix): input can never change the query structure.
- **Input validation:** check type and format (an integer must be an integer); handle characters with special meaning such as `'` `;` `%` `-` `_`.
- **Whitelisting over blacklisting:** allow only a well-defined set of safe values (for example with regular expressions). Blacklists miss characters and can block valid input like the name O'Brien.
- **Least privilege** for the database account the web app uses.
- **Hash and salt passwords** (bcrypt, Argon2) so a leak does not reveal them.
- Do not show database error messages to users; use a web application firewall.

## Cross-site scripting (XSS)

**Definition:** XSS is an attack in which the attacker gets a website to send **malicious script** to other users' browsers. The browser trusts the script because it comes from the real site.

A web application is vulnerable if it:
- stores user input without sanitizing, validating or encoding it, or
- includes user data in its HTTP responses without sanitizing or encoding it.

**Types:**

- **Stored (persistent) XSS:** the script is saved on the server (in a comment, review or profile) and runs for **every user who views the page**. More damaging.
- **Reflected XSS:** the script is placed in a link; the site reflects it back in the response, so it runs only for the user who **clicks the crafted link**.

**Consequences:**

- **Session cookies stolen**, letting the attacker impersonate users (session hijacking).
- User accounts compromised.
- Page content changed, or users tricked into giving private information.
- Further malware (trojans) activated.

**How XSS leads to session hijacking, in short:** the injected script runs in the victim's browser on the real site, so it can read the site's session cookie and send it to the attacker, who then uses that cookie to act as the logged-in victim.

**Prevention:**

- **Output encoding / escaping** of all user data before putting it in a page (for example `<` becomes `&lt;`).
- **Input validation and sanitization**, with whitelists of allowed content.
- **HttpOnly cookies**, so scripts cannot read the session cookie.
- **Content Security Policy (CSP)** to block inline and untrusted scripts.

## Cross-site request forgery (CSRF)

**Definition:** CSRF tricks a user's browser into sending an **unwanted request** to a site where the user is **already logged in**. The browser automatically attaches the user's session cookie, so the site thinks the user made the request.

**Steps:**

1. The victim logs in to a site (a bank, a shop, a payroll portal) and the session stays open.
2. The victim visits a malicious page or clicks a link made by the attacker.
3. That page silently makes the victim's browser send a request to the real site (for example, transfer money or change the email).
4. The browser includes the valid session cookie.
5. The site cannot tell it apart from a real request, so it performs the action.

<figure class="csec-figure csec-figure--image"><img src="figures/csrf.webp" alt="Step 1: the user victim establishes a session with the server victim. Step 2: the user visits the attack server. Step 3: the user receives a malicious page. Step 4: the user browser sends a forged request to the server victim." width="783" height="480" loading="lazy" decoding="async"><figcaption>CSRF, from the class notes: steps 1 to 4.<a href="figures/csrf.webp" target="_blank" rel="noopener">Open full size</a></figcaption></figure>

**Example from the notes:** a normal transfer request looks like
`GET http://netbank.com/transfer.do?acct=PersonB&amount=$100`.
The attacker changes the account to their own and hides the link behind innocent text such as "Read more!". A logged-in victim who clicks it sends the transfer.

**Why it succeeds:** the site trusts any request that carries a valid session cookie and does not check whether the user actually intended it.

**Impact:** money transfers, changed email or password (account takeover), changed bank details, purchases, all made in the victim's name.

**Prevention (server side):**

- **Anti-CSRF tokens:** a secret random token in every form, checked by the server. The attacker's page cannot know it.
- **SameSite cookies**, so the browser does not send the session cookie with cross-site requests.
- **Strict Referer / Origin checking**, especially for login forms and sensitive sites like banks.
- **Re-authentication** (password or OTP) for sensitive actions like changing bank details.
- Use secure frameworks that implement CSRF tokens correctly (e.g. Ruby on Rails). Never change state with GET requests.

**Mitigation (user side):** log out when finished, do not let browsers remember passwords, and do not browse other sites while logged in to a sensitive application.

## Click-jacking

**Definition:** click-jacking (UI redressing) tricks a user into **clicking something different from what they see**. The real site is loaded in an invisible frame placed over a harmless-looking page, so the user's click lands on a hidden button (like "Buy", "Delete" or "Allow").

**Prevention:** stop the site from being framed by other sites with the `X-Frame-Options: DENY` header or the CSP `frame-ancestors` rule.

**Click-jacking vs XSS:**

| Click-jacking | XSS |
|---|---|
| Tricks the user's **click** with a hidden frame | Runs **injected script** in the user's browser |
| No code is injected into the target site | Malicious code is injected into the target site's pages |
| User must click | Script runs when the page loads or the link is opened |
| Stopped by frame protection (X-Frame-Options, CSP) | Stopped by output encoding, input validation, CSP |

## Exam-ready answers

**Q. What is SQL injection? How can it be prevented? (3 marks)**

SQL injection is a vulnerability where user input is inserted into an SQL query without validation, so input containing SQL syntax changes the query and can read or change data the user should not access.
Prevention: parameterized queries, input validation with whitelisting, least privilege database accounts, and hashed passwords.

**Q. Explain a CSRF attack and its prevention. (3 marks)**

CSRF makes a logged-in user's browser send an unwanted request to a trusted site, for example through a hidden form on a malicious page. The browser adds the session cookie, so the site performs the action (transfer money, change email).
Prevention: anti-CSRF tokens, SameSite cookies, Referer/Origin checks, re-authentication for sensitive actions.

**Q. What is stored XSS? Give three defences. (3 marks)**

Stored XSS is when malicious script is saved on a site (e.g. in a comment) and runs in every visitor's browser.
- Encode output so script is shown as text, not run.
- Validate and sanitize input with a whitelist.
- Use HttpOnly cookies and a Content Security Policy to limit damage.
