# TCP Session Hijacking

## Background: TCP sequence numbers

TCP starts every connection with a **three-way handshake**:

```seq
Client | Server
Client -> Server: SYN, seq = x
Server -> Client: SYN-ACK, seq = y, ack = x + 1
Client -> Server: ACK, seq = x + 1, ack = y + 1
```

After this, every packet carries a **sequence number (seq)** and an **acknowledgement number (ack)**. A receiver accepts a packet only if its numbers fit the current connection. These numbers are 32 bits long (2<sup>32</sup> possible values), so they are hard to guess.

## What is TCP session hijacking?

**TCP session hijacking** is an attack in which the attacker takes over an **already established** TCP connection by sending packets with the **correct seq and ack numbers** and a **spoofed source IP address** (the IP of one of the real parties).

The server believes the injected packets come from the real client, so the attacker can send commands inside the victim's logged-in session.

## How it works (attacker on the same network)

1. The attacker is on the same LAN segment as the client or server and **sniffs** their packets (for example after ARP spoofing).
2. From the sniffed packets, the attacker reads the current **seq and ack numbers**.
3. The attacker builds a packet with the client's IP as the source and the next expected seq number. This needs low-level (raw) packet programming, not normal socket programming.
4. The server accepts it as part of the session.
5. The real client's numbers are now out of step, so it is pushed out (often it is also blocked with a DoS or a RST packet).

## Example with sequence numbers (from the class notes)

**A normal session.** Each side acknowledges the next byte it expects: after 128 bytes from Seq = 3001 the server expects 3129, and after 141 more it expects 3270.

```seq
Client | Server
Client -> Server: SYN = 1, Seq = 3000
Server -> Client: SYN = 1, ACK = 1, Seq = 8000, Ack = 3001
Client -> Server: ACK = 1, Seq = 3001, Ack = 8001
Server: TCP connection established
Client -> Server: Seq = 3001, Ack = 8001, Data = 128
Server -> Client: Ack = 3129, Seq = 8001
Client -> Server: Seq = 3129, Ack = 8001, Data = 141
Server -> Client: Ack = 3270, Seq = 8001
```

**The hijack.** The attacker has sniffed the numbers, so it sends the next expected packet first (Seq = 3270). The server now expects 4270, so the real client's packet with Seq = 3270 looks like a duplicate and is rejected. The attacker keeps the session.

```seq
Client | Attacker | Server
Attacker -> Server: Seq = 3270, Ack = 8001, Data = 1000
Server -> Attacker: Ack = 4270, Seq = 8001
Client -> Server: Seq = 3270, Ack = 8001, Data = 500
Server: sequence mismatch / duplicate sequence; client packet not accepted
Attacker -> Server: Seq = 4270, Ack = 8001, Data = 1000
Server -> Attacker: Ack = 5270, Seq = 8001
```



If the attacker is on a different subnet, it **cannot sniff** the traffic. Challenges:

- **Cannot see seq/ack numbers**: they must be **guessed or predicted** out of 2<sup>32</sup> values.
- **Cannot see replies**: the server sends its answers to the real client, not to the attacker, so the attacker works "blind".
- **The real client may interfere**: it may send RST or its own packets and break the attack.
- **Spoofed packets may be filtered** by routers that drop packets with impossible source addresses (ingress filtering).

How it can still be done:

1. The attacker keeps the real client quiet, for example with a DoS attack, so it cannot reset the connection.
2. It learns how the server picks initial sequence numbers by opening its own connections and watching the pattern (old systems used predictable increments).
3. It predicts the current seq/ack window and sends spoofed packets with the client's IP and many guessed numbers.
4. If one guess is in the window, the server accepts the injected data (for example, a command that adds a new user). The attacker never sees the response.

```seq
Alice | Attacker | Bob
Alice -> Bob: established TCP session
Attacker: keeps Alice busy with DoS
Attacker -> Bob: probe connections to learn ISN pattern
Attacker: predicts seq/ack of Alice's session
Attacker -> Bob: spoofed packet, src IP = Alice, guessed seq
Bob: accepts if seq is in window
Bob -> Alice: replies go to Alice (attacker is blind)
```

## Prevention

- Use **encrypted and authenticated protocols**: SSH, TLS/HTTPS, IPsec. Injected packets fail the integrity check.
- Use **random initial sequence numbers** so they cannot be predicted.
- Use **ingress and egress filtering** on routers to drop spoofed source IPs.
- Use **secure session cookies** (HttpOnly, Secure flag) and short session timeouts for web sessions.
- Defend against sniffing on the LAN (switch security, ARP spoofing protection).
