# SYN Flooding and Smurf Attack

Both are **Denial-of-Service (DoS)** attacks. They attack **availability**: the victim's resources are used up, so real users cannot be served.

## SYN flooding attack

**Definition:** a SYN flood is a DoS attack where the attacker sends many TCP connection requests (SYN) but never completes the three-way handshake (the final ACK never comes).

**In one line:** each unfinished request leaves a **half-open connection** in the server's memory, and enough of them fill the server's connection queue.

**Effects:**

- The server's backlog queue fills up, so **real users' connections are refused**.
- Memory, CPU and bandwidth are wasted on fake requests.
- Spoofed source IPs are usually used, which hides the attacker and makes fake requests hard to tell from real ones.
- No full connection is ever made (unlike TCP session hijacking).

## SYN cookies (main defence)

With **SYN cookies**, the server keeps **no state** until the handshake is complete.

1. On a SYN, the server computes a special sequence number, the **SYN cookie**, using a keyed hash (HMAC) of a **secret key**, the **IP addresses and ports**, and a **time value**.
2. It sends the SYN-ACK with this cookie and **stores nothing**.
3. A genuine client returns an ACK carrying cookie + 1.
4. The server recomputes the cookie and checks it. Only a valid ACK makes the server allocate memory and open the connection.

Fake requests never come back with a valid ACK, so they cost the server no memory.

**Other defences:** a larger backlog queue, shorter SYN-ACK timeout, rate-limiting SYNs per source, filtering spoofed source IPs, and firewalls or DDoS protection services.

## Smurf attack

**Definition:** a Smurf attack is a DoS attack that misuses **ICMP echo (ping)** and **broadcast networks** to multiply traffic towards a victim.

**In one line:** pings sent to a broadcast address with the victim's spoofed IP make every host on that network reply to the victim at the same time.

**Effects:**

- One small request turns into many replies (**amplification**), so the victim's bandwidth is overloaded.
- The broadcast networks act as innocent "bounce sites"; the real source is hidden.

## Defence against Smurf attacks

- **Disable directed broadcasts** on routers, so outside pings cannot reach a whole subnet (Cisco: `no ip directed-broadcast`).
- **Access control lists (ACLs)** to block ICMP echo requests entering the network. This can make troubleshooting harder.
- **Configure hosts not to reply** to pings sent to broadcast addresses. RFC 1122 allows such requests to be silently discarded.
- **Filter spoofed source addresses** at network edges.

## SYN flood vs Smurf attack

| Point | SYN flood | Smurf attack |
|---|---|---|
| Protocol | TCP | ICMP |
| Resource exhausted | Server memory (connection queue) | Victim's network bandwidth |
| Traffic source | Attacker sends directly (spoofed IPs) | Reflected by hosts on broadcast networks |
| Amplification | No | Yes, one request gives many replies |
| Main defence | SYN cookies | Disable directed broadcasts |

## Exam-ready answers

**Q. What is a SYN flooding attack? How do SYN cookies stop it? (4 marks)**

A SYN flood is a DoS attack where many SYN requests are sent but the final ACK is never sent. The server keeps each half-open connection in its queue, the queue fills, and real users are refused.

With SYN cookies the server stores nothing on a SYN. It sends a SYN-ACK whose sequence number is a cookie made from a secret key, addresses, ports and time. Only when a valid ACK returns with that cookie does it allocate memory. Fake requests never return, so they cannot fill the queue.

**Q. Difference between SYN flood and Smurf attack. (3 marks)**

- SYN flood uses TCP and exhausts the server's memory with half-open connections; Smurf uses ICMP echo and exhausts the victim's bandwidth.
- SYN flood is sent directly by the attacker; Smurf is reflected and amplified by hosts on broadcast networks.
- SYN flood is stopped with SYN cookies; Smurf is stopped by disabling directed broadcasts.
