# Digital Signature and Certificate

## What is a digital signature?

A **digital signature** is a cryptographic value attached to a message, like a handwritten signature on paper. It is made with the sender's **private key** and checked with the sender's **public key**.

It provides three things:

- **Authentication**: the message really came from the claimed sender.
- **Integrity**: the message was not changed on the way.
- **Non-repudiation**: the sender cannot later deny sending it, since only they have the private key.

A digital signature does **not** hide the message. For secrecy, the message must also be encrypted.

## How it works

**Signing (sender, Bob):**

1. Compute the hash of the message: h = H(m). A hash is a short fixed-size fingerprint of the message.
2. Encrypt the hash with Bob's **private key**: S = h<sup>d</sup> mod n. This S is the signature.
3. Send the message and the signature (m, S).

**Verifying (receiver, Alice):**

1. Compute the hash of the received message: h = H(m).
2. Decrypt the signature with Bob's **public key**: h′ = S<sup>e</sup> mod n.
3. If h = h′, the signature is valid. If not, the message was changed or did not come from Bob.

Hashing first keeps the signature small and fast, because the hash is much shorter than the message.

## Worked example: RSA digital signature

**Anis sends M = 20 to Boshir with a digital signature using RSA. p = 17, q = 11, d = 7, n = p × q, and the hash function is h(x) = (Ax + C) mod n with A = 4, C = 8. Show how Anis signs and how Boshir verifies.**

```calc
# Given
n = p × q = 17 × 11 = 187
z = (p − 1)(q − 1) = 16 × 10 = 160
d = 7
```

**At Anis's side: hash and sign**

```calc
h(M) = (A × M + C) mod n
     = (4 × 20 + 8) mod 187
     = 88 mod 187
     = 88
```

```calc
S = h^{d} mod n
  = 88^{7} mod 187
  = (88^{2} mod 187)^{3} × 88 mod 187
  = 77^{3} × 88 mod 187   [7744 mod 187 = 77]
  = 66 × 88 mod 187   [77^{3} = 456533, 456533 mod 187 = 66]
  = 5808 mod 187
  = 11
∴ Signature S = 11. Anis sends (M, S) = (20, 11)
```

**At Boshir's side: hash the message again**

```calc
h = (4 × 20 + 8) mod 187
  = 88
```

**At Boshir's side: find Anis's public key e and decrypt S**

```calc
e = d^{−1} mod z
  = 7^{−1} mod 160
  = (1 + 160 × k) / 7 mod 160
  = (1 + 160 × 1) / 7 mod 160   [k = 1]
  = 161 / 7 mod 160
  = 23
```

```calc
h′ = S^{e} mod n
   = 11^{23} mod 187
   = (11^{5} mod 187)^{4} × 11^{3} mod 187
   = 44^{4} × 22 mod 187   [161051 mod 187 = 44, 1331 mod 187 = 22]
   = (44^{2} mod 187)^{2} × 22 mod 187
   = 66^{2} × 22 mod 187   [1936 mod 187 = 66]
   = 55 × 22 mod 187   [4356 mod 187 = 55]
   = 1210 mod 187
   = 88
∴ h = h′ = 88, so the signature is verified
```

## Certification Authority (CA) and digital certificates

**The problem:** to verify Bob's signature, Alice needs Bob's public key. But an attacker could send Alice a fake public key and claim it is Bob's. Then the attacker's signatures would look valid.

**The solution:** a **Certification Authority (CA)** is a trusted third party that checks a person's identity and then signs a **digital certificate** that binds the person's name to their public key.

A certificate contains, in short: the owner's name, the owner's public key, the CA's name, the validity period, and the **CA's signature** over all of this.

**How it is used:**

1. Bob proves his identity to the CA and gives it his public key.
2. The CA hashes Bob's public key (with his details) and signs the hash with the **CA's private key**. This is Bob's certificate.
3. Alice receives Bob's public key with the certificate.
4. Alice verifies the CA's signature with the **CA's public key**, which she already trusts (for example, built into the browser or operating system).
5. If the check passes, Alice knows the key really belongs to Bob.

```seq
Sazzad | CA | Rubel
Sazzad -> CA: identity and public key k
CA: h = h(k); S = h^{d_CA} mod n_CA
CA -> Sazzad: certificate (k, S)
CA -> Rubel: CA public key (e_CA, n_CA), given in advance
Sazzad -> Rubel: k and certificate S
Rubel: h = h(k); h′ = S^{e_CA} mod n_CA; valid if h = h′
Rubel -> Sazzad: C = m^{k} mod n_S (now safe to use k)
```

**If there is no CA:** nobody can prove that a public key belongs to its claimed owner. An attacker can publish a fake key in someone's name, impersonate them, forge "valid" signatures and run man-in-the-middle attacks. Non-repudiation also breaks down, because the owner can claim the key was never theirs.

## Worked example: verifying a digital certificate

**Rubel receives a public key k = 11 with a digital certificate S from the CA. The key belongs to Sazzad. The CA uses RSA with p = 3, q = 11, private key d = 3 and the hash h(z) = (Az + b) mod R with A = 9, b = 7, R = 13. Calculate S and show how Rubel verifies it.**

Rubel requests Sazzad's digital certificate from the CA; the CA returns the certificate (k, S).
```calc
# Given
n_CA = p × q = 3 × 11 = 33
z_CA = (p − 1)(q − 1) = 2 × 10 = 20
d_CA = 3
k = 11
```

**At the CA: hash Sazzad's key and sign it**

```calc
h(k) = (A × k + b) mod R
     = (9 × 11 + 7) mod 13
     = 106 mod 13
     = 2
```

```calc
S = h^{d_CA} mod n_CA
  = 2^{3} mod 33
  = 8
∴ Certificate S = 8
```

**At Rubel: hash the key again, then check the signature with the CA's public key**

```calc
h = (9 × 11 + 7) mod 13
  = 2
```

```calc
e_CA = d_CA^{−1} mod z_CA
     = 3^{−1} mod 20
     = (1 + 20 × 1) / 3 mod 20   [k = 1]
     = 7
```

```calc
h′ = S^{e_CA} mod n_CA
   = 8^{7} mod 33
   = (8^{3} mod 33)^{2} × 8 mod 33
   = 17^{2} × 8 mod 33   [512 mod 33 = 17]
   = 25 × 8 mod 33   [289 mod 33 = 25]
   = 200 mod 33
   = 2
∴ h = h′ = 2, so the certificate is valid and k really belongs to Sazzad
```

## Exam-ready answers

**Q. What is a digital signature? How does it give integrity and authenticity? (3 marks)**

A digital signature is a hash of the message encrypted with the sender's private key. The sender sends (m, S). The receiver hashes m and decrypts S with the sender's public key.
- **Integrity:** if the message is changed, its hash changes and will not match.
- **Authenticity:** only the sender's private key can make a signature that the sender's public key opens correctly.
- **Non-repudiation:** the sender cannot deny it, since only they hold the private key.

**Q. Why do we need a Certification Authority to verify a signature? (3 marks)**

To verify a signature we need the signer's public key, and we must be sure that the key really belongs to the signer. Otherwise an attacker can give us their own key in the signer's name, and their forged signatures will verify correctly. A CA checks the owner's identity and signs a certificate binding the name to the public key. We trust the CA's public key in advance, so we can check the certificate and know the key is genuine.
