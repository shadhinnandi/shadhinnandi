# Chapter 11: Exception Handling

Real programs meet problems they cannot prevent: a user types `abc` where a number is
expected, a file is missing, a divisor is zero. Java reports such problems with
*exceptions*. In this chapter you learn what an exception is, how to read the error
report Java prints, and how to handle problems so that your program reacts sensibly
instead of crashing.

**In this chapter you will learn:**

- what an exception is and what happens when nobody handles it
- how to read a stack trace
- the exception hierarchy: `Throwable`, `Error`, `Exception`, `RuntimeException`
- the difference between checked and unchecked exceptions
- `try`, `catch` and `finally`, multiple catch blocks and multi-catch
- `throw` and `throws`, and how an exception travels through methods
- how to write your own exception classes (checked and unchecked)
- `getMessage()` and other useful methods of an exception object
- `try-with-resources` for closing files and other resources
- good practices: validate early, do not swallow exceptions, write clear messages

## 1. Concept Explanation

### What is an exception?

An **exception** is an event that happens while a program runs and stops the normal
flow of statements. Dividing an `int` by zero, reading index 5 of a 3-element array
and opening a file that does not exist are typical examples.

When the problem happens, Java creates an **exception object**. This object is an
instance of a class such as `ArithmeticException`. It records what went wrong (a
message) and where it happened (the list of method calls). Java then **throws** the
object: it stops the current statement and searches for code that will **catch**
(handle) it.

Think of a canteen. A cashier who finds a problem with an order (no rice left) does
not quietly guess what to do. She hands a note to the manager, and the manager
decides. In Java, the method that finds the problem throws an exception object, and a
method that knows what to do catches it.

```text
   normal flow                      with an exception

   statement 1                      statement 1
   statement 2                      statement 2   --> problem!
   statement 3                         |  exception object thrown
   statement 4                         v
                                    statement 3 and 4 are skipped
                                    Java looks for a matching catch
```

> **Coming from C?** C reports errors with special return values (`-1`, `NULL`) and
> the global `errno`. It is easy to forget to check them, and the program continues
> with bad data. In Java an exception cannot be ignored by accident: if nobody
> catches it, the program stops and reports it.

### What happens when nobody handles it: the stack trace

This program splits a canteen bill. It reads the total and the number of people from
input:

```java
import java.util.Scanner;

public class DivideCrash {
    static int share(int total, int people) {
        return total / people;
    }

    public static void main(String[] args) {
        Scanner in = new Scanner(System.in);
        int total = in.nextInt();
        int people = in.nextInt();
        int each = share(total, people);
        System.out.println("Each person pays " + each + " Tk");
    }
}
```

With input `450 3` it prints `Each person pays 150 Tk`. With input `450 0` the
division `total / people` cannot be computed for integers, so Java throws an
`ArithmeticException`. Nobody catches it, so the program stops and the JVM prints
this report to the error stream:

```text
Exception in thread "main" java.lang.ArithmeticException: / by zero
    at DivideCrash.share(DivideCrash.java:5)
    at DivideCrash.main(DivideCrash.java:12)
```

This report is called a **stack trace**. Read it like this:

| Part | Meaning |
|---|---|
| `thread "main"` | the problem happened in the main thread of the program |
| `java.lang.ArithmeticException` | the exception class (the kind of problem) |
| `/ by zero` | the message stored in the exception object |
| `at DivideCrash.share(...:5)` | thrown in method `share`, line 5 |
| `at DivideCrash.main(...:12)` | `share` was called by `main`, line 12 |

The first `at` line is where the exception was created. Each line below it is the
caller of the line above. So you read the trace from the top to find **where** it
broke, and downwards to see **how** the program got there. The last line
`System.out.println(...)` never ran.

When you meet a stack trace, look first for the top-most line that mentions your own
class. That is usually the line you need to fix.

### How an exception travels: propagation

Every method call puts a frame on the **call stack** (Chapter 03). When an exception
is thrown, Java looks for a matching `catch` in the current method. If there is
none, the method ends at once, its frame is removed, and the search continues in the
caller. This is called **propagation**.

```text
  call stack (top = running)      exception thrown in share()

  +------------------+            share(): no catch -> frame removed
  | share()          |  <-- here      |
  +------------------+                v
  | main()           |            main(): no catch -> frame removed
  +------------------+                |
                                      v
                                  JVM: prints stack trace, program ends
```

If any method on the way has a matching `catch`, the search stops there. The program
continues after that `try`/`catch` statement as if nothing else happened.

### Errors versus exceptions

All throwable objects belong to the class `Throwable`. It has two direct subclasses:

- **`Error`**: a serious problem the program normally cannot recover from, such as
  `OutOfMemoryError` or `StackOverflowError` (endless recursion). A normal program cannot repair these and
  should not try to catch them.
- **`Exception`**: a problem that a program can reasonably expect and handle, such as
  bad input or a missing file.

When people say "exception handling" they mean handling objects of class
`Exception` and its subclasses.

### Checked versus unchecked exceptions

Java divides exceptions into two groups.

**Checked exceptions** are subclasses of `Exception` that are *not* subclasses of
`RuntimeException`. They describe problems outside your program's control: a file is
missing, a network connection breaks. The compiler checks them: a method that can
cause one must either **catch** it or **declare** it with `throws`. Otherwise the
program does not compile.

**Unchecked exceptions** are `RuntimeException` and its subclasses (and also
`Error`). They usually mean a bug or input that should have been validated: dividing
by zero, a `null` reference, a wrong index. The compiler does not force you to catch
or declare them.

| | Checked | Unchecked |
|---|---|---|
| Superclass | `Exception` (not `RuntimeException`) | `RuntimeException` |
| Compiler forces catch or `throws`? | yes | no |
| Typical cause | outside world (files, network) | bug or unvalidated input |
| Examples | `IOException`, `FileNotFoundException` | `ArithmeticException`, `NumberFormatException` |

### The exception hierarchy

Exceptions are ordinary classes connected by inheritance (Chapter 09). This matters:
a `catch` for a superclass also catches all of its subclasses.

```text
                          Throwable
                              |
              +---------------+----------------+
              |                                |
            Error                          Exception
              |                                |
     +--------+--------+            +----------+-----------+
     |                 |            |                      |
OutOfMemoryError  StackOverflow  IOException        RuntimeException
                  Error             |               (unchecked)
                              FileNotFound               |
                              Exception     +------------+-------------+
                              (checked)     |            |             |
                                      Arithmetic  NullPointer  IllegalArgument
                                      Exception   Exception    Exception
                                                                       |
                                                              NumberFormat
                                                              Exception

  Also under RuntimeException:
    IndexOutOfBoundsException --> ArrayIndexOutOfBoundsException
    NoSuchElementException    --> InputMismatchException (Scanner)
```

Notice that `NumberFormatException` is a kind of `IllegalArgumentException`, and
`InputMismatchException` is a kind of `NoSuchElementException`.

### Common unchecked exceptions

| Exception | Typical cause | How to avoid it |
|---|---|---|
| `ArithmeticException` | integer division or `%` by zero | check the divisor first |
| `ArrayIndexOutOfBoundsException` | index `< 0` or `>= length` | check `0 <= i && i < a.length` |
| `NullPointerException` | calling a method on `null` | check for `null` first |
| `NumberFormatException` | `Integer.parseInt("12a")` | catch it when parsing user text |
| `InputMismatchException` | `nextInt()` reads `abc` | catch it, skip the bad token |
| `ClassCastException` | wrong downcast (Chapter 10) | test with `instanceof` first |

Note that dividing a `double` by zero does **not** throw an exception. It gives
`Infinity` or `NaN`. Only integer division and `%` throw `ArithmeticException`.

### When to use exceptions

Exceptions are for **exceptional** situations: something went wrong and the current
method cannot continue normally. They are not a replacement for `if`. A user typing
`q` to quit a menu is normal flow, so use an `if`. A file that should exist but does
not is exceptional, so use an exception.

## 2. Syntax

### try and catch

```java
try {
    // code that may throw an exception
} catch (ArithmeticException e) {
    // runs only if an ArithmeticException (or a subclass) was thrown
}
// execution continues here in both cases
```

- The `try` block holds the statements you want to protect.
- A `catch` block names one exception type and a variable (`e` by convention). The
  variable refers to the exception object that was thrown.
- If no exception happens, the `catch` block is skipped.
- If an exception happens, the rest of the `try` block is skipped and the matching
  `catch` block runs. Then the program continues after the whole statement.

```java
int people = in.nextInt();
try {
    int each = total / people;
    System.out.println("Each pays " + each);
} catch (ArithmeticException e) {
    System.out.println("Cannot split a bill among 0 people");
}
System.out.println("Thank you");
```

### Multiple catch blocks (specific first)

One `try` can have several `catch` blocks. Java checks them **from top to bottom** and
runs the first one whose type matches. At most one `catch` block runs.

```java
try {
    int marks = Integer.parseInt(parts[1]);
    System.out.println("Marks: " + marks);
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Marks are missing");
} catch (NumberFormatException e) {
    System.out.println("Marks are not a number");
}
```

Because a superclass catch also catches its subclasses, put **specific types first**
and general types later. If a general type comes first, the specific block can never
run, and the compiler rejects the program:

```java nocompile
try {
    int marks = Integer.parseInt(text);
} catch (IllegalArgumentException e) {
    System.out.println("Bad argument");
} catch (NumberFormatException e) {   // compile error: exception
    System.out.println("Not a number");  // NumberFormatException has already been caught
}
```

### Multi-catch

When two unrelated exception types need the **same** handling, list them in one
`catch` with `|`:

```java
try {
    int marks = Integer.parseInt(parts[1]);
    System.out.println("Marks: " + marks);
} catch (ArrayIndexOutOfBoundsException | NumberFormatException e) {
    System.out.println("Bad record: " + line);
}
```

The types in a multi-catch must not be subclasses of each other (writing
`NumberFormatException | IllegalArgumentException` is a compile error, because the
second already covers the first).

### finally

A `finally` block runs **after** the `try` (and any `catch`), whether an exception
happened or not. It even runs when the `try` block executes `return`, or when an
exception passes through without being caught.

```java
try {
    System.out.println("Start processing");
    process();                        // may throw
} catch (IllegalStateException e) {
    System.out.println("Problem: " + e.getMessage());
} finally {
    System.out.println("Cleanup");    // always printed
}
```

| Case | What runs |
|---|---|
| no exception | `try` (all of it) → `finally` |
| exception caught | `try` (up to the problem) → matching `catch` → `finally` |
| exception not caught here | `try` (up to the problem) → `finally` → caller |

Use `finally` for cleanup that must always happen. Do not put `return` inside
`finally`; it hides exceptions (IDEs and `javac -Xlint` warn about it).

### throw

You can throw an exception yourself with the `throw` statement. You create an
exception object with `new` and pass a message to its constructor:

```java
static void setMarks(int marks) {
    if (marks < 0 || marks > 100) {
        throw new IllegalArgumentException("Marks must be 0-100, got " + marks);
    }
    // ... marks are valid here
}
```

`throw` ends the method immediately, just like `return`, but instead of returning a
value it starts the search for a `catch`. This is how a method reports "I cannot do
what you asked" without printing anything itself. In Chapter 05 setters returned
`false` or printed a message for invalid values; throwing an exception is the usual
Java way.

### throws

`throws` appears in a method **header**. It declares which checked exceptions the
method may pass to its caller:

```java
static int readFirstNumber(String fileName) throws FileNotFoundException {
    Scanner file = new Scanner(new File(fileName));  // may throw
    int value = file.nextInt();
    file.close();
    return value;
}
```

Do not mix the two words up:

| Keyword | Where | Meaning |
|---|---|---|
| `throw` | a statement inside a method body | "throw this exception object now" |
| `throws` | the method header | "this method may pass these exceptions to you" |

For a checked exception, every caller must now catch it or declare it in turn. You
may also list unchecked exceptions in `throws` as documentation, but it is not
required.

### Writing your own exception classes

Java's built-in exceptions describe general problems. Your program's own rules
("not enough balance", "marks out of range") deserve their own exception classes.
The name then tells the reader exactly what went wrong, and callers can catch exactly
that problem.

A custom exception is a class that extends `Exception` (checked) or
`RuntimeException` (unchecked). It usually passes a message to the superclass
constructor:

```java
// Checked: callers must handle or declare it.
class InsufficientFundsException extends Exception {
    InsufficientFundsException(String message) {
        super(message);
    }
}

// Unchecked: signals a programming or validation error.
class InvalidMarksException extends RuntimeException {
    InvalidMarksException(String message) {
        super(message);
    }
}
```

How to choose:

- **Checked** (`extends Exception`) when the caller can reasonably recover and you
  want the compiler to remind every caller, for example a withdrawal larger than the
  balance.
- **Unchecked** (`extends RuntimeException`) when the problem means the caller broke
  a rule it could have checked, for example passing marks of 150.

A custom exception is a normal class, so it can have extra fields and getters, such
as the amount that was missing.

### getMessage and other methods

Every exception object inherits these methods from `Throwable`:

| Method | Returns |
|---|---|
| `getMessage()` | the message given to the constructor (may be `null`) |
| `toString()` | full class name plus message |
| `getCause()` | the exception that caused this one, or `null` |
| `printStackTrace()` | prints the stack trace to `System.err` |

```java
try {
    int n = Integer.parseInt("12a");
} catch (NumberFormatException e) {
    System.out.println(e.getMessage());   // For input string: "12a"
    System.out.println(e.getClass().getSimpleName());  // NumberFormatException
}
```

`e.getClass().getSimpleName()` gives the class name of the actual exception object
without the package. `printStackTrace()` is useful while debugging, but it writes to
the error stream. In this course, programs print their messages to `System.out`.

### Wrapping an exception (cause)

Sometimes a low-level exception (`NumberFormatException`) should be reported as a
higher-level problem ("record 3 is invalid"). You can create the new exception and
pass the old one as its **cause**:

```java
class RecordException extends Exception {
    RecordException(String message, Throwable cause) {
        super(message, cause);
    }
}

try {
    id = Integer.parseInt(fields[0]);
} catch (NumberFormatException e) {
    throw new RecordException("id is not a number", e);
}
```

The caller sees a meaningful `RecordException`, and `getCause()` still gives the
original exception for anyone who needs the detail.

### try-with-resources

A **resource** is an object that must be closed after use: a file, a network
connection, a `Scanner` on a file. Chapter 06 introduced `try-with-resources`. Now
you can see its full meaning:

```java
try (Scanner file = new Scanner(new File("marks.txt"))) {
    while (file.hasNextInt()) {
        sum += file.nextInt();
    }
} catch (FileNotFoundException e) {
    System.out.println("marks.txt is missing");
}
```

- Objects declared in the parentheses must implement `AutoCloseable`.
- Java calls `close()` on each resource automatically when the `try` block ends,
  normally or by an exception.
- Several resources are separated by `;` and are closed in **reverse order** of
  opening.
- Resources are closed **before** any `catch` or `finally` block of the same
  statement runs.
- If a resource's constructor throws, only the resources opened before it are closed.

This is safer than closing in `finally` by hand, because you cannot forget it.

### Good practices

- **Catch what you can handle.** Catch an exception only where you can do something
  useful: ask again, skip a record, show a message. Otherwise let it propagate.
- **Do not swallow exceptions.** An empty `catch { }` hides the problem and the
  program continues with wrong data. At least report it.
- **Do not catch `Exception` or `Throwable` without a reason.** A broad catch also
  catches bugs you never expected (such as `NullPointerException`) and hides them.
  Catch the specific types you expect.
- **Validate early.** Check arguments at the start of a method (or in a constructor)
  and throw immediately. The error then appears close to its cause.
- **Use exceptions for exceptional cases**, not for normal decisions that an `if`
  can make.
- **Write meaningful messages.** `"Marks must be 0-100, got 150"` helps; `"Error"`
  does not. Include the bad value.

```java
// BAD: swallows every problem, including bugs
try {
    account.withdraw(amount);
} catch (Exception e) {
}

// GOOD: handles the expected problem and reports it
try {
    account.withdraw(amount);
} catch (InsufficientFundsException e) {
    System.out.println("Withdrawal refused: " + e.getMessage());
}
```

## 3. Worked Examples

### Example 1: Splitting Canteen Bills Safely

**Problem:** Read the number of bills, then for each bill a total in Tk and the
number of people sharing it. Print how much each person pays (integer Tk). If the
number of people is 0, print a clear message for that bill and continue with the
next one.

The division happens in a small method `share`. When `people` is 0, integer division
throws `ArithmeticException`. We catch it inside the loop, so only that one bill is
affected.

```java
import java.util.Scanner;

public class BillSplit {
    static int share(int total, int people) {
        return total / people;   // throws ArithmeticException if people is 0
    }

    public static void main(String[] args) {
        Scanner in = new Scanner(System.in);
        int bills = in.nextInt();
        for (int i = 1; i <= bills; i++) {
            int total = in.nextInt();
            int people = in.nextInt();
            try {
                int each = share(total, people);
                System.out.println("Bill " + i + ": " + each + " Tk each");
            } catch (ArithmeticException e) {
                System.out.println("Bill " + i + ": cannot split ("
                        + e.getMessage() + ")");
            }
        }
        System.out.println("All bills processed.");
    }
}
```

**Input:**

```text
3
450 3
300 0
1000 4
```

**Output:**

```text
Bill 1: 150 Tk each
Bill 2: cannot split (/ by zero)
Bill 3: 250 Tk each
All bills processed.
```

**Why it works:** The exception is thrown inside `share`, which has no `catch`, so it
propagates to `main`. The `try` around the call catches it, prints a message and the
loop continues with bill 3. The println inside the `try` for bill 2 is skipped,
because the exception happened before it. In a real program you would also check
`people <= 0` before dividing (validate early); here the point is to see what the
exception looks like.

### Example 2: Asking Again Until the Input Is Valid

**Problem:** A course registration program asks for the number of credits of a
course. A valid answer is a whole number from 1 to 4. Keep asking until a valid
answer arrives, and report each wrong answer.

`nextInt()` throws `InputMismatchException` when the next token is not an integer.
The bad token stays in the `Scanner`, so the `catch` block must remove it with
`next()`. Otherwise the loop would read the same bad token forever.

```java
import java.util.InputMismatchException;
import java.util.Scanner;

public class CreditInput {
    public static void main(String[] args) {
        Scanner in = new Scanner(System.in);
        int credits = 0;
        int attempts = 0;
        boolean valid = false;
        while (!valid) {
            System.out.println("Enter course credits (1-4):");
            attempts++;
            try {
                credits = in.nextInt();
                if (credits < 1 || credits > 4) {
                    System.out.println("Out of range: " + credits);
                } else {
                    valid = true;
                }
            } catch (InputMismatchException e) {
                String bad = in.next();   // remove the bad token
                System.out.println("Not a whole number: " + bad);
            }
        }
        System.out.println("Accepted " + credits + " credits after "
                + attempts + " attempts.");
    }
}
```

**Input:**

```text
three
7
3
```

**Output:**

```text
Enter course credits (1-4):
Not a whole number: three
Enter course credits (1-4):
Out of range: 7
Enter course credits (1-4):
Accepted 3 credits after 3 attempts.
```

**Why it works:** This is a **re-validation loop**. Two kinds of bad input are
handled in two ways: a wrong *type* (`three`) is an exception from `Scanner`, so it
is caught; a wrong *value* (`7`) is a normal check with `if`. The loop stops only when
`valid` becomes `true`. The typed input is not shown in the Output block, because the
program does not echo it.

### Example 3: Reading Student Records Line by Line

**Problem:** Read a number `n` and then `n` lines, each meant to be a name followed by
marks, such as `Rahim 78`. Some lines are broken. For each line print the record or
an error, then print how many records were valid and their average with two decimal
places.

Splitting a line gives an array of words. Two things can go wrong: the marks word is
missing (index 1 does not exist) or it is not a number. Each has its own `catch`
block.

```java
import java.util.Scanner;

public class MarksLines {
    public static void main(String[] args) {
        Scanner in = new Scanner(System.in);
        int n = Integer.parseInt(in.nextLine().trim());
        int total = 0;
        int counted = 0;
        for (int i = 1; i <= n; i++) {
            String[] parts = in.nextLine().trim().split(" ");
            try {
                String name = parts[0];
                int marks = Integer.parseInt(parts[1]);
                total += marks;
                counted++;
                System.out.println(name + ": " + marks);
            } catch (ArrayIndexOutOfBoundsException e) {
                System.out.println("Line " + i + ": marks missing ("
                        + e.getMessage() + ")");
            } catch (NumberFormatException e) {
                System.out.println("Line " + i + ": bad marks ("
                        + e.getMessage() + ")");
            }
        }
        if (counted > 0) {
            double average = (double) total / counted;
            System.out.printf("Valid records: %d, average %.2f%n", counted, average);
        } else {
            System.out.println("No valid records.");
        }
    }
}
```

**Input:**

```text
4
Rahim 78
Nusrat 8O
Karim
Ayesha 91
```

**Output:**

```text
Rahim: 78
Line 2: bad marks (For input string: "8O")
Line 3: marks missing (Index 1 out of bounds for length 1)
Ayesha: 91
Valid records: 2, average 84.50
```

**Why it works:** For `Nusrat 8O` (letter O instead of zero), `parseInt` throws
`NumberFormatException`. For `Karim`, the array has length 1, so `parts[1]` throws
`ArrayIndexOutOfBoundsException`. Each exception skips the rest of the `try` block,
so `total` and `counted` are only updated for good lines. The messages printed by
`getMessage()` come from Java. A cleaner design checks `parts.length < 2` with an
`if` before reading `parts[1]` (validate early) and keeps the `catch` only for the
number format, which cannot be checked easily in advance.

### Example 4: Handling a Missing File

**Problem:** Add up the integers stored in two files, `marks.txt` and `backup.txt`.
If a file does not exist, report it and continue with the next file.

`new Scanner(new File(name))` throws the checked `FileNotFoundException`. The helper
method does not know what the caller wants to do about a missing file, so it declares
the exception with `throws` and lets `main` decide.

```java
import java.io.File;
import java.io.FileNotFoundException;
import java.util.Scanner;

public class ReadMarksFile {
    static int sumFile(String fileName) throws FileNotFoundException {
        int sum = 0;
        try (Scanner file = new Scanner(new File(fileName))) {
            while (file.hasNextInt()) {
                sum += file.nextInt();
            }
        }
        return sum;
    }

    public static void main(String[] args) {
        String[] names = {"marks.txt", "backup.txt"};
        for (String name : names) {
            try {
                int sum = sumFile(name);
                System.out.println(name + ": total " + sum);
            } catch (FileNotFoundException e) {
                System.out.println(name + ": file not found, skipped");
            }
        }
        System.out.println("Done.");
    }
}
```

**Input file `marks.txt`:**

```text
70 85 64
```

**Output:**

```text
marks.txt: total 219
backup.txt: file not found, skipped
Done.
```

**Why it works:** `marks.txt` exists, so the `Scanner` reads it and
`try-with-resources` closes it when the loop ends. `backup.txt` does not exist, so
the `Scanner` constructor throws `FileNotFoundException`. Because it is a checked
exception, the compiler forces either a `catch` or a `throws`: `sumFile` declares it,
and `main` catches it. We print our own message instead of `e.getMessage()`, because
the text of that message depends on the operating system. Chapter 12 covers files in
depth.

### Example 5: A Custom Checked Exception for Withdrawals

**Problem:** A campus mobile wallet allows withdrawals only up to the current
balance. Read the owner's name, the starting balance, a count `n` and `n` withdrawal
amounts. For each amount, either withdraw it or refuse it with a reason. A refusal for
low balance must also say how much money was missing.

We write `InsufficientFundsException` as a checked exception with an extra field
`shortfall`. An amount that is zero or negative is a different kind of mistake, so
it uses the built-in unchecked `IllegalArgumentException`.

```java
import java.util.Scanner;

class InsufficientFundsException extends Exception {
    private final int shortfall;

    InsufficientFundsException(String message, int shortfall) {
        super(message);
        this.shortfall = shortfall;
    }

    int getShortfall() {
        return shortfall;
    }
}

class WalletAccount {
    private final String owner;
    private int balance;

    WalletAccount(String owner, int balance) {
        this.owner = owner;
        this.balance = balance;
    }

    void withdraw(int amount) throws InsufficientFundsException {
        if (amount <= 0) {
            throw new IllegalArgumentException("Amount must be positive: " + amount);
        }
        if (amount > balance) {
            throw new InsufficientFundsException(
                    owner + " has only " + balance + " Tk", amount - balance);
        }
        balance -= amount;
    }

    int getBalance() {
        return balance;
    }
}

public class WalletDemo {
    public static void main(String[] args) {
        Scanner in = new Scanner(System.in);
        String owner = in.next();
        int start = in.nextInt();
        WalletAccount account = new WalletAccount(owner, start);
        int n = in.nextInt();
        for (int i = 0; i < n; i++) {
            int amount = in.nextInt();
            try {
                account.withdraw(amount);
                System.out.println("Withdrew " + amount + " Tk, balance "
                        + account.getBalance() + " Tk");
            } catch (InsufficientFundsException e) {
                System.out.println("Refused: " + e.getMessage()
                        + " (short by " + e.getShortfall() + " Tk)");
            } catch (IllegalArgumentException e) {
                System.out.println("Refused: " + e.getMessage());
            }
        }
    }
}
```

**Input:**

```text
Tanvir 1000
4
300
900
-50
700
```

**Output:**

```text
Withdrew 300 Tk, balance 700 Tk
Refused: Tanvir has only 700 Tk (short by 200 Tk)
Refused: Amount must be positive: -50
Withdrew 700 Tk, balance 0 Tk
```

**Why it works:** `withdraw` checks its rules first and throws before changing
`balance`, so a refused withdrawal leaves the account unchanged (the object's
invariant "balance is never negative" holds). Because `InsufficientFundsException`
is checked, the compiler would reject `main` if it called `withdraw` without a
matching `catch`. The custom field `shortfall` gives the caller more than a message:
it could, for example, suggest a smaller amount.

### Example 6: Validation Exception Passing Through Methods

**Problem:** Read `n` students, each with a name and marks. Print a letter grade for
each (A for 80 and above, B for 65 and above, C for 50 and above, F otherwise). Marks
outside 0 to 100 are invalid: report them and skip that student. Show which code runs
on the way out when an exception passes through a method.

`checkMarks` throws the unchecked `InvalidMarksException`. `grade` does not catch it.
`printGrade` does not catch it either, but has a `finally` block. Only `main`
catches it.

```java
import java.util.Scanner;

class InvalidMarksException extends RuntimeException {
    InvalidMarksException(String message) {
        super(message);
    }
}

public class GradeReport {
    static void checkMarks(int marks) {
        if (marks < 0 || marks > 100) {
            throw new InvalidMarksException("Marks must be 0-100, got " + marks);
        }
    }

    static String grade(int marks) {
        checkMarks(marks);
        if (marks >= 80) {
            return "A";
        } else if (marks >= 65) {
            return "B";
        } else if (marks >= 50) {
            return "C";
        }
        return "F";
    }

    static void printGrade(String name, int marks) {
        System.out.println("Grading " + name);
        try {
            System.out.println(name + " -> " + grade(marks));
        } finally {
            System.out.println("Done with " + name);
        }
    }

    public static void main(String[] args) {
        Scanner in = new Scanner(System.in);
        int n = in.nextInt();
        for (int i = 0; i < n; i++) {
            String name = in.next();
            int marks = in.nextInt();
            try {
                printGrade(name, marks);
            } catch (InvalidMarksException e) {
                System.out.println("Skipped: " + e.getMessage());
            }
        }
    }
}
```

**Input:**

```text
3
Nusrat 86
Fahim 105
Sadia 58
```

**Output:**

```text
Grading Nusrat
Nusrat -> A
Done with Nusrat
Grading Fahim
Done with Fahim
Skipped: Marks must be 0-100, got 105
Grading Sadia
Sadia -> C
Done with Sadia
```

**Why it works:** For Fahim the exception travels
`checkMarks` → `grade` → `printGrade` → `main`:

```text
checkMarks(105)  throws InvalidMarksException
grade            no catch: ends at once
printGrade       no catch, but finally prints "Done with Fahim"
main             catch prints "Skipped: ..."
```

`Fahim -> ` is never printed, because the string is built only after `grade`
returns, and it never returns. The `finally` block runs even though `printGrade` does
not handle the exception. Since `InvalidMarksException` is unchecked, no method needs
`throws`.

### Example 7: Order of try-with-resources, catch and finally

**Problem:** A lab booking opens two resources, the computer lab and the projector,
and uses them for a number of minutes. A booking longer than 180 minutes is not
allowed. Trace exactly when each resource is opened and closed, when the `catch`
runs and when the `finally` runs, for one valid and one invalid booking.

`LabResource` implements `AutoCloseable` and prints a line in its constructor and in
`close()`, so the order becomes visible.

```java
import java.util.Scanner;

class LabResource implements AutoCloseable {
    private final String name;

    LabResource(String name) {
        this.name = name;
        System.out.println("Open " + name);
    }

    void use(int minutes) {
        if (minutes > 180) {
            throw new IllegalStateException("Booking too long: " + minutes + " min");
        }
        System.out.println("Using " + name + " for " + minutes + " min");
    }

    @Override
    public void close() {
        System.out.println("Close " + name);
    }
}

public class LabBooking {
    static void book(int minutes) {
        try (LabResource lab = new LabResource("computer lab");
             LabResource projector = new LabResource("projector")) {
            lab.use(minutes);
            projector.use(minutes);
        } catch (IllegalStateException e) {
            System.out.println("Caught: " + e.getMessage());
        } finally {
            System.out.println("Finally: booking of " + minutes + " min ended");
        }
    }

    public static void main(String[] args) {
        Scanner in = new Scanner(System.in);
        book(in.nextInt());
        book(in.nextInt());
    }
}
```

**Input:**

```text
90
200
```

**Output:**

```text
Open computer lab
Open projector
Using computer lab for 90 min
Using projector for 90 min
Close projector
Close computer lab
Finally: booking of 90 min ended
Open computer lab
Open projector
Close projector
Close computer lab
Caught: Booking too long: 200 min
Finally: booking of 200 min ended
```

**Why it works:** Resources are closed in reverse order of opening (projector first),
like plates taken off a stack. In the second booking, `lab.use(200)` throws, so
`projector.use` never runs. Both resources are still closed, and they are closed
**before** the `catch` block runs. The `finally` block runs last in both cases.

## Common Mistakes

- **Empty catch blocks.** `catch (Exception e) { }` hides the problem. The program
  continues with wrong values and the bug becomes hard to find.
- **Catching `Exception` everywhere.** It also catches `NullPointerException` and
  other bugs you did not plan for. Catch the specific types you expect.
- **General catch before specific catch.** `catch (IllegalArgumentException e)`
  above `catch (NumberFormatException e)` does not compile.
- **Forgetting to remove the bad token.** After `InputMismatchException`, call
  `in.next()` (or `nextLine()`), or the loop reads the same bad token forever.
- **Confusing `throw` and `throws`.** `throw` is a statement that throws an object;
  `throws` is part of a method header.
- **Using exceptions for normal decisions.** Checking a menu choice or a password
  attempt is a job for `if`, not for exceptions.
- **Messages without details.** `"Invalid"` does not say what was invalid. Include
  the value and the rule.
- **Expecting `double` division by zero to throw.** `5.0 / 0` gives `Infinity`; only
  integer `/` and `%` throw `ArithmeticException`.
- **Thinking `finally` is optional cleanup that may be skipped.** It runs in every
  case (unless the JVM itself stops, e.g. `System.exit`), so do not put code there
  that should run only on success.

## Summary

- An exception is an object that describes a problem at run time; throwing it stops
  normal flow until a matching `catch` is found.
- An unhandled exception ends the program with a stack trace: the top `at` line shows
  where it was thrown, the lines below show the chain of callers.
- `Throwable` has two branches: `Error` (serious problems, do not catch) and `Exception`.
- Checked exceptions (subclasses of `Exception` but not of `RuntimeException`) must be
  caught or declared with `throws`; unchecked ones (`RuntimeException`) need not be.
- `try`/`catch` handles problems; several catch blocks are checked top to bottom, so
  put specific types first; multi-catch `catch (A | B e)` shares one handler.
- `finally` always runs, whether an exception happened or not (unless the JVM stops,
  e.g. `System.exit`).
- `throw` throws an exception object; `throws` in a header declares what a method may
  pass to its caller.
- Custom exceptions extend `Exception` (checked) or `RuntimeException` (unchecked)
  and carry meaningful messages, read with `getMessage()`.
- `try-with-resources` closes `AutoCloseable` objects automatically, in reverse order,
  before `catch` and `finally` run.
- Validate early, catch only what you can handle, never swallow exceptions, and write
  messages that name the bad value.
