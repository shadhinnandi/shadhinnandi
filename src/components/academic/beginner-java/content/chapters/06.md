# Chapter 06: Constructors and Object Lifecycle

Every object has a life story. It is created with `new`, it is set up, it is used, and
one day nothing refers to it any more and its memory is reclaimed. This chapter follows
that story from start to end. You will learn how constructors make sure an object is
ready to use from its first moment, how to copy objects safely, and what really happens
when an object is no longer needed.

**In this chapter you will learn:**

- What a constructor is, when it runs, and how it differs from a method
- When Java gives you a default constructor, and when it does not
- Parameterized constructors, constructor overloading and chaining with `this(...)`
- That every constructor first calls a superclass constructor (`super(...)`)
- The exact order in which a new object is initialized
- How `final` fields and validation make objects trustworthy from the start
- How to write a copy constructor yourself, and the difference between shallow and deep copy
- The object lifecycle and how the garbage collector reclaims memory
- Why Java has no destructors, and how `try-with-resources` cleans up files and connections

## 1. Concept Explanation

### Why constructors exist

In Chapter 04 you often created an object first and filled in its fields afterwards:

```java
Student s = new Student();
s.name = "Rahim";
s.cgpa = 3.75;
```

This has a weakness. Between the first line and the last one, the object exists but is
only half ready. If you forget a line, the student silently has `name == null` and
`cgpa == 0.0`. With private fields (Chapter 05) you cannot even set them directly.

A **constructor** solves this. It is a special block of code that runs automatically,
exactly once, while the object is being created. Its job is to put the new object into a
valid starting state.

```java
Student s = new Student("Rahim", 3.75);   // created AND set up in one step
```

When `new` finishes and hands you the reference, the object is already complete.

### What happens during `new`

The expression `new Student("Rahim", 3.75)` does several things in a fixed order:

```text
 new Student("Rahim", 3.75)
        |
        v
 +---------------------------------------------+
 | 1. JVM allocates memory for the object      |
 |    on the heap                              |
 | 2. every field gets its default value       |
 |    (0, 0.0, false, null)                    |
 | 3. the constructor runs: superclass part,   |
 |    field initializers, then your body       |
 | 4. a reference to the finished object is    |
 |    returned                                 |
 +---------------------------------------------+
        |
        v
 Student s  -->  [ name: "Rahim" | cgpa: 3.75 ]
```

Step 3 is where your constructor code lives. You will see its inner order in detail
later in this chapter.

### Constructor vs method

A constructor looks like a method, but it is not one.

| | Constructor | Method |
|---|---|---|
| Name | exactly the class name | any name |
| Return type | none, not even `void` | required (`void`, `int`, ...) |
| When it runs | once, automatically, during `new` | whenever you call it |
| Purpose | set up a new object | do work with an existing object |
| Called on an existing object? | no | yes |

A common trap: if you write `void Student(...)`, it is no longer a constructor. It is
an ordinary method that happens to have the class name, and it will not run during `new`.

### The default constructor

If you write **no constructor at all**, the compiler adds one for you. It is called the
**default constructor**. It takes no parameters and does nothing except the
superclass step, so every field keeps its default value.

```java
class Book {
    String title;
}
// The compiler behaves as if you had written:  Book() { }
```

The important rule: the compiler adds it **only when you write none**. As soon as you
write any constructor, the free one disappears. If you still want a no-argument
constructor, you must write it yourself.

```java nocompile
class Book {
    String title;

    Book(String title) {
        this.title = title;
    }
}

public class NoDefaultDemo {
    public static void main(String[] args) {
        Book b = new Book();   // compile error: no constructor Book()
    }
}
```

The compiler reports something like `constructor Book in class Book cannot be applied
to given types`. People often call any no-argument constructor a "default constructor",
but strictly the term means the one the compiler generates.

### Parameterized constructors

A **parameterized constructor** takes the starting values as parameters. This is the
most common kind, because most objects need some data to make sense: a bank account
needs an owner, a course needs a code.

```java
class Course {
    private String code;
    private int credits;

    Course(String code, int credits) {
        this.code = code;
        this.credits = credits;
    }
}
```

`this.code` is the field; `code` alone is the parameter (Chapter 04). Writing
`code = code;` would assign the parameter to itself and leave the field `null`.

### Constructor overloading

A class may have several constructors, as long as their parameter lists differ in the
number, types or order of parameters. This is **constructor overloading**, the same idea
as method overloading in Chapter 03. The compiler picks the constructor whose parameters
match the arguments.

```java
new Course("CSE1115", 3);   // calls Course(String, int)
new Course("CSE1115");      // calls Course(String), if you wrote one
```

Overloading lets the caller give only the information they have, while the class fills
in sensible values for the rest.

### Constructor chaining with `this(...)`

Overloaded constructors often repeat the same assignments. Repeated code means repeated
bugs. Instead, let the shorter constructors call the most complete one with `this(...)`.
This is called **constructor chaining**.

```text
 Course("CSE1115")
       |  this(code, 3)
       v
 Course("CSE1115", 3)
       |  this(code, credits, "TBA")
       v
 Course("CSE1115", 3, "TBA")   <-- the only place with real set-up code
```

Rules for `this(...)`:

- It must be the **first statement** in the constructor.
- A constructor can call `this(...)` at most once.
- Constructors must not call each other in a circle (the compiler rejects it).

### `super(...)`: the first step of every constructor

Every class in Java has a parent class, called its **superclass**. If you do not name
one, the superclass is `Object`, the class at the top of every class hierarchy.

Every constructor starts by running a superclass constructor. You can write it as
`super(...)` in the first line. If the first line is neither `this(...)` nor
`super(...)`, the compiler silently inserts `super();` for you.

```java
class Course {
    private String code;

    Course(String code) {
        super();            // added automatically if you leave it out: runs Object()
        this.code = code;
    }
}
```

So the superclass part of an object is always ready before your constructor body runs.
For now you never need to write `super(...)` yourself. Chapter 09 (Inheritance) shows
when you must.

### Initialization order

A field can get its value in three places: a **field initializer** (`int seats = 40;`),
an **instance initializer block** (a plain `{ ... }` block inside the class), and the
constructor body. When you call `new`, they run in this order:

```text
 1. all fields get default values (0, false, null)
 2. superclass constructor (super(...))
 3. field initializers and instance initializer blocks,
    top to bottom, in the order they appear in the class
 4. the rest of the constructor body
```

If a constructor starts with `this(...)`, steps 2 and 3 happen once, inside the
constructor that is called last in the chain; then each constructor body finishes, from
the innermost back out to the one you called. Example 3 prints every step so you can see
the order with your own eyes.

Instance initializer blocks are rare in everyday code. Usually a field initializer plus
constructors is clearer. You should still know the order, because it explains surprising
output.

### `final` fields

A `final` field (Chapter 05) can be assigned **exactly once**. For an instance field
that means: either in its declaration, or in an initializer block, or in **every**
constructor. If any constructor path could leave it unassigned, the code does not
compile.

```java nocompile
class StudentCard {
    private final String studentId;
    private String name;

    StudentCard(String studentId, String name) {
        this.studentId = studentId;
        this.name = name;
    }

    StudentCard(String name) {
        this.name = name;
        // compile error: variable studentId might not have been initialized
    }
}
```

This is a feature, not an annoyance: the compiler guarantees that every `StudentCard`
has an ID. A constructor that uses `this(...)` counts as assigning it, because the called
constructor does the assignment.

### Validation in constructors

A constructor is the gatekeeper of an object. If it accepts bad data, the object starts
its life broken, and every method afterwards must deal with that. Check the parameters
before you store them.

At this stage of the course you have two simple choices:

- **Correct the value** to a safe one and report it (for example, set a negative balance
  to 0 and print a message).
- **Record that the object is invalid** in a `boolean` field and let the caller check it.

In Chapter 11 you will learn the professional way: the constructor *throws an
exception*, so an invalid object is never created at all.

```java
class Wallet {
    private int balance;

    Wallet(int balance) {
        if (balance < 0) {
            System.out.println("Negative balance " + balance + " set to 0");
            balance = 0;
        }
        this.balance = balance;
    }
}
```

Validate in one place: put the checks in the most complete constructor and let the other
constructors chain to it. Then no path can skip them.

### Copying objects: assignment copies only the reference

Suppose you want a second student just like the first one. This does **not** copy the
object:

```java
Student a = new Student("Nusrat", 3.90);
Student b = a;        // copies the reference, not the object
```

```text
 a --+
     +-->  [ name: "Nusrat" | cgpa: 3.90 ]
 b --+
```

There is still only one object, with two references to it. A change made through `b` is
visible through `a`. To get a real second object, you must create one with `new` and copy
the field values into it.

### Copy constructors: written by you

C++ has a copy constructor built into the language. **Java does not.** Java never copies
an object for you behind your back. If you want a convenient way to copy, you write a
normal constructor that takes an object of the same class and copies its fields. By
convention this is called a **copy constructor**.

```java
Student(Student other) {
    this.name = other.name;
    this.cgpa = other.cgpa;
}
```

Because it is in the same class, it may read `other`'s private fields. You call it like
any constructor: `Student b = new Student(a);`.

(Java also has a `clone()` method, but it is tricky to use correctly and is not
recommended for beginners; copy constructors are clearer.)

### Shallow copy vs deep copy

The tricky part is a field that refers to **another mutable object**. Say each `Student`
has an `Address` object, and `Address` has a `setCity` method.

A **shallow copy** copies each field's value as it is. For a reference field, that value
is the reference, so the copy points to the *same* `Address`:

```java
Student(Student other) {               // shallow
    this.name = other.name;
    this.address = other.address;      // same Address object!
}
```

```text
 SHALLOW COPY

 original --> [ name: "Rafi" | address: o-]--+
                                             |
                                             v
                                   [ Address: Dhaka ]
                                             ^
                                             |
 copy -----> [ name: "Rafi" | address: o-]---+
```

Now the bug: you move the copy to Chattogram with
`copy.getAddress().setCity("Chattogram")`. There is only one `Address` object, so the
original student moves too. Nobody asked for that.

A **deep copy** also copies the objects that the fields refer to, by calling *their*
copy constructors:

```java
Student(Student other) {               // deep
    this.name = other.name;
    this.address = new Address(other.address);   // a new Address
}
```

```text
 DEEP COPY

 original --> [ name: "Rafi" | address: o-]--> [ Address: Dhaka ]

 copy -----> [ name: "Rafi" | address: o-]--> [ Address: Dhaka ]
                                               (separate object)
```

Changing the copy's address now changes only the copy.

Which fields need a deep copy?

| Field type | What to do in a copy constructor |
|---|---|
| primitive (`int`, `double`, `boolean`, ...) | copy the value; it is already independent |
| `String` | copy the reference; `String` is immutable, so sharing is safe |
| reference to a mutable object (`Address`, `StringBuilder`) | usually create a new copy |
| reference to a shared real-world thing (the same teacher, the same bank) | sharing may be correct; decide on purpose |

Shallow or deep is a **design decision** for each field: "should the copy have its own
one, or should both share the same one?"

### The object lifecycle

Every object goes through the same stages:

```text
 +----------+    +--------+    +-------------+    +-----------+
 | created  |--->|  used  |--->| unreachable |--->| collected |
 | (new +   |    | (calls |    | (no live    |    | (memory   |
 | construc-|    |  on its|    |  reference  |    |  reused   |
 |   tor)   |    |  ref.) |    |  left)      |    |  by JVM)  |
 +----------+    +--------+    +-------------+    +-----------+
```

Your code drives the first three stages: it creates the object, uses it and finally
drops the last reference. Only the collection is done by the JVM.

### No destructors in Java: the garbage collector

In C++, a **destructor** is a function that runs at a known moment when an object is
destroyed, and programmers often free memory there. **Java has no destructors.** You
never free memory yourself; there is no `delete` and no `free`.

Instead, the JVM has a **garbage collector (GC)**. From time to time it finds objects
that the program can no longer reach and reuses their memory. *When* it runs is not
specified: it may be soon, much later, or never (if the program ends first). Your code
must not depend on the timing.

An object becomes **eligible for garbage collection** when no live reference can reach
it. The three everyday ways:

```text
 1. reference set to null
    Student s = new Student("Imran", 3.1);
    s = null;              s --> null      [Imran]  <- unreachable

 2. reference reassigned
    Student s = new Student("Imran", 3.1);
    s = new Student("Mitu", 3.6);
                           s --> [Mitu]    [Imran]  <- unreachable

 3. reference goes out of scope
    static void register() {
        Student temp = new Student("Sadia", 3.4);
    }                      // temp is gone   [Sadia] <- unreachable
                           // after the method returns
```

"Unreachable" means *no path* of references from the running program leads to it. If
another live object still holds a reference, the object stays alive.

Some facts to remember:

- `System.gc()` is only a **hint** asking the JVM to consider collecting. The JVM may
  ignore it. Never use it to "make the destructor run".
- Older Java had a method called `finalize()` that the GC might call before reclaiming
  an object. It is **deprecated** (since Java 9, and marked for removal since Java 18)
  because it may run late or never. Do not use it, and never treat it as a destructor.
- The GC manages **memory only**. It does not close your files, network connections or
  database connections at a predictable time.

### Cleaning up resources: `try-with-resources`

Memory is not the only thing an object can hold. A file, a printer session or a network
connection is a **resource**: something outside the object that must be released
promptly, at a known time. For these, Java gives you the `AutoCloseable` interface and
the `try-with-resources` statement.

- A class that says `implements AutoCloseable` promises to have a method
  `public void close()`. (An *interface* is a promise of methods; Chapter 10 covers
  interfaces fully.)
- In `try (Resource r = new Resource()) { ... }`, Java calls `r.close()` automatically
  when the block ends, however it ends: normally, through a `return`, or because of an
  error.
- If you open several resources in one `try`, they are closed in **reverse order** of
  opening.

```text
 try (LabSession s = new LabSession("PC-07")) {
     s.run("javac Hello.java");
 }                                  <-- s.close() runs here, always
```

This is the Java answer to "I need code that runs when I am done with an object." The
`try` statement has more features (`catch`, `finally`) that you will learn with
exceptions in Chapter 11.

### Coming from C++?

> **Coming from C++?** Java keeps constructors and overloading, but the end of an
> object's life works differently.

| C++ idea | Java equivalent |
|---|---|
| destructor frees memory | garbage collector reclaims unreachable objects automatically |
| destructor releases a file or lock | `AutoCloseable.close()` + `try-with-resources` |
| manually deleting an object | nothing: drop the reference and let the GC work |
| built-in copy constructor | none; write `Student(Student other)` yourself |
| `b = a;` copies the object | `b = a;` copies the reference only |
| default copy is member-wise | you choose shallow or deep, field by field |

## 2. Syntax

### Declaring and calling a constructor

```java
ClassName(Type1 param1, Type2 param2) {   // class name, no return type
    // set up the fields from the parameters
}

ClassName obj = new ClassName(arg1, arg2);  // runs only as part of new
```

You cannot call a constructor like a method (`obj.ClassName(...)` is an error). It runs
only during `new`, or from another constructor through `this(...)` or `super(...)`.

A constructor may have an access modifier (`public Course(...)`, `private Course(...)`).
Without one it is package-private, which is fine for the single-file programs in this
course. In a real project each public class lives in its own file; here we keep each
program in one file so you can compile it with one command.

### Overloading, `this(...)` and `super(...)`

```java
class Course {
    private String code;
    private int credits;
    private String room;

    Course(String code, int credits, String room) {   // the complete one
        super();                       // optional: inserted automatically
        this.code = code;
        this.credits = credits;
        this.room = room;
    }

    Course(String code, int credits) {
        this(code, credits, "TBA");    // must be the first statement
    }

    Course(String code) {
        this(code, 3);                 // chains to the two-parameter version
    }
}
```

The first statement of a constructor is `this(...)`, `super(...)`, or (if you write
neither) an invisible `super();`. A constructor cannot contain both.

### Field initializers, initializer blocks and `final` fields

```java
class Ticket {
    private final String ticketNo;      // final: set exactly once
    private int fare = 30;              // field initializer

    {                                   // instance initializer block
        System.out.println("Initializer block runs before the constructor body");
    }

    Ticket(String ticketNo) {
        this.ticketNo = ticketNo;       // every constructor must set it
    }
}
```

### A copy constructor

```java
class Address {
    private String city;

    Address(Address other) {            // copy constructor
        this.city = other.city;
    }
}

class Student {
    private String name;
    private Address address;

    Student(Student other) {            // deep copy constructor
        this.name = other.name;                       // String: sharing is safe
        this.address = new Address(other.address);    // mutable: make a new one
    }
}
```

### Making an object unreachable

```java
Student s = new Student("Imran", 3.1);
s = null;                              // that Student is now eligible for GC
System.gc();                           // only a request; no guarantee
```

You will almost never write `System.gc()` in real programs. It is shown only so you
recognise it.

### `AutoCloseable` and `try-with-resources`

```java
class ResourceName implements AutoCloseable {
    public void close() {              // must be public; no "throws" needed
        // release the resource
    }
}

try (ResourceName r = new ResourceName()) {
    // use r here
}   // r.close() runs automatically here

try (First a = new First(); Second b = new Second()) {
    // use a and b
}   // b.close() runs first, then a.close()
```

The variable declared in `try (...)` exists only inside the block. Use the resource in
the block: `javac -Xlint` warns about a resource that is never used.

## 3. Worked Examples

### Example 1: Library Books with Overloaded Constructors

**Problem:** The university library records books. Sometimes a librarian knows the
title, author and number of copies; sometimes only the title and author (then there is
1 copy); sometimes only the title (author "Unknown", 1 copy). Write a `Book` class with
three overloaded constructors that chain to one complete constructor, and create one book
of each kind.

Design:

- One complete constructor stores all fields.
- The other two constructors use `this(...)` to supply the missing values.
- A `describe()` method returns a one-line summary.

```java
class Book {
    private String title;
    private String author;
    private int copies;

    Book(String title, String author, int copies) {
        this.title = title;
        this.author = author;
        this.copies = copies;
        System.out.println("  [complete constructor ran for " + title + "]");
    }

    Book(String title, String author) {
        this(title, author, 1);
    }

    Book(String title) {
        this(title, "Unknown");
    }

    String describe() {
        return title + " by " + author + ", copies: " + copies;
    }
}

public class LibraryBooks {
    public static void main(String[] args) {
        System.out.println("Creating book 1");
        Book b1 = new Book("Java: A Beginner's Guide", "Herbert Schildt", 4);
        System.out.println("Creating book 2");
        Book b2 = new Book("Clean Code", "Robert Martin");
        System.out.println("Creating book 3");
        Book b3 = new Book("Old Lecture Notes");

        System.out.println(b1.describe());
        System.out.println(b2.describe());
        System.out.println(b3.describe());
    }
}
```

**Output:**

```text
Creating book 1
  [complete constructor ran for Java: A Beginner's Guide]
Creating book 2
  [complete constructor ran for Clean Code]
Creating book 3
  [complete constructor ran for Old Lecture Notes]
Java: A Beginner's Guide by Herbert Schildt, copies: 4
Clean Code by Robert Martin, copies: 1
Old Lecture Notes by Unknown, copies: 1
```

**Why it works:** The compiler picks a constructor by the arguments: three arguments
match `Book(String, String, int)`, two match `Book(String, String)`, one matches
`Book(String)`. `Book("Old Lecture Notes")` chains twice: it calls
`this(title, "Unknown")`, which calls `this(title, author, 1)`. The message from the
complete constructor appears once per book, which proves that all set-up code lives in
one place. If you later add a rule (for example, copies must not be negative), you add it
once.

### Example 2: Mobile Wallet with Validation and a Final Field

**Problem:** A campus mobile wallet has an owner, a phone number and a balance in Tk.
The phone number identifies the wallet, so it must never change after creation. A valid
phone number has 11 characters and starts with `01`; an invalid one is stored as
`"INVALID"` and the wallet is marked unusable. A negative starting balance is set to 0.
Read several wallets and print them.

Input format: an integer `n`, then `n` lines, each `owner phone balance` (owner is one
word).

Design:

- `phone` is `private final`: it must be assigned exactly once on every path through the
  constructor, which the `if`/`else` does.
- `usable` records whether validation passed, since we cannot throw exceptions yet.
- A second constructor `Wallet(owner, phone)` chains with a balance of 0, so validation
  is written once.

```java
import java.util.Scanner;

class Wallet {
    private final String phone;
    private String owner;
    private int balance;
    private boolean usable;

    Wallet(String owner, String phone, int balance) {
        this.owner = owner;
        if (phone.length() == 11 && phone.substring(0, 2).equals("01")) {
            this.phone = phone;
            usable = true;
        } else {
            System.out.println("Rejected phone " + phone + " for " + owner);
            this.phone = "INVALID";
            usable = false;
        }
        if (balance < 0) {
            System.out.println("Negative balance " + balance + " set to 0");
            balance = 0;
        }
        this.balance = balance;
    }

    Wallet(String owner, String phone) {
        this(owner, phone, 0);
    }

    boolean isUsable() {
        return usable;
    }

    String describe() {
        return owner + " (" + phone + "): Tk " + balance;
    }
}

public class WalletSetup {
    public static void main(String[] args) {
        Scanner in = new Scanner(System.in);
        int n = in.nextInt();
        int usableCount = 0;
        for (int i = 0; i < n; i++) {
            String owner = in.next();
            String phone = in.next();
            int balance = in.nextInt();
            Wallet w = new Wallet(owner, phone, balance);
            System.out.println(w.describe());
            if (w.isUsable()) {
                usableCount++;
            }
        }
        Wallet guest = new Wallet("Guest", "01700000000");
        System.out.println(guest.describe());
        System.out.println("Usable wallets from input: " + usableCount + " of " + n);
    }
}
```

**Input:**

```text
3
Ayesha 01711223344 500
Karim 0171 200
Tanvir 01822334455 -50
```

**Output:**

```text
Ayesha (01711223344): Tk 500
Rejected phone 0171 for Karim
Karim (INVALID): Tk 200
Negative balance -50 set to 0
Tanvir (01822334455): Tk 0
Guest (01700000000): Tk 0
Usable wallets from input: 2 of 3
```

**Why it works:** Every wallet passes through the same checks, because the two-parameter
constructor chains to the three-parameter one. The `final` field `phone` is assigned in
both branches of the `if`, so the compiler is satisfied that it is set exactly once.
There is no setter for `phone`, and because it is `final`, even code inside the class
cannot change it later. The `balance` parameter is corrected *before* it is stored, so the
field never holds a negative value, not even for a moment.

### Example 3: Tracing the Initialization Order

**Problem:** Show, by printing, the exact order in which Java initializes a new object:
default values, field initializers, an instance initializer block and constructor bodies,
including a constructor that chains with `this(...)`.

Design: the field initializers call a helper method `log(...)` that prints a message and
returns a value, so we can see when each initializer runs. The initializer block reads
`this.bonus` before `bonus` has been initialized, to show its default value.

```java
class Enrollment {
    private int base = log("field initializer: base = 10", 10);

    {
        System.out.println("instance initializer block: bonus is still " + this.bonus);
    }

    private int bonus = log("field initializer: bonus = 5", 5);
    private String course;

    Enrollment(String course, int extra) {
        System.out.println("constructor (String, int) body starts");
        this.course = course;
        bonus = bonus + extra;
    }

    Enrollment(String course) {
        this(course, 0);
        System.out.println("constructor (String) body finishes");
    }

    private int log(String message, int value) {
        System.out.println(message);
        return value;
    }

    String describe() {
        return course + ": base " + base + ", bonus " + bonus;
    }
}

public class InitOrder {
    public static void main(String[] args) {
        System.out.println("--- new Enrollment(\"CSE1115\", 2) ---");
        Enrollment a = new Enrollment("CSE1115", 2);
        System.out.println(a.describe());
        System.out.println("--- new Enrollment(\"MAT1101\") ---");
        Enrollment b = new Enrollment("MAT1101");
        System.out.println(b.describe());
    }
}
```

**Output:**

```text
--- new Enrollment("CSE1115", 2) ---
field initializer: base = 10
instance initializer block: bonus is still 0
field initializer: bonus = 5
constructor (String, int) body starts
CSE1115: base 10, bonus 7
--- new Enrollment("MAT1101") ---
field initializer: base = 10
instance initializer block: bonus is still 0
field initializer: bonus = 5
constructor (String, int) body starts
constructor (String) body finishes
MAT1101: base 10, bonus 5
```

**Why it works:** Before any of your code runs, every field already holds its default
value, which is why the block prints `bonus is still 0`. After the (invisible) `super()`
call, the field initializers and the block run top to bottom in source order. Only then
does the constructor body run. For `new Enrollment("MAT1101")`, the call `this(course, 0)`
happens first; the initializers run once, inside the two-parameter constructor, and the
one-parameter constructor's own line prints last.

### Example 4: Shallow Copy vs Deep Copy

**Problem:** A hostel office keeps a `Student` record with a name and an `Address`. When
Rafi's younger brother joins, the clerk copies Rafi's record and then changes the name
and the city. Write the copy two ways, shallow and deep, and show what happens to Rafi's
original record in each case.

Design:

- `Address` is mutable (it has `setCity`) and has its own copy constructor.
- `Student` has a deep copy constructor `Student(Student other)`.
- For comparison, `shallowCopy()` builds a copy that shares the `Address`. (It uses a
  private constructor that takes the parts.)

```java
class Address {
    private String area;
    private String city;

    Address(String area, String city) {
        this.area = area;
        this.city = city;
    }

    Address(Address other) {
        this.area = other.area;
        this.city = other.city;
    }

    void setCity(String city) {
        this.city = city;
    }

    String describe() {
        return area + ", " + city;
    }
}

class Student {
    private String name;
    private Address address;

    Student(String name, Address address) {
        this.name = name;
        this.address = address;
    }

    // Deep copy constructor: the copy gets its own Address.
    Student(Student other) {
        this.name = other.name;
        this.address = new Address(other.address);
    }

    // Shallow copy: the copy shares the same Address object.
    Student shallowCopy() {
        return new Student(name, address);
    }

    void setName(String name) {
        this.name = name;
    }

    Address getAddress() {
        return address;
    }

    String describe() {
        return name + " lives at " + address.describe();
    }
}

public class CopyDemo {
    public static void main(String[] args) {
        Student rafi = new Student("Rafi", new Address("Mirpur", "Dhaka"));

        System.out.println("Shallow copy:");
        Student brother = rafi.shallowCopy();
        brother.setName("Arif");
        brother.getAddress().setCity("Chattogram");
        System.out.println("  " + rafi.describe());
        System.out.println("  " + brother.describe());

        Student rafi2 = new Student("Rafi", new Address("Mirpur", "Dhaka"));
        System.out.println("Deep copy:");
        Student brother2 = new Student(rafi2);
        brother2.setName("Arif");
        brother2.getAddress().setCity("Chattogram");
        System.out.println("  " + rafi2.describe());
        System.out.println("  " + brother2.describe());
    }
}
```

**Output:**

```text
Shallow copy:
  Rafi lives at Mirpur, Chattogram
  Arif lives at Mirpur, Chattogram
Deep copy:
  Rafi lives at Mirpur, Dhaka
  Arif lives at Mirpur, Chattogram
```

**Why it works:** Changing the name never affects the original, because `setName` puts a
new `String` reference into the copy's own `name` field. The address is different. In
the shallow copy, both `Student` objects hold a reference to one `Address` object, so
`setCity` through the brother also "moves" Rafi. That is the classic shallow-copy bug. The
deep copy constructor calls `new Address(other.address)`, so the brother gets a separate
`Address`, and Rafi's record stays correct.

### Example 5: Lab Sessions with try-with-resources

**Problem:** In the computer lab, a student logs in to a PC and to a printer queue, does
some work, and must always be logged out of both, even when the work stops early. Write
resource classes that print a message when they are opened and closed, and show the order
in which Java closes them.

Design:

- `LabSession` and `PrintQueue` implement `AutoCloseable`; their `close()` prints a
  message.
- `doWork` uses both in one `try` and returns early when there are no pages to print.
- We call `doWork` twice: once normally, once with the early `return`.

```java
class LabSession implements AutoCloseable {
    private String pc;

    LabSession(String pc) {
        this.pc = pc;
        System.out.println("Logged in to " + pc);
    }

    void run(String command) {
        System.out.println("  " + pc + " runs: " + command);
    }

    public void close() {
        System.out.println("Logged out of " + pc);
    }
}

class PrintQueue implements AutoCloseable {
    private String student;
    private int printed;

    PrintQueue(String student) {
        this.student = student;
        System.out.println("Print queue opened for " + student);
    }

    void print(int pages) {
        printed = printed + pages;
        System.out.println("  printed " + pages + " page(s)");
    }

    public void close() {
        System.out.println("Print queue closed for " + student
                + " (" + printed + " page(s))");
    }
}

public class LabDay {
    static void doWork(String student, String pc, int pages) {
        try (LabSession session = new LabSession(pc);
                PrintQueue queue = new PrintQueue(student)) {
            session.run("javac Report.java");
            if (pages == 0) {
                System.out.println("  nothing to print, leaving early");
                return;
            }
            queue.print(pages);
        }
        System.out.println("Work finished normally for " + student);
    }

    public static void main(String[] args) {
        doWork("Sadia", "PC-12", 3);
        System.out.println();
        doWork("Fahim", "PC-03", 0);
        System.out.println("Back in main");
    }
}
```

**Output:**

```text
Logged in to PC-12
Print queue opened for Sadia
  PC-12 runs: javac Report.java
  printed 3 page(s)
Print queue closed for Sadia (3 page(s))
Logged out of PC-12
Work finished normally for Sadia

Logged in to PC-03
Print queue opened for Fahim
  PC-03 runs: javac Report.java
  nothing to print, leaving early
Print queue closed for Fahim (0 page(s))
Logged out of PC-03
Back in main
```

**Why it works:** Both resources are declared in the `try (...)` header, separated by a
semicolon. When the block ends, Java calls `close()` on them in reverse order: the print
queue, which was opened last, is closed first. In Fahim's run, the `return` leaves the
method early, yet both `close()` calls still happen before the method returns; that is
why "Work finished normally" is not printed for him, but the logout messages are. This is
deterministic clean-up at a known point, which the garbage collector cannot give you.

## Common Mistakes

- **Adding a return type to a constructor.** `void Book(String t) { ... }` is a method,
  not a constructor. `new Book("x")` then fails to compile, or the fields stay at their
  defaults.
- **Expecting the default constructor after writing your own.** Once you write any
  constructor, `new Book()` only works if you also write `Book()` yourself.
- **Assigning a parameter to itself.** `name = name;` changes nothing. Write
  `this.name = name;`.
- **Putting `this(...)` anywhere but the first line.** The compiler rejects it.
- **Copying code between overloaded constructors** instead of chaining. Sooner or later
  one copy gets a fix and the others do not.
- **Thinking `b = a;` copies an object.** It copies the reference; both names refer to
  one object.
- **Writing a shallow copy constructor for a class with mutable fields.** The copy and
  the original then secretly share those objects. Copy mutable fields with their own
  copy constructors.
- **Looking for a destructor.** Java has none. Do not override `finalize()` and do not
  call `System.gc()` hoping something will happen at a certain time.
- **Forgetting to close resources.** Use `try-with-resources` for anything that
  implements `AutoCloseable`, so `close()` runs even on an early `return`.

## Summary

- A constructor has the class name and no return type; it runs once, during `new`, to
  put the object into a valid starting state.
- The compiler adds a no-argument default constructor only when the class has no
  constructor at all.
- Constructors can be overloaded; shorter ones should chain to the complete one with
  `this(...)` as their first statement, so set-up and validation live in one place.
- Every constructor first runs a superclass constructor (`super(...)`, inserted
  automatically if you write neither `this(...)` nor `super(...)`); `Object` is at the
  top.
- Initialization order: default values, superclass constructor, field initializers and
  initializer blocks in source order, then the constructor body.
- A `final` field must be assigned exactly once on every constructor path.
- Java has no built-in copy constructor; write `ClassName(ClassName other)` yourself and
  decide for each reference field whether to share it (shallow) or copy it (deep).
- An object becomes eligible for garbage collection when no live reference can reach it;
  the garbage collector reclaims it at an unspecified time, and `System.gc()` is only a
  hint.
- Java has no destructors and `finalize()` is deprecated; release files and other
  resources with `try-with-resources` and `AutoCloseable.close()`.
