# Chapter 05: Encapsulation, Abstraction and Access Control

In Chapter 04 you built classes whose fields any other code could read and change. That
works for tiny programs, but as soon as a program grows, one careless line somewhere can
put an object into a state that makes no sense: a bank balance of minus 5000 Tk, a
course section with 45 students in 40 seats. This chapter shows how a class protects
itself, how it shows other code only *what* it does and hides *how*, and how Java's
access modifiers enforce those decisions at compile time.

**In this chapter you will learn:**

- what encapsulation is: bundling data with its methods and protecting the object's rules
- what an invariant is and why a class must guard it
- data hiding with `private`, and getters and setters (and why not every field needs a setter)
- how to validate changes without exceptions (keep the old value and return `false`)
- what abstraction is: the public interface (what) versus the implementation (how)
- the exact difference between encapsulation and abstraction
- the four access levels: `private`, package-private, `protected`, `public`
- `final` fields and immutable objects (and why `String` is immutable)
- how a badly designed class gets corrupted, and how a well designed class prevents it

## 1. Concept Explanation

### The problem: anyone can change anything

Here is a class in the Chapter 04 style. Its fields have no access modifier, so every
other class in the program can change them directly.

```java
class CourseSection {
    String courseCode;
    int capacity;
    int enrolled;
}
```

Nothing stops other code from doing this:

```java
CourseSection section = new CourseSection();
section.capacity = 40;
section.enrolled = 45;      // 45 students in 40 seats
section.capacity = -10;     // a negative capacity
```

The compiler accepts every line. The object now holds data that is impossible in the
real world, and the bug may only show up much later, far away from the line that caused
it. In a program with 50 classes, finding *who* set `enrolled` to 45 is painful.

The cause is not one bad line. The cause is a design that *allows* bad lines. The rest of
this chapter fixes the design.

### Invariants: the rules an object must always obey

An **invariant** is a condition that must be true for an object at every moment that
other code can see it. Some examples:

| Class | Invariant |
|---|---|
| `BankAccount` | `balance >= 0` |
| `CourseSection` | `0 <= enrolled <= capacity` |
| `GradeRecord` | `0 <= marks <= 100` |
| `InventoryItem` | `stock >= 0` and `price > 0` |
| `ClockTime` | `0 <= hour <= 23` and `0 <= minute <= 59` |

If any code in the program can write to the fields, then *every* line of the program
is responsible for keeping the invariant true. That is impossible to check. If only the
class itself can write to its fields, then only the class's own methods must be checked.
That is the core idea of encapsulation.

### What encapsulation means

**Encapsulation** has two parts:

1. **Bundling:** the data (fields) and the code that works on that data (methods) live
   together in one class.
2. **Protection:** the data is hidden, and other code can change it only through the
   class's methods, which check the rules first.

```text
          other code
              |
              |  deposit(500)   withdraw(200)   getBalance()
              v
   +----------------------------------------------+
   |  BankAccount                                 |
   |   public methods  (the only doors)           |
   |  +----------------------------------------+  |
   |  |  private int balance;                  |  |
   |  |  private String owner;                 |  |
   |  |  (no direct access from outside)       |  |
   |  +----------------------------------------+  |
   +----------------------------------------------+
```

Think of a medicine capsule: the powder is inside, and you take the capsule as one unit
without touching the powder. In Java, the "shell" is made of access modifiers, and the
compiler refuses any code outside the class that tries to touch a hidden field.

### Data hiding with `private`

The keyword `private` makes a field (or method) visible **only inside its own class**.
Code in any other class gets a compile error if it tries to use it.

```java
class BankAccount {
    private int balance;     // only BankAccount's own methods can use this

    boolean deposit(int amount) {
        if (amount <= 0) {
            return false;        // rule: deposits must be positive
        }
        balance = balance + amount;
        return true;
    }

    int getBalance() {
        return balance;
    }
}
```

Hiding the data is called **data hiding**. It is the tool; encapsulation is the goal.
Because `balance` is private, the only ways to change it are the methods that the class
author wrote and checked.

> **Note:** `private` is a rule for *code*, checked by the compiler. It is not
> encryption and not a security feature against people. Its job is to stop other parts
> of the program from breaking an object by mistake.

`private` works per **class**, not per object. A method of `BankAccount` may read the
private fields of *another* `BankAccount` object (for example, in a `transferTo` method).
Code in a different class may not.

### Getters and setters

A **getter** is a method that returns the value of a field. A **setter** is a method
that changes a field, usually after checking the new value. By convention:

| Field | Getter | Setter |
|---|---|---|
| `String name` | `getName()` | `setName(String name)` |
| `int marks` | `getMarks()` | `setMarks(int marks)` |
| `boolean active` | `isActive()` | `setActive(boolean active)` |

Getters and setters are not magic. They are ordinary methods. Their value comes from the
fact that the field is private, so the method is the only way in.

### Not every field needs a setter

Beginners often make every field private and then add a public getter and setter for
each one. That gives almost no protection: `setBalance(-5000)` is no better than
`balance = -5000`. Ask for each field: *"Should other code be allowed to change this
directly?"*

| Field | Setter? | Why |
|---|---|---|
| student ID | No | An ID never changes after the object is created. |
| account balance | No | It changes only through `deposit` and `withdraw`, which apply rules. |
| number of rides taken | No | It only grows, inside `ride()`. |
| phone number | Yes, validated | A person can change it, but it must look like a phone number. |
| password / PIN | No getter at all | Other code may *check* a PIN, never read it. |

Prefer methods named after real actions (`deposit`, `enroll`, `restock`, `borrow`) over
raw setters. An action method can apply the business rule; a raw setter usually cannot.

### Validation without exceptions

When a method receives an invalid value, it must not store it. For now (exceptions come
in Chapter 11) there are two simple ways to reject a value:

1. **Keep the old value and return `false`.** The caller checks the result and decides
   what to do. This keeps input/output code out of the class. This is the style used in
   this chapter.
2. **Keep the old value and print a message.** Simple, but the class now decides how
   errors are shown, which makes it harder to reuse.

```java
boolean setMarks(int newMarks) {
    if (newMarks < 0 || newMarks > 100) {
        return false;          // reject: marks keeps its old value
    }
    marks = newMarks;
    return true;
}
```

> In Chapter 11 you will learn to *throw an exception* instead, which forces the caller
> to notice the error. The rule stays the same: an invalid value never gets stored.

### Abstraction: what, not how

**Abstraction** means showing other code *what* an object can do and hiding *how* it
does it. The "what" is the **public interface**: the method names, their parameters and
what they promise. The "how" is the **implementation**: private fields, private helper
methods and the algorithms inside the method bodies.

Analogy: when you order at the campus canteen, you say "one plate of khichuri". You do
not tell the cook how to make it, and if the cook changes the recipe you still order the
same way. The menu is the interface; the kitchen is the implementation.

You have already used abstraction many times:

- `Scanner.nextInt()` reads a number. You do not know how it buffers input or skips
  spaces, and you do not need to.
- `"hello".length()` gives a length. You do not know how `String` stores its
  characters inside (and it has changed between Java versions without breaking your
  code).
- `Math.sqrt(2.0)` returns a square root. The algorithm is hidden.

```text
   What other code sees            What stays hidden
   (public interface)              (implementation)
  +---------------------------+   +-------------------------------+
  | boolean withdraw(int tk)  |   | private int balance;          |
  | int getBalance()          |   | private int feeFor(int tk)    |
  |                           |   | fee rule: 1.5% above 1000 Tk  |
  +---------------------------+   +-------------------------------+
        stable, small                 free to change later
```

The benefit: the class author can change the implementation (a new fee rule, a faster
algorithm, a different way to store data) without changing any code that uses the class,
as long as the interface stays the same.

### Encapsulation vs abstraction

These two ideas are related and often confused. They answer different questions.

| | Encapsulation | Abstraction |
|---|---|---|
| Main question | "Who may touch this data?" | "What does the user of this class need to know?" |
| Focus | Protecting the object's state | Simplifying how the object is used |
| Hides | Data (fields) | Complexity (how the work is done) |
| Main tool in Java | `private` fields + checked methods | A small, well named public interface |
| Protects against | Invalid states (broken invariants) | Callers depending on details |
| Without it | Any code can set `balance = -5000` | Every caller must know the fee formula |
| Level | Implementation / code level | Design / interface level |

**One example showing both:**

```java
class BankAccount {
    private int balance;                  // ENCAPSULATION: hidden, protected data

    boolean withdraw(int amount) {        // ABSTRACTION: the caller sees only this
        int total = amount + feeFor(amount);
        if (amount <= 0 || total > balance) {
            return false;                 // ENCAPSULATION: balance never goes negative
        }
        balance = balance - total;
        return true;
    }

    private int feeFor(int amount) {      // ABSTRACTION: how the fee works is hidden
        if (amount <= 1000) {
            return 0;
        }
        return amount * 15 / 1000;        // 1.5% (a hypothetical rule)
    }
}
```

The caller writes `account.withdraw(2000)` and checks `true` or `false`.

- **Encapsulation** is the reason the caller *cannot* write `account.balance = -5000`:
  the balance is private and `withdraw` refuses anything that would make it negative.
- **Abstraction** is the reason the caller *does not need to* know the fee rule: if the
  bank changes it to 2%, only `feeFor` changes, and no caller is edited.

A short way to remember it: **encapsulation hides the data; abstraction hides the
complexity.**

### Access modifiers

Java has four access levels. Three have keywords; the fourth is what you get when you
write no keyword at all.

| Modifier | Same class | Same package | Subclass (other package) | Any other class |
|---|---|---|---|---|
| `private` | Yes | No | No | No |
| (none) = package-private | Yes | Yes | No | No |
| `protected` | Yes | Yes | Yes | No |
| `public` | Yes | Yes | Yes | Yes |

- **`private`**: only inside the class. Use it for almost all fields and for helper
  methods.
- **package-private** (no keyword): visible to every class in the same package. This is
  what Chapter 04 used.
- **`protected`**: like package-private, plus subclasses in other packages. Subclasses
  come with inheritance in Chapter 09, where `protected` is explained fully.
- **`public`**: visible to every class everywhere. Use it for the methods that form the
  class's interface.

A top-level class itself can only be `public` or package-private.

### Packages (concept only)

A **package** is a named group of related classes, like a folder. Java's own classes
live in packages: `Scanner` is in `java.util`, `String` is in `java.lang`. That is why you
write `import java.util.Scanner;`. Large projects put their own classes in packages such
as `bd.campus.library` and use access modifiers to decide what other packages may use.

The programs in this course are single files without a `package` line. All classes in
such a file belong to the same unnamed package, so package-private members are visible
to every class in the file. That is why `private` is the modifier that matters most in
our examples. In a real project each public class lives in its own file; here we keep
each program in one file so you can compile it with one command.

### `final` fields

A `final` field can be assigned **exactly once**: either where it is declared or in the
constructor. After that, the compiler rejects any assignment.

```java
class Student {
    private final String studentId;   // set once, never changed
    private String name;

    Student(String studentId, String name) {
        this.studentId = studentId;
        this.name = name;
    }
}
```

`final` turns "the ID never changes" from a comment into a rule the compiler checks.
Chapter 06 shows more about `final` fields and constructors.

Careful: `final` on a field that holds a *reference* means the field always refers to the
same object. It does not freeze the object itself. A `final StringBuilder log` can still
be changed with `log.append("x")`; it just cannot be replaced by another `StringBuilder`.

### Immutable objects

An **immutable** object cannot change after it is created. Java's `String` is immutable:
`toUpperCase()` does not change the string, it returns a *new* string.

```java
String city = "dhaka";
city.toUpperCase();              // result thrown away; city is still "dhaka"
city = city.toUpperCase();       // city now refers to a new String "DHAKA"
```

To make your own class immutable:

1. Make every field `private final`.
2. Set all fields in the constructor.
3. Write no setters and no method that changes a field.
4. For a "change", return a **new object** with the new values.
5. Do not store or return a reference to a mutable object (such as a `StringBuilder`)
   that outside code could change.

Classes are often also declared `final` so that no subclass can add changing behaviour;
Chapter 09 explains this.

Why bother? An immutable object has no invariants to break after construction, can be
shared freely between many parts of a program, and is easy to reason about. Values such
as money amounts, dates, times, coordinates and fractions are ideal candidates.

> **Note (Java 16+):** Java has *records*, a short way to write an immutable data class:
> `record Point(int x, int y) { }` creates private final fields, a constructor and
> getters `x()` and `y()`. This course writes immutable classes by hand so you can see
> every part.

### Bad design vs good design

Here are the two designs side by side in code. The bad one exposes its fields:

```java
// BAD: anyone can write any value
class Thermostat {
    double targetCelsius;
}

// some other class, far away:
thermostat.targetCelsius = 500.0;   // compiles, and now the heater is told 500 C
```

The good one hides the field and guards the rule:

```java
// GOOD: the only way in is a checked method
class Thermostat {
    private double targetCelsius = 22.0;

    boolean setTarget(double celsius) {
        if (celsius < 16.0 || celsius > 30.0) {
            return false;               // keep the old target
        }
        targetCelsius = celsius;
        return true;
    }

    double getTarget() {
        return targetCelsius;
    }
}

// some other class:
thermostat.setTarget(500.0);        // returns false; target stays 22.0
// thermostat.targetCelsius = 500.0;   would not compile: private access
```

| Bad design (public fields) | Good design (encapsulated) |
|---|---|
| Any line in the program can break the object | Only the class's methods can change the state |
| Rules are copied (or forgotten) in every caller | Rules are written once, inside the class |
| A bug can come from anywhere | A broken invariant points to one class |
| Changing a field's type breaks all callers | Internals can change; the interface stays |

Example 1 in section 3 shows this difference in a running program.

### Designing good classes

Use this checklist when you design a class:

1. **Should this be a class?** Does it have its own data *and* rules? A course section
   (seats, enrolment rules) is a class. A single number with no rules usually is not.
2. **Write down the invariants** before writing code ("stock is never negative").
3. **Make every field `private`.** Make fields `final` when they never change.
4. **Keep the public interface small.** Every public method is a promise you must keep.
   Helper methods that callers do not need are `private`.
5. **Name methods after actions** (`enroll`, `withdraw`, `restock`), not after fields.
6. **Add getters only for information callers really need**, and setters only for
   fields that may legally change, always with validation.
7. **Prefer immutable classes** for values (money, dates, times).

## 2. Syntax

### Private fields with public methods

```java
class GradeRecord {
    private String studentName;    // private: hidden data
    private int marks;

    public int getMarks() {        // public: part of the interface
        return marks;
    }
}
```

The access modifier comes first, before the type. In single-file programs you will often
see methods written without `public`; they are then package-private, which is enough
because all classes are in the same package. Writing `public` on the interface methods
makes your intent clear.

### Getter and setter pair

```java
public String getName() {
    return name;
}

public void setName(String name) {
    this.name = name;              // this.name is the field, name is the parameter
}
```

Remember `this` from Chapter 04: when the parameter has the same name as the field,
`this.name` means the field.

### A validating setter that returns `boolean`

```java
public boolean setPhone(String phone) {
    if (phone.length() != 11 || !phone.startsWith("01")) {
        return false;              // invalid: keep the old phone number
    }
    this.phone = phone;
    return true;
}
```

The caller uses the result:

```java
if (!student.setPhone(input)) {
    System.out.println("Invalid phone number, not changed");
}
```

### Boolean getter

```java
private boolean onLoan;

public boolean isOnLoan() {        // "is" instead of "get" for a boolean
    return onLoan;
}
```

### A private helper method

```java
public int priceFor(int quantity) {
    return quantity * unitPrice - discountFor(quantity);
}

private int discountFor(int quantity) {   // callers never see this
    if (quantity >= 10) {
        return quantity * unitPrice / 10;
    }
    return 0;
}
```

### The four access levels on members

```java
class Example {
    private int a;        // this class only
    int b;                // package-private: same package
    protected int c;      // same package + subclasses (Chapter 09)
    public int d;         // everyone (a public field is almost always a bad idea)
}
```

### What the compiler says

Accessing a private member from another class is a compile error:

```java nocompile
class Wallet {
    private int balance;
}

public class Hack {
    public static void main(String[] args) {
        Wallet w = new Wallet();
        w.balance = 1000000;
    }
}
```

```text
Hack.java:8: error: balance has private access in Wallet
        w.balance = 1000000;
         ^
1 error
```

### `final` fields

```java
class Book {
    private final String isbn;          // must be set in the constructor
    private final int maxLoanDays = 14; // or where it is declared

    Book(String isbn) {
        this.isbn = isbn;
    }

    void wrong() {
        // isbn = "123";   compile error: cannot assign a value to final variable isbn
    }
}
```

### An immutable class

```java
class Point {
    private final int x;
    private final int y;

    Point(int x, int y) {
        this.x = x;
        this.y = y;
    }

    public int getX() {
        return x;
    }

    public int getY() {
        return y;
    }

    public Point moveBy(int dx, int dy) {
        return new Point(x + dx, y + dy);   // a new object; this one is unchanged
    }
}
```

Calling `p.moveBy(1, 2)` does not move `p`. You must keep the result:
`p = p.moveBy(1, 2);`.

## 3. Worked Examples

### Example 1: Bad Design vs Good Design

**Problem:** A course section has a course code, a capacity and a number of enrolled
students. Show what happens when the fields are open to everyone, and how an
encapsulated version keeps the rule `0 <= enrolled <= capacity` no matter what other
code tries.

Both designs are in one program. `OpenSection` uses non-private fields like Chapter 04.
`CourseSection` makes every field private, makes the code and capacity `final`, and
offers only `enroll()`, `drop()` and getters. There is no `setEnrolled`: the count may
change only by one student at a time through the rules.

```java
class OpenSection {
    String courseCode;
    int capacity;
    int enrolled;
}

class CourseSection {
    private final String courseCode;
    private final int capacity;
    private int enrolled;

    CourseSection(String courseCode, int capacity) {
        this.courseCode = courseCode;
        this.capacity = capacity;
        this.enrolled = 0;
    }

    public boolean enroll() {
        if (enrolled >= capacity) {
            return false;
        }
        enrolled++;
        return true;
    }

    public boolean drop() {
        if (enrolled == 0) {
            return false;
        }
        enrolled--;
        return true;
    }

    public String getCourseCode() {
        return courseCode;
    }

    public int getCapacity() {
        return capacity;
    }

    public int getEnrolled() {
        return enrolled;
    }

    public int getSeatsLeft() {
        return capacity - enrolled;
    }
}

public class SectionDesign {
    public static void main(String[] args) {
        OpenSection open = new OpenSection();
        open.courseCode = "CSE 1115";
        open.capacity = 40;
        open.enrolled = 40;
        // Somewhere else in a big program, careless code runs:
        open.enrolled = open.enrolled + 5;
        open.capacity = -10;
        System.out.println("Open design:");
        System.out.println("  " + open.courseCode + ": " + open.enrolled
                + " enrolled, capacity " + open.capacity);

        CourseSection safe = new CourseSection("CSE 1115", 40);
        int accepted = 0;
        int refused = 0;
        for (int i = 1; i <= 45; i++) {
            if (safe.enroll()) {
                accepted++;
            } else {
                refused++;
            }
        }
        System.out.println("Encapsulated design:");
        System.out.println("  accepted " + accepted + ", refused " + refused);
        System.out.println("  " + safe.getCourseCode() + ": " + safe.getEnrolled()
                + " enrolled, capacity " + safe.getCapacity());
        safe.drop();
        System.out.println("  after one drop: " + safe.getSeatsLeft() + " seat(s) left");
        // safe.enrolled = 45;     would not compile: enrolled has private access
    }
}
```

**Output:**

```text
Open design:
  CSE 1115: 45 enrolled, capacity -10
Encapsulated design:
  accepted 40, refused 5
  CSE 1115: 40 enrolled, capacity 40
  after one drop: 1 seat(s) left
```

**Why it works:** The open design trusts every line of the program, and two careless
lines are enough to create a section with more students than seats and a negative
capacity. The encapsulated design trusts only its own methods. `enrolled` is private, so
the only way to change it is `enroll()` or `drop()`, and both check the rule first. The
5 extra students are refused, and the invariant holds after every call.

### Example 2: Getters, Setters and Validation

**Problem:** Keep a student's profile: an ID that never changes, a name that may be
corrected but never be blank, a CGPA that must stay between 0.00 and 4.00, and a count
of completed credits that may only grow. Try several valid and invalid updates and show
that invalid ones leave the old value in place.

Design decisions, field by field:

- `studentId`: `private final`, getter only. It never changes.
- `name`: getter and a validating setter that rejects a blank name.
- `cgpa`: getter and a validating setter (0.00 to 4.00).
- `completedCredits`: getter and `addCredits(int)`, but no setter, because credits are
  only ever added.

```java
class StudentProfile {
    private final String studentId;
    private String name;
    private double cgpa;
    private int completedCredits;

    StudentProfile(String studentId, String name) {
        this.studentId = studentId;
        this.name = name;
        this.cgpa = 0.0;
        this.completedCredits = 0;
    }

    public String getStudentId() {
        return studentId;
    }

    public String getName() {
        return name;
    }

    public double getCgpa() {
        return cgpa;
    }

    public int getCompletedCredits() {
        return completedCredits;
    }

    public boolean setName(String newName) {
        if (newName == null || newName.trim().length() == 0) {
            return false;
        }
        name = newName.trim();
        return true;
    }

    public boolean setCgpa(double newCgpa) {
        if (newCgpa < 0.0 || newCgpa > 4.0) {
            return false;
        }
        cgpa = newCgpa;
        return true;
    }

    public boolean addCredits(int credits) {
        if (credits <= 0 || credits > 24) {
            return false;
        }
        completedCredits = completedCredits + credits;
        return true;
    }
}

public class ProfileDemo {
    static void report(String action, boolean ok) {
        System.out.println(action + " -> " + (ok ? "accepted" : "rejected"));
    }

    static void show(StudentProfile p) {
        System.out.printf("%s | %s | CGPA %.2f | %d credits%n", p.getStudentId(),
                p.getName(), p.getCgpa(), p.getCompletedCredits());
    }

    public static void main(String[] args) {
        StudentProfile p = new StudentProfile("011221045", "Nusrat Jahn");
        show(p);
        report("setCgpa(3.85)", p.setCgpa(3.85));
        report("setCgpa(4.50)", p.setCgpa(4.50));
        report("setName(\"   \")", p.setName("   "));
        report("setName(\"Nusrat Jahan\")", p.setName("Nusrat Jahan"));
        report("addCredits(-3)", p.addCredits(-3));
        report("addCredits(12)", p.addCredits(12));
        show(p);
    }
}
```

**Output:**

```text
011221045 | Nusrat Jahn | CGPA 0.00 | 0 credits
setCgpa(3.85) -> accepted
setCgpa(4.50) -> rejected
setName("   ") -> rejected
setName("Nusrat Jahan") -> accepted
addCredits(-3) -> rejected
addCredits(12) -> accepted
011221045 | Nusrat Jahan | CGPA 3.85 | 12 credits
```

**Why it works:** Every change goes through a method that checks the new value before
storing it. A rejected update returns `false` and leaves the field alone, so the CGPA is
still 3.85 after the attempt to set 4.50. The class never prints anything itself; it
reports success with a `boolean`, and `main` decides what to print. There is no way to
change `studentId` at all, and no way to reduce `completedCredits`, because no method
does that.

### Example 3: Encapsulation and Abstraction Together

**Problem:** A bank account (fees are hypothetical) allows deposits and withdrawals.
Withdrawals up to 1000 Tk are free; above that a fee of 1.5% of the amount is charged.
The balance, including the fee, must never go negative. The code that uses the account
should not need to know the fee rule.

- **Encapsulation:** `balance` is private and changes only through `deposit` and
  `withdraw`, which refuse anything that would break `balance >= 0`.
- **Abstraction:** callers see `withdraw(int)` and `getBalance()`. The fee rule lives in
  a private helper `feeFor`, so it can change without touching `main`.

```java
class BankAccount {
    private final String owner;
    private int balance;

    BankAccount(String owner) {
        this.owner = owner;
        this.balance = 0;
    }

    public boolean deposit(int amount) {
        if (amount <= 0) {
            return false;
        }
        balance = balance + amount;
        return true;
    }

    public boolean withdraw(int amount) {
        if (amount <= 0) {
            return false;
        }
        int total = amount + feeFor(amount);
        if (total > balance) {
            return false;
        }
        balance = balance - total;
        return true;
    }

    public int getBalance() {
        return balance;
    }

    public String getOwner() {
        return owner;
    }

    private int feeFor(int amount) {
        if (amount <= 1000) {
            return 0;
        }
        return amount * 15 / 1000;
    }
}

public class AccountDemo {
    static void deposit(BankAccount acc, int amount) {
        boolean ok = acc.deposit(amount);
        System.out.println("Deposit " + amount + ": " + (ok ? "done" : "refused")
                + " | balance " + acc.getBalance());
    }

    static void withdraw(BankAccount acc, int amount) {
        boolean ok = acc.withdraw(amount);
        System.out.println("Withdraw " + amount + ": " + (ok ? "done" : "refused")
                + " | balance " + acc.getBalance());
    }

    public static void main(String[] args) {
        BankAccount acc = new BankAccount("Rahim");
        System.out.println("Account of " + acc.getOwner());
        deposit(acc, 10000);
        withdraw(acc, 500);
        withdraw(acc, 4000);
        withdraw(acc, 5400);
        deposit(acc, -200);
        withdraw(acc, 2000);
    }
}
```

**Output:**

```text
Account of Rahim
Deposit 10000: done | balance 10000
Withdraw 500: done | balance 9500
Withdraw 4000: done | balance 5440
Withdraw 5400: refused | balance 5440
Deposit -200: refused | balance 5440
Withdraw 2000: done | balance 3410
```

**Why it works:** `main` never touches `balance` and never computes a fee. It sends the
messages `deposit` and `withdraw` and reads the answer. The withdrawal of 4000 cost 4060
(fee 60). The withdrawal of 5400 would cost 5481 (fee 81), more than the balance of
5440, so it is refused and the balance is untouched, even though 5400 alone would have
fit. The last withdrawal of 2000 cost 2030. `main` never needed to know any of these
fees. If the fee rule changes, only `feeFor` is edited: that is the practical benefit of
abstraction.

### Example 4: An Immutable Money Class

**Problem:** A canteen app needs a safe money type. Amounts are stored as whole paisa
(1 Tk = 100 paisa) to avoid rounding errors with `double`. A `Money` object must never
change after creation; adding, multiplying or applying a discount returns a new `Money`.
Show also that ignoring the result of a "change" method changes nothing, exactly as with
`String`.

```java
class Money {
    private final long paisa;

    Money(long paisa) {
        this.paisa = paisa;
    }

    public long getPaisa() {
        return paisa;
    }

    public Money plus(Money other) {
        return new Money(paisa + other.paisa);
    }

    public Money times(int quantity) {
        return new Money(paisa * quantity);
    }

    public Money percentOff(int percent) {
        return new Money(paisa * (100 - percent) / 100);
    }

    public boolean isMoreThan(Money other) {
        return paisa > other.paisa;
    }

    public String toString() {
        return String.format("Tk %d.%02d", paisa / 100, paisa % 100);
    }
}

public class CanteenBill {
    public static void main(String[] args) {
        Money tea = new Money(1500);
        Money samosa = new Money(1250);
        System.out.println("Tea: " + tea + ", samosa: " + samosa);

        Money bill = tea.times(2).plus(samosa.times(3));
        System.out.println("2 tea + 3 samosa = " + bill);

        Money studentPrice = bill.percentOff(10);
        System.out.println("With 10% student discount: " + studentPrice);
        System.out.println("Original bill unchanged: " + bill);

        tea.times(10);
        System.out.println("After tea.times(10) without saving: " + tea);

        Money budget = new Money(6000);
        System.out.println("Bill more than budget? " + bill.isMoreThan(budget));
        System.out.println("Discounted more than budget? "
                + studentPrice.isMoreThan(budget));

        String name = "rahim";
        name.toUpperCase();
        System.out.println("String not saved: " + name);
        name = name.toUpperCase();
        System.out.println("String saved: " + name);
    }
}
```

**Output:**

```text
Tea: Tk 15.00, samosa: Tk 12.50
2 tea + 3 samosa = Tk 67.50
With 10% student discount: Tk 60.75
Original bill unchanged: Tk 67.50
After tea.times(10) without saving: Tk 15.00
Bill more than budget? true
Discounted more than budget? true
String not saved: rahim
String saved: RAHIM
```

**Why it works:** The only field is `private final`, so after the constructor nothing
can change it. Every "change" method builds and returns a new `Money`, so `bill` keeps
its value after `percentOff` creates `studentPrice`. Inside `plus`, the code reads
`other.paisa` even though it is private: `private` is checked per class, and both
objects are `Money`. `toString()` is declared `public` because it replaces a public
method that every object already has (Chapter 09 explains this). The same object can be
shared safely anywhere, because no one can modify it.

### Example 5: A Small Public Interface: Campus Shuttle Pass

**Problem:** A campus shuttle pass belongs to one student. It can be recharged and used
for rides. Rules (hypothetical): the balance must stay between 0 and 1000 Tk, a ride
costs 30 Tk, and every 5th ride is free. The program reads the holder's name, a number
of commands, and the commands `RECHARGE <amount>`, `RIDE` and `STATUS`.

Design:

- Public interface: `recharge(int)`, `ride()`, `getBalance()`, `getRides()`,
  `getHolder()`. Nothing else.
- Hidden: the fare amount, the free-ride rule (`private fareForNextRide()`), and the
  limits. Callers cannot change them, and do not need to know them.
- `rides` has a getter but no setter: it grows only inside `ride()`.

```java
import java.util.Scanner;

class ShuttlePass {
    private final String holder;
    private final int maxBalance = 1000;
    private final int fare = 30;
    private int balance;
    private int rides;

    ShuttlePass(String holder) {
        this.holder = holder;
    }

    public boolean recharge(int amount) {
        if (amount <= 0 || balance + amount > maxBalance) {
            return false;
        }
        balance = balance + amount;
        return true;
    }

    public boolean ride() {
        int cost = fareForNextRide();
        if (cost > balance) {
            return false;
        }
        balance = balance - cost;
        rides++;
        return true;
    }

    public String getHolder() {
        return holder;
    }

    public int getBalance() {
        return balance;
    }

    public int getRides() {
        return rides;
    }

    private int fareForNextRide() {
        if ((rides + 1) % 5 == 0) {
            return 0;
        }
        return fare;
    }
}

public class ShuttleDemo {
    public static void main(String[] args) {
        Scanner in = new Scanner(System.in);
        ShuttlePass pass = new ShuttlePass(in.nextLine());
        int n = in.nextInt();
        for (int i = 0; i < n; i++) {
            String command = in.next();
            if (command.equals("RECHARGE")) {
                int amount = in.nextInt();
                boolean ok = pass.recharge(amount);
                System.out.println("Recharge " + amount + ": "
                        + (ok ? "OK" : "REFUSED"));
            } else if (command.equals("RIDE")) {
                boolean ok = pass.ride();
                System.out.println("Ride: " + (ok ? "OK" : "REFUSED")
                        + ", balance " + pass.getBalance());
            } else {
                System.out.println(pass.getHolder() + ": " + pass.getRides()
                        + " rides, balance " + pass.getBalance());
            }
        }
    }
}
```

**Input:**

```text
Farhana Akter
10
RECHARGE 100
RIDE
RIDE
RIDE
RIDE
RECHARGE 1200
RECHARGE 950
RIDE
RIDE
STATUS
```

**Output:**

```text
Recharge 100: OK
Ride: OK, balance 70
Ride: OK, balance 40
Ride: OK, balance 10
Ride: REFUSED, balance 10
Recharge 1200: REFUSED
Recharge 950: OK
Ride: OK, balance 930
Ride: OK, balance 930
Farhana Akter: 5 rides, balance 930
```

**Why it works:** `main` only reads commands and calls the five public methods. All
rules are inside `ShuttlePass`. The ride after the third one is refused because 10 Tk is
less than the fare, and it does not count as a ride. Recharging 1200 is refused because
the balance would pass 1000; recharging 950 is accepted (10 + 950 = 960). The next ride
is the 4th successful one and costs 30; the one after it is the 5th and costs nothing, so
the balance stays 930. `main` never saw the fare or the free-ride rule, and because
`rides` has no setter, no caller can "cheat" its way to a free ride.

## Common Mistakes

- **A public setter for every field.** `setBalance(int)` with no checks is the same as a
  public field. Offer action methods (`deposit`, `withdraw`) and only the setters that
  are really needed, each with validation.
- **Forgetting `this` in a setter.** `name = name;` assigns the parameter to itself and
  leaves the field unchanged. Write `this.name = name;`.
- **Storing an invalid value and "fixing it later".** Check first, store second. A
  rejected value must leave the old value in place.
- **Ignoring the result of an immutable "change".** `price.percentOff(10);` and
  `name.toUpperCase();` create new objects and throw them away. Assign the result.
- **Thinking `final` makes an object immutable.** A `final` reference cannot be pointed
  at another object, but the object it points to can still change if its class allows.
- **Thinking `private` means "secret from people".** It is a compiler rule that stops
  other code from depending on and breaking your internals; it is not encryption.
- **Printing inside the class for every error.** It ties the class to the console.
  Return `boolean` (or, from Chapter 11, throw an exception) and let the caller report.
- **Making helper methods public.** Every public method is a promise. If callers do not
  need it, make it `private`.

## Summary

- Encapsulation bundles data with the methods that work on it and protects the object's
  invariants by allowing changes only through checked methods.
- An invariant is a rule that must always hold, such as `balance >= 0`; write the
  invariants down before you write the class.
- `private` hides fields from every other class; getters expose values, and setters (only
  where a change is legal) validate before storing.
- Without exceptions, reject invalid values by keeping the old value and returning
  `false`; exceptions come in Chapter 11.
- Abstraction exposes *what* an object does (its public interface) and hides *how*
  (private fields, private helpers, algorithms), so the implementation can change freely.
- Encapsulation hides the data; abstraction hides the complexity. A good class uses both.
- Access levels: `private` (class), package-private (package), `protected` (package +
  subclasses), `public` (everyone).
- `final` fields are assigned exactly once; immutable classes use only `private final`
  fields and return new objects instead of changing themselves, like `String`.
- Public fields let any line in the program corrupt an object; encapsulated classes keep
  every rule in one place.
