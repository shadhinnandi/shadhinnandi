# Chapter 09: Inheritance

Many classes in a real program are related. A `Student` and a `Teacher` are both people
with a name and an age; a `Bus` and a `Car` are both vehicles with a registration number.
Inheritance lets you write the shared part once, in a general class, and build more
specific classes on top of it. This chapter shows how Java inheritance works, what it
gives you, and when you should not use it.

**In this chapter you will learn:**

- why inheritance exists and what the "is-a" relationship means
- how to write a subclass with `extends`, and the words superclass and subclass
- what a subclass inherits and what it does not (private fields, constructors)
- how `super(...)` and `super.method()` work, and the order in which constructors run
- single, multilevel and hierarchical inheritance
- why Java does not let a class extend two classes (the diamond problem), and how
  interfaces give multiple inheritance of *type*
- method overriding with `@Override`, the `protected` modifier, `final` methods and
  `final` classes
- the `Object` class at the top of every hierarchy: `toString`, `equals`, `hashCode`
- "is-a" versus "has-a" (composition), and when NOT to inherit

## 1. Concept Explanation

### Why inheritance?

Imagine you write a `Student` class and a `Teacher` class for a university system.
Both need a name, an age, an `introduce()` method and getters. Without inheritance you
copy the same fields and methods into both classes.

```text
 +------------------+        +------------------+
 | Student          |        | Teacher          |
 |------------------|        |------------------|
 | name   (copy)    |        | name   (copy)    |
 | age    (copy)    |        | age    (copy)    |
 | introduce() (cp) |        | introduce() (cp) |
 | studentId        |        | designation      |
 | cgpa             |        | salary           |
 +------------------+        +------------------+
```

Copying code causes real problems. If you later fix a bug in `introduce()`, you must
fix it in every copy, and sooner or later one copy is forgotten.

With inheritance you move the shared part into a general class `Person`. `Student` and
`Teacher` then say "I am a `Person`, plus these extra things".

```text
                 +------------------+
                 | Person           |
                 |------------------|
                 | name, age        |
                 | introduce()      |
                 +------------------+
                    ^            ^
                    |            |
        +-----------+--+      +--+-----------+
        | Student      |      | Teacher      |
        |--------------|      |--------------|
        | studentId    |      | designation  |
        | cgpa         |      | salary       |
        +--------------+      +--------------+

   Arrow points from the subclass to its superclass.
```

Inheritance gives you three things:

- **Reuse:** shared fields and methods are written once.
- **A clear model:** the code says out loud that a student *is a* person.
- **A common type:** later (Chapter 10) you can treat students and teachers the same
  way wherever a `Person` is expected.

### The "is-a" relationship

Inheritance is correct only when the sentence "every X *is a* Y" is true and stays true.

| Sentence | True? | Inheritance? |
|---|---|---|
| A Student is a Person | yes | `Student extends Person` |
| A Bus is a Vehicle | yes | `Bus extends Vehicle` |
| A SavingsAccount is an Account | yes | `SavingsAccount extends Account` |
| A Car is an Engine | no (a car *has* an engine) | no, use a field |
| A Library is a Book | no (a library *has* books) | no, use a list field |

Keep this test in mind. Section "is-a vs has-a" below explains the second half.

### Superclass and subclass

The general class is the **superclass**; the specific class is the **subclass**. You
will meet other names for the same idea in books and online.

| This course says | Other common names |
|---|---|
| superclass | parent class, base class |
| subclass | child class, derived class |
| "B extends A" | "B inherits from A", "B is derived from A" |

A subclass object contains everything a superclass object contains, plus its own extra
fields. Think of a `Student` object on the heap as a `Person` part with a `Student`
part added on.

```text
  Student object on the heap
 +---------------------------+
 | Person part               |
 |   name = "Nusrat"         |
 |   age  = 20               |
 |---------------------------|
 | Student part              |
 |   studentId = "011-221"   |
 |   cgpa      = 3.75        |
 +---------------------------+
```

### What is inherited and what is not

A subclass gets the superclass members, but access rules still apply.

| Member of the superclass | What the subclass gets |
|---|---|
| `public` fields and methods | inherited, usable directly |
| `protected` fields and methods | inherited, usable directly (even in another package) |
| package-private (no modifier) | inherited, usable only if the subclass is in the same package |
| `private` fields | they **exist** inside every subclass object, but subclass code cannot name them; use the superclass's getters or methods |
| `private` methods | not inherited: the subclass cannot call or override them |
| constructors | never inherited; a subclass constructor calls one with `super(...)` |
| `static` members | belong to the class, not to objects; a subclass can use them by name |

The private-field rule surprises many students. A `Student` object really has a `name`
inside it, because the `Person` part is there. But code written inside `Student` cannot
say `name`; it must call `getName()`. This keeps the `Person` class in control of its own
data, which is exactly what encapsulation (Chapter 05) promised.

### The `super` keyword

Inside a subclass, `super` refers to the superclass part of the current object. It has
two uses:

- `super(arguments)` as the **first statement of a constructor**: run a superclass
  constructor so the superclass part is set up.
- `super.methodName(arguments)` anywhere in an instance method: call the superclass's
  version of a method, usually from inside an overriding method that wants to extend
  that version rather than replace it.

`this` and `super` look similar but mean different things.

| Expression | Meaning |
|---|---|
| `this.name` | a field of the current object (found from the current class upward) |
| `this(...)` | call another constructor of the same class |
| `super(...)` | call a constructor of the superclass |
| `super.describe()` | call the superclass's version of `describe()` |

### Constructor call order

Every constructor must start by calling another constructor: either `this(...)` in the
same class or `super(...)` in the superclass. If you write neither, the compiler
inserts `super();` for you, which calls the superclass's no-argument constructor.

This means building an object always starts at the top of the hierarchy. `Object` is the
superclass of every class, so it is always the first constructor to finish.

```text
  new ElectricCar(...)
        |
        v  calls super(...)          bodies finish in this order:
  ElectricCar(...) ----+
        |              |                 1. Object()
        v  super(...)  |                 2. Vehicle(...)  body
  Car(...) ------------+                 3. Car(...)      body
        |              |                 4. ElectricCar(...) body
        v  super(...)  |
  Vehicle(...) --------+
        |
        v  super()  (inserted by the compiler)
  Object()
```

The calls go **up** the hierarchy, and the constructor bodies run **down** from the top.
This order is sensible: a subclass constructor may use inherited fields, so the
superclass part must be ready first. Example 2 traces it with printed messages.

### Types of inheritance in Java

**Single inheritance:** one subclass extends one superclass.

```text
   +---------+
   | Vehicle |
   +---------+
        ^
        |
   +---------+
   |   Bus   |
   +---------+
```

**Multilevel inheritance:** a chain, where a subclass is itself extended.

```text
   +---------+       +---------+       +-------------+
   | Vehicle | <---- |   Car   | <---- | ElectricCar |
   +---------+       +---------+       +-------------+
   ElectricCar is a Car, and a Car is a Vehicle,
   so ElectricCar is also a Vehicle.
```

**Hierarchical inheritance:** several subclasses extend the same superclass.

```text
                  +----------+
                  | Employee |
                  +----------+
                  ^    ^     ^
                  |    |     |
       +---------+ +--------+ +--------+
       | Manager | | Intern | | Driver |
       +---------+ +--------+ +--------+
```

You can combine these: a hierarchy can be hierarchical at one level and multilevel
below it. What you cannot do with classes is the next shape.

### Multiple inheritance and the diamond problem

**Multiple inheritance** would mean one class extending two classes at once. Java does
not allow this for classes: `class C extends A, B` is a compile error. The reason is
the **diamond problem**.

```text
                 +-------------------+
                 | Device            |
                 | powerOn()         |
                 +-------------------+
                   ^               ^
                   |               |
        +--------------+     +--------------+
        | Camera       |     | MusicPlayer  |
        | powerOn()    |     | powerOn()    |
        | (overridden) |     | (overridden) |
        +--------------+     +--------------+
                   ^               ^
                   |               |
                 +-------------------+
                 | SmartPhone        |
                 | powerOn() = ???   |
                 +-------------------+

   NOT allowed in Java: a class cannot extend two classes.
```

If `SmartPhone` extended both `Camera` and `MusicPlayer`, which `powerOn()` should
`phone.powerOn()` run? And would a `SmartPhone` object contain one `Device` part or two
copies of it? Java's designers avoided these questions completely: **a class extends
exactly one class** (if you write no `extends`, that class is `Object`).

> **Coming from C++?** C++ allows a class to have several base classes and adds extra
> rules (such as virtual base classes) to deal with the diamond. Java keeps class
> inheritance single and uses interfaces instead.

### Multiple inheritance of type: interfaces

A smartphone really is a camera and a music player. Java expresses this with
**interfaces**. An interface is a named list of methods that a class promises to
provide. It describes *what* an object can do, not *how*, and it has no instance
fields, so there is no state that could be inherited twice.

```text
                 +-----------+
                 |  Device   |   class: fields + code
                 +-----------+
                       ^
                       | extends (exactly one class)
                 +------------+
                 | SmartPhone |
                 +------------+
                  :          :
       implements :          : implements (any number)
                  v          v
          <<interface>>    <<interface>>
          +---------+      +-------------+
          | Camera  |      | MusicPlayer |
          +---------+      +-------------+
```

```java
class SmartPhone extends Device implements Camera, MusicPlayer {
    // must provide the method bodies listed in Camera and MusicPlayer
}
```

A `SmartPhone` object now has three types at once: it *is a* `Device`, *is a* `Camera`
and *is a* `MusicPlayer`. This is called **multiple inheritance of type**: Java allows a
class to implement many interfaces, while it inherits fields and code from only one
class. Example 5 builds this program. Chapter 10 covers interfaces fully (default
methods, abstract classes and how they compare).

### Method overriding (introduction)

A subclass inherits methods, but sometimes the inherited behaviour is not right for it.
**Overriding** means the subclass writes a method with the same name and the same
parameter list as an inherited method, giving its own version.

```java
class Employee {
    public int monthlyPay() {
        return basicSalary;
    }
}

class Manager extends Employee {
    @Override
    public int monthlyPay() {
        return super.monthlyPay() + teamAllowance;   // extends the old version
    }
}
```

Rules for a correct override:

- same method name and same parameter types (otherwise it is a new, overloaded method)
- same return type (or a subclass of it)
- access may stay the same or become wider (`protected` to `public`), never narrower
- `private`, `static` and `final` methods cannot be overridden

Always put **`@Override`** on an overriding method. It is an annotation: a note to the
compiler that says "this method must override something". If you misspell the name or
get a parameter type wrong, the compiler reports an error instead of silently creating a
new method.

| | Overloading (Chapter 03) | Overriding (this chapter) |
|---|---|---|
| Where | usually in the same class | in a subclass |
| Name | same | same |
| Parameters | must differ | must be the same |
| Purpose | same idea, different inputs | change inherited behaviour |
| Which version runs | chosen by the compiler from argument types | chosen by the object's actual class when the program runs |

When an overridden method is called on an object, Java runs the version of the
object's **actual class**. This is true even when the call is written inside an
inherited superclass method. Example 3 relies on it, and Chapter 10 explains the
mechanism (dynamic method dispatch) in detail.

### A first look: a superclass variable can hold a subclass object

Because every `Student` is a `Person`, Java lets a `Person` variable refer to a
`Student` object.

```java
Person p = new Student("Rafi", 21, "011-305", 3.40);
p.introduce();        // allowed: every Person has introduce()
```

You will see this in a few practice problems where an `ArrayList<Employee>` stores
managers and interns together. Chapter 10 builds on this idea (upcasting, downcasting
and polymorphism); here you only need to know that it is allowed.

### `protected` in full

Chapter 05 listed `protected` without fully explaining it. Here is the complete table.

| Modifier | Same class | Same package | Subclass in another package | Everyone else |
|---|---|---|---|---|
| `private` | yes | no | no | no |
| (none) package-private | yes | yes | no | no |
| `protected` | yes | yes | yes | no |
| `public` | yes | yes | yes | yes |

So `protected` means "visible in my package, and also to my subclasses wherever they
are". All programs in this course are single files in one package, so in our examples
`protected` behaves like package-private; the difference matters in larger projects
with several packages.

Use `protected` with care. A `protected` field can be changed by every subclass,
which weakens encapsulation: the superclass can no longer guarantee its rules. A good
default is:

- fields `private`
- `public` methods for everyone
- `protected` methods (or occasionally fields) for things that only subclasses need

### `final` methods and `final` classes

You met `final` variables in Chapter 01 and `final` fields in Chapter 05. On methods
and classes, `final` means "no further changes by inheritance".

| Written as | Meaning |
|---|---|
| `final int MAX = 5;` | the variable cannot be reassigned |
| `public final String payslip()` | no subclass may override this method |
| `final class Book` | no class may extend `Book` |

Why forbid something? A `final` method protects behaviour that must stay the same for
all subclasses, such as a payslip format or a security check. A `final` class protects
a design that would break if someone changed parts of it. Java's own `String`, `Math`
and `Integer` classes are `final`; that is one reason a `String` can be trusted to be
immutable.

```java nocompile
final class Book {
}

class EBook extends Book {      // error: cannot inherit from final Book
}
```

### The `Object` class

Every class in Java has exactly one superclass. If you write no `extends`, the compiler
uses `java.lang.Object`. So `Object` is at the top of every hierarchy, and every object
has `Object`'s methods.

```text
                        +--------+
                        | Object |   toString(), equals(), hashCode(), ...
                        +--------+
                       ^    ^     ^
                       |    |     |
               +--------+ +------+ +---------+
               | Person | | Book | | Vehicle |
               +--------+ +------+ +---------+
                   ^
             +-----------+
             | Student   |
             +-----------+
```

Three `Object` methods are worth overriding in your own classes.

- **`toString()`** returns a text form of the object. `System.out.println(obj)` and
  string concatenation `"x" + obj` call it automatically. The version from `Object`
  prints the class name, `@` and a hexadecimal number, which is not useful to a reader,
  so override it. (In Chapter 04 you wrote `toString()` without knowing it was an
  override; now you add `@Override`.)
- **`equals(Object other)`** decides whether two objects are "equal in meaning". The
  version from `Object` only checks `this == other` (same object). Override it when two
  different objects with the same key data (for example, the same ISBN) should count as
  equal. `ArrayList.contains` and `indexOf` use `equals`.
- **`hashCode()`** returns an `int` used by hash-based collections such as `HashSet`
  and `HashMap`. The rule: **if two objects are equal by `equals`, they must have the
  same `hashCode`**. So whenever you override `equals`, override `hashCode` too, using
  the same fields. Many IDEs (and `javac -Xlint:overrides`) warn if you forget, but
  the plain compiler does not.

Note the parameter type: `equals` takes an `Object`, not a `Book`. Writing
`public boolean equals(Book other)` creates an overload, not an override, and
`ArrayList.contains` will never call it. `@Override` catches this mistake.

### "is-a" vs "has-a": when NOT to inherit

Inheritance is only one way to reuse code. The other is **composition**: one object
holds a reference to another object in a field, and calls its methods. This is the
**has-a** relationship.

```text
   is-a (inheritance)                has-a (composition)

   +---------+                       +---------+      +--------+
   | Vehicle |                       | Shuttle |----->| Engine |
   +---------+                       |         |      +--------+
        ^                            |         |      +--------+
        |                            |         |----->| Driver |
   +---------+                       +---------+      +--------+
   | Shuttle |
   +---------+               A Shuttle is a Vehicle, and it has an
                             Engine and a Driver.
```

Use **inheritance** when:

- "every X is a Y" is true and stays true for the object's whole life
- X should support every public method of Y without surprises
- you want to treat all kinds of Y the same way (Chapter 10)

Use **composition** when:

- the relationship is "has a" or "uses a" (a `Car` has an `Engine`)
- you only want to reuse *some* of another class's code
- the role can change over time (a student who becomes a teaching assistant for one
  trimester is still the same person; model the role as a field, not as a subclass)

A classic bad design is a `BookStack extends ArrayList<String>`. It looks like free
reuse, but the subclass now inherits `add(index, item)`, `remove(index)` and many other
methods, so any caller can insert a book in the middle and break the "last in, first
out" rule. A `BookStack` that **has** a private `ArrayList<String>` and offers only
`push`, `pop` and `peek` keeps its rule. Java's own old `Stack` class extends `Vector`
and has exactly this weakness; modern code prefers `ArrayDeque`.

**Should this be a subclass?** Ask three questions:

1. Is "every X is a Y" true, permanently?
2. Does every public method of Y make sense for an X?
3. Would X ever need to be two different things at once (use interfaces then)?

If any answer is "no", reach for composition.

## 2. Syntax

### Declaring a subclass with `extends`

```java
class Person {
    private String name;

    Person(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
}

class Student extends Person {   // Student inherits from Person
    private double cgpa;          // extra field only students have

    Student(String name, double cgpa) {
        super(name);              // set up the Person part first
        this.cgpa = cgpa;
    }
}
```

`extends` names exactly one superclass. The subclass lists only what is *new*; it does
not repeat `name` or `getName()`.

### Calling a superclass constructor with `super(...)`

```java
Student(String name, double cgpa) {
    super(name);       // must be the very first statement
    this.cgpa = cgpa;
}
```

If the superclass has no no-argument constructor, every subclass constructor **must**
call `super(...)` with arguments. Otherwise the compiler inserts `super();`, finds no
matching constructor and stops.

```java nocompile
class Person {
    private String name;

    Person(String name) {
        this.name = name;
    }
}

class Student extends Person {
    Student() {
        // compiler inserts super(); here, but Person() does not exist
        // error: constructor Person in class Person cannot be applied to given types
    }
}
```

`super(...)` and `this(...)` both must be the first statement, so a constructor uses
one of them, never both. A constructor that calls `this(...)` still reaches `super(...)`
through the other constructor.

### Overriding and calling the superclass version

```java
class Account {
    public String describe() {
        return "Account " + number;
    }
}

class SavingsAccount extends Account {
    @Override
    public String describe() {
        return super.describe() + " (savings, 4% interest)";
    }
}
```

Without the `super.` prefix, `describe()` inside `SavingsAccount` would call itself
forever. `super.describe()` means "the version I inherited".

### `protected` members

```java
class Vehicle {
    protected int speedKmh;            // subclasses may read and change it

    protected void log(String event) { // helper meant for subclasses
        System.out.println("[" + event + "]");
    }
}
```

### `final` methods and classes

```java
class Employee {
    public final String payslip() {    // subclasses cannot override this
        return name + ": Tk " + monthlyPay();
    }
}

final class Receipt {                  // no class can extend Receipt
}
```

### Interfaces and `implements`

```java
interface Camera {
    void takePhoto(String subject);    // no body: implementing classes provide it
}

interface MusicPlayer {
    void play(String song);
}

class SmartPhone extends Device implements Camera, MusicPlayer {
    @Override
    public void takePhoto(String subject) {
        System.out.println("Photo of " + subject);
    }

    @Override
    public void play(String song) {
        System.out.println("Playing " + song);
    }
}
```

Interface methods are automatically `public`, so the implementing methods must be
`public` too. Order matters in the header: `extends` (one class) comes first, then
`implements` (one or more interfaces, separated by commas).

### Overriding `toString`, `equals` and `hashCode`

```java
@Override
public String toString() {
    return title + " [" + isbn + "]";
}

@Override
public boolean equals(Object other) {
    if (this == other) {
        return true;                          // same object
    }
    if (other == null || getClass() != other.getClass()) {
        return false;                         // not a Book at all
    }
    Book that = (Book) other;                 // now safe to treat it as a Book
    return isbn.equals(that.isbn);            // equal if the ISBNs match
}

@Override
public int hashCode() {
    return isbn.hashCode();                   // same field as equals
}
```

`getClass()` (another `Object` method) returns the object's actual class, and
`(Book) other` is a cast from `Object` to `Book`. Chapter 10 explains casts between
class types; for now, use this pattern as written. The private field `that.isbn` is
accessible because the code is inside the `Book` class.

## 3. Worked Examples

In a real project each public class lives in its own file; here we keep each program in
one file so you can compile it with one command.

### Example 1: University Members

**Problem:** A university system needs students and teachers. Both have a name and an
age and can introduce themselves. Students also have an ID and a CGPA; teachers have a
designation. Read one student's details from input, create the objects, and show which
methods each object can use.

Put the shared data in `Person` and let `Student` and `Teacher` extend it. The fields
of `Person` are `private`, so the subclasses use the inherited getters.

```java
import java.util.Scanner;

class Person {
    private String name;
    private int age;

    Person(String name, int age) {
        this.name = name;
        this.age = age;
    }

    public String getName() {
        return name;
    }

    public int getAge() {
        return age;
    }

    public void introduce() {
        System.out.println("Hi, I am " + name + ", age " + age + ".");
    }
}

class Student extends Person {
    private String studentId;
    private double cgpa;

    Student(String name, int age, String studentId, double cgpa) {
        super(name, age);
        this.studentId = studentId;
        this.cgpa = cgpa;
    }

    public void showRecord() {
        // name is private in Person, so we call the inherited getter
        System.out.printf("%s (%s) CGPA %.2f%n", getName(), studentId, cgpa);
    }
}

class Teacher extends Person {
    private String designation;

    Teacher(String name, int age, String designation) {
        super(name, age);
        this.designation = designation;
    }

    public void teach(String course) {
        System.out.println(designation + " " + getName() + " is teaching " + course + ".");
    }
}

public class UniversityMembers {
    public static void main(String[] args) {
        Scanner in = new Scanner(System.in);
        String name = in.nextLine();
        int age = in.nextInt();
        String id = in.next();
        double cgpa = in.nextDouble();

        Student student = new Student(name, age, id, cgpa);
        Teacher teacher = new Teacher("Arif Hossain", 41, "Lecturer");

        student.introduce();       // inherited from Person
        student.showRecord();      // defined in Student
        teacher.introduce();       // inherited from Person
        teacher.teach("OOP");      // defined in Teacher
        System.out.println("Ages: " + student.getAge() + " and " + teacher.getAge());
    }
}
```

**Input:**

```text
Nusrat Jahan
20
011-221-045
3.756
```

**Output:**

```text
Hi, I am Nusrat Jahan, age 20.
Nusrat Jahan (011-221-045) CGPA 3.76
Hi, I am Arif Hossain, age 41.
Lecturer Arif Hossain is teaching OOP.
Ages: 20 and 41
```

**Why it works:** `introduce()` and `getAge()` are written once in `Person` and both
subclasses inherit them. Each subclass constructor first calls `super(name, age)`, so
the `Person` part of the object is filled in before the subclass sets its own fields.
`showRecord()` needs the name, but `name` is `private` in `Person`; the object does
contain it, so the inherited public `getName()` can return it.

### Example 2: Tracing Constructor Call Order

**Problem:** Show, with printed messages, the order in which constructors run when you
create an object in a three-level hierarchy `Vehicle -> Car -> ElectricCar`.

Each constructor prints a line just after its `super(...)` call. A message printed
*before* `super(...)` is impossible, because `super(...)` must come first; so we also
print a message in `main` before each `new`.

```java
class Vehicle {
    protected String regNo;

    Vehicle(String regNo) {
        // super(); is inserted here: Object's constructor runs first
        this.regNo = regNo;
        System.out.println("  Vehicle body: regNo = " + regNo);
    }
}

class Car extends Vehicle {
    protected int seats;

    Car(String regNo, int seats) {
        super(regNo);
        this.seats = seats;
        System.out.println("  Car body: seats = " + seats);
    }
}

class ElectricCar extends Car {
    private int batteryKwh;

    ElectricCar(String regNo, int seats, int batteryKwh) {
        super(regNo, seats);
        this.batteryKwh = batteryKwh;
        System.out.println("  ElectricCar body: battery = " + batteryKwh + " kWh");
    }

    public void describe() {
        // regNo and seats are protected, so the subclass may use them directly
        System.out.println(regNo + ", " + seats + " seats, " + batteryKwh + " kWh");
    }
}

public class ConstructorOrder {
    public static void main(String[] args) {
        System.out.println("new ElectricCar(...):");
        ElectricCar ev = new ElectricCar("DHAKA-GA-1234", 4, 60);

        System.out.println("new Car(...):");
        Car car = new Car("CTG-KA-5678", 7);

        System.out.println("Done.");
        ev.describe();
        System.out.println(car.regNo + " has " + car.seats + " seats");
    }
}
```

**Output:**

```text
new ElectricCar(...):
  Vehicle body: regNo = DHAKA-GA-1234
  Car body: seats = 4
  ElectricCar body: battery = 60 kWh
new Car(...):
  Vehicle body: regNo = CTG-KA-5678
  Car body: seats = 7
Done.
DHAKA-GA-1234, 4 seats, 60 kWh
CTG-KA-5678 has 7 seats
```

Here is the trace for `new ElectricCar("DHAKA-GA-1234", 4, 60)`.

| Step | What happens | Printed |
|---|---|---|
| 1 | `ElectricCar(...)` starts, first statement is `super(regNo, seats)` | |
| 2 | `Car(...)` starts, first statement is `super(regNo)` | |
| 3 | `Vehicle(...)` starts, hidden `super()` runs `Object()` | |
| 4 | `Vehicle` body sets `regNo` | `Vehicle body ...` |
| 5 | back in `Car`, body sets `seats` | `Car body ...` |
| 6 | back in `ElectricCar`, body sets `batteryKwh` | `ElectricCar body ...` |

**Why it works:** each constructor's first action is to call the constructor above it,
so the calls climb to `Object` and the bodies then finish from the top down. Creating a
`Car` runs only two of our constructors, because a `Car` has no `ElectricCar` part.
`main` can read `car.regNo` because `protected` members are visible in the same package.

### Example 3: Payroll with Overriding

**Problem:** A company pays three kinds of staff. A regular employee gets a basic
salary. A manager gets the basic salary plus Tk 500 for each team member. An intern
gets a fixed stipend and no basic salary. Every payslip must have the same format.
Print one payslip for each.

This is hierarchical inheritance: `Manager` and `Intern` both extend `Employee`.
Each overrides `monthlyPay()`. The payslip format is written once, in a `final`
method of `Employee`, so no subclass can change it.

```java
class Employee {
    private String name;
    private int basicSalary;

    Employee(String name, int basicSalary) {
        this.name = name;
        this.basicSalary = basicSalary;
    }

    public String getName() {
        return name;
    }

    public int monthlyPay() {
        return basicSalary;
    }

    public String role() {
        return "Employee";
    }

    public final String payslip() {
        return String.format("%-8s %-10s Tk %,7d", role(), name, monthlyPay());
    }
}

class Manager extends Employee {
    private int teamSize;

    Manager(String name, int basicSalary, int teamSize) {
        super(name, basicSalary);
        this.teamSize = teamSize;
    }

    @Override
    public int monthlyPay() {
        return super.monthlyPay() + 500 * teamSize;   // basic + allowance
    }

    @Override
    public String role() {
        return "Manager";
    }
}

class Intern extends Employee {
    private int stipend;

    Intern(String name, int stipend) {
        super(name, 0);                // interns have no basic salary
        this.stipend = stipend;
    }

    @Override
    public int monthlyPay() {
        return stipend;                // replaces the inherited version
    }

    @Override
    public String role() {
        return "Intern";
    }
}

public class PayrollDemo {
    public static void main(String[] args) {
        Employee karim = new Employee("Karim", 38000);
        Manager sadia = new Manager("Sadia", 52000, 6);
        Intern fahim = new Intern("Fahim", 12000);

        System.out.println(karim.payslip());
        System.out.println(sadia.payslip());
        System.out.println(fahim.payslip());

        int total = karim.monthlyPay() + sadia.monthlyPay() + fahim.monthlyPay();
        System.out.printf("Total payroll: Tk %,d%n", total);
    }
}
```

**Output:**

```text
Employee Karim      Tk  38,000
Manager  Sadia      Tk  55,000
Intern   Fahim      Tk  12,000
Total payroll: Tk 105,000
```

**Why it works:** `payslip()` is defined only in `Employee`, yet for `sadia` it prints
`Manager` and Tk 55,000. Inside `payslip()`, the calls `role()` and `monthlyPay()` run
the version belonging to the object's actual class, so the manager's overrides are
used. `Manager.monthlyPay()` reuses the inherited calculation with
`super.monthlyPay()` and adds the allowance; `Intern.monthlyPay()` replaces it
completely. Because `payslip()` is `final`, all three payslips are guaranteed to share
one format. (`%,7d` prints the number with thousands separators, 7 characters wide.)

### Example 4: Books, `toString` and `equals`

**Problem:** A library keeps a list of books. Two `Book` objects with the same ISBN are
the same book, even if they were created separately (for example, read twice from a
form). Show the difference between `==` and an overridden `equals`, and use it to stop
duplicate entries.

`Book` overrides the three `Object` methods. It is also a `final` class: a book's
equality rule should not be changed by a subclass.

```java
import java.util.ArrayList;

final class Book {
    private final String isbn;
    private final String title;

    Book(String isbn, String title) {
        this.isbn = isbn;
        this.title = title;
    }

    @Override
    public String toString() {
        return title + " [" + isbn + "]";
    }

    @Override
    public boolean equals(Object other) {
        if (this == other) {
            return true;
        }
        if (other == null || getClass() != other.getClass()) {
            return false;
        }
        Book that = (Book) other;
        return isbn.equals(that.isbn);
    }

    @Override
    public int hashCode() {
        return isbn.hashCode();
    }
}

public class LibraryBooks {
    public static void main(String[] args) {
        Book a = new Book("978-0134685991", "Effective Java");
        Book b = new Book("978-0134685991", "Effective Java");
        Book c = new Book("978-0596009205", "Head First Java");

        System.out.println(a);                         // calls toString()
        System.out.println("a == b      : " + (a == b));
        System.out.println("a.equals(b) : " + a.equals(b));
        System.out.println("a.equals(c) : " + a.equals(c));
        System.out.println("same hash   : " + (a.hashCode() == b.hashCode()));

        ArrayList<Book> shelf = new ArrayList<Book>();
        Book[] incoming = {a, c, b};
        for (Book book : incoming) {
            if (shelf.contains(book)) {                // uses equals
                System.out.println("Duplicate skipped: " + book);
            } else {
                shelf.add(book);
                System.out.println("Added: " + book);
            }
        }
        System.out.println("Shelf: " + shelf);
    }
}
```

**Output:**

```text
Effective Java [978-0134685991]
a == b      : false
a.equals(b) : true
a.equals(c) : false
same hash   : true
Added: Effective Java [978-0134685991]
Added: Head First Java [978-0596009205]
Duplicate skipped: Effective Java [978-0134685991]
Shelf: [Effective Java [978-0134685991], Head First Java [978-0596009205]]
```

**Why it works:** `a` and `b` are two different objects, so `==` is `false`. The
overridden `equals` compares ISBNs, so it reports them as equal, and `hashCode` agrees
because it uses the same field. `ArrayList.contains` calls `equals` on each element, so
the second copy is detected. Printing the whole list calls `toString()` on each book.
Without the overrides, `contains` would compare references and the duplicate would get
in.

### Example 5: A SmartPhone with Multiple Types

**Problem:** A phone is a device with a model name and a battery level. It can also
take photos like a camera and play songs like a music player. Java does not allow
`class SmartPhone extends Device, Camera, MusicPlayer`. Model it correctly.

`Device` is a class (it has state: model and battery). `Camera` and `MusicPlayer` are
interfaces (only a promise of methods). `SmartPhone` extends the one class and
implements both interfaces.

```java
interface Camera {
    void takePhoto(String subject);
}

interface MusicPlayer {
    void play(String song);

    void stop();
}

class Device {
    private String model;
    private int battery;

    Device(String model, int battery) {
        this.model = model;
        this.battery = battery;
    }

    public String getModel() {
        return model;
    }

    public int getBattery() {
        return battery;
    }

    protected boolean useBattery(int percent) {
        if (percent > battery) {
            System.out.println(model + ": battery too low");
            return false;
        }
        battery -= percent;
        return true;
    }

    public void powerOn() {
        System.out.println(model + " is on, battery " + battery + "%");
    }
}

class SmartPhone extends Device implements Camera, MusicPlayer {
    private int photoCount;
    private String nowPlaying;

    SmartPhone(String model, int battery) {
        super(model, battery);
        nowPlaying = "nothing";
    }

    @Override
    public void takePhoto(String subject) {
        if (useBattery(2)) {
            photoCount++;
            System.out.println("Photo #" + photoCount + ": " + subject);
        }
    }

    @Override
    public void play(String song) {
        if (useBattery(5)) {
            nowPlaying = song;
            System.out.println("Playing: " + song);
        }
    }

    @Override
    public void stop() {
        System.out.println("Stopped: " + nowPlaying);
        nowPlaying = "nothing";
    }
}

public class SmartPhoneDemo {
    public static void main(String[] args) {
        SmartPhone phone = new SmartPhone("Nova X", 10);
        phone.powerOn();                     // from Device
        phone.takePhoto("Shaheed Minar");    // from Camera
        phone.play("Ami Banglay Gaan Gai");  // from MusicPlayer
        phone.stop();

        // The same object seen through each of its types
        Camera camera = phone;
        MusicPlayer player = phone;
        camera.takePhoto("Campus canteen");
        player.play("Coke Studio mix");

        System.out.println(phone.getModel() + " battery left: " + phone.getBattery() + "%");
    }
}
```

**Output:**

```text
Nova X is on, battery 10%
Photo #1: Shaheed Minar
Playing: Ami Banglay Gaan Gai
Stopped: Ami Banglay Gaan Gai
Photo #2: Campus canteen
Nova X: battery too low
Nova X battery left: 1%
```

**Why it works:** `SmartPhone` inherits fields and code from exactly one class,
`Device`, so there is only one battery and one `powerOn()`. From the two interfaces it
inherits only *types* and the duty to write `takePhoto`, `play` and `stop`. That is why
the same object can be stored in a `Camera` variable and a `MusicPlayer` variable. The
last `play` fails because only 1% battery is left after the second photo, and
`useBattery` refuses.

### Example 6: Composition: A Campus Shuttle

**Problem:** A university runs shuttle buses. A shuttle is a vehicle (registration
number, capacity), it has an engine that can be started and stopped, and it has a
driver. Model this, deciding for each relationship whether it is "is-a" or "has-a".

- "A shuttle is a vehicle" is true: `Shuttle extends Vehicle`.
- "A shuttle is an engine" is false; it *has* an engine: an `Engine` field.
- "A shuttle is a driver" is false, and drivers change between trips: a `Driver` field
  with a method to assign a new driver.

```java
class Engine {
    private int horsePower;
    private boolean running;

    Engine(int horsePower) {
        this.horsePower = horsePower;
    }

    public void start() {
        running = true;
        System.out.println("  Engine (" + horsePower + " hp) started");
    }

    public void stop() {
        running = false;
        System.out.println("  Engine stopped");
    }

    public boolean isRunning() {
        return running;
    }
}

class Driver {
    private String name;

    Driver(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
}

class Vehicle {
    private String regNo;
    private int capacity;

    Vehicle(String regNo, int capacity) {
        this.regNo = regNo;
        this.capacity = capacity;
    }

    public String getRegNo() {
        return regNo;
    }

    public int getCapacity() {
        return capacity;
    }
}

class Shuttle extends Vehicle {             // is-a Vehicle
    private Engine engine;                  // has-an Engine
    private Driver driver;                  // has-a Driver

    Shuttle(String regNo, int capacity, Engine engine, Driver driver) {
        super(regNo, capacity);
        this.engine = engine;
        this.driver = driver;
    }

    public void changeDriver(Driver newDriver) {
        System.out.println("Driver change: " + driver.getName()
                + " -> " + newDriver.getName());
        driver = newDriver;
    }

    public void runTrip(String route, int passengers) {
        if (passengers > getCapacity()) {
            System.out.println("Trip " + route + " refused: " + passengers
                    + " passengers, capacity " + getCapacity());
            return;
        }
        System.out.println(getRegNo() + " on " + route + " with "
                + driver.getName() + ", " + passengers + " passengers");
        engine.start();                     // delegate to the Engine object
        engine.stop();
    }
}

public class CampusShuttle {
    public static void main(String[] args) {
        Shuttle shuttle = new Shuttle("DHAKA-BA-4321", 30,
                new Engine(150), new Driver("Imran"));

        shuttle.runTrip("Campus -> Kuril", 24);
        shuttle.changeDriver(new Driver("Tanvir"));
        shuttle.runTrip("Kuril -> Campus", 35);
        shuttle.runTrip("Kuril -> Campus", 30);
    }
}
```

**Output:**

```text
DHAKA-BA-4321 on Campus -> Kuril with Imran, 24 passengers
  Engine (150 hp) started
  Engine stopped
Driver change: Imran -> Tanvir
Trip Kuril -> Campus refused: 35 passengers, capacity 30
DHAKA-BA-4321 on Kuril -> Campus with Tanvir, 30 passengers
  Engine (150 hp) started
  Engine stopped
```

**Why it works:** `Shuttle` inherits `getRegNo()` and `getCapacity()` because a shuttle
truly is a vehicle. It does not inherit from `Engine`, so callers cannot do strange
things like `shuttle.isRunning()` as if the bus itself were an engine; the shuttle
decides when to call `engine.start()`. This is called **delegation**: the shuttle passes
the work to the object it holds. The driver is a field, so changing drivers is a simple
assignment; with inheritance, a shuttle could never change who drives it.

## Common Mistakes

- **Forgetting `super(...)` when the superclass has no no-argument constructor.** The
  compiler inserts `super();` and reports "constructor Person in class Person cannot be
  applied to given types". Call the right `super(...)` explicitly.
- **Putting `super(...)` after other statements.** It must be the first statement of the
  constructor.
- **Using a private superclass field in the subclass.** `name` has private access in
  `Person`. Use a getter, or a `protected` method if only subclasses need it.
- **Redeclaring an inherited field in the subclass.** Writing `private String name;`
  again in `Student` creates a *second*, separate field that hides the first. Do not
  repeat inherited fields.
- **Overloading when you meant to override.** `public boolean equals(Book b)` or
  `public String tostring()` compile, but override nothing. Always write `@Override`;
  then the compiler tells you.
- **Making an overriding method less visible.** Overriding a `public` method with a
  package-private one is a compile error ("attempting to assign weaker access
  privileges").
- **Calling the method itself instead of the superclass version.** Inside an override,
  `describe()` calls the override again (endless recursion); `super.describe()` calls
  the inherited one.
- **Overriding `equals` without `hashCode`.** Equal objects must have equal hash codes,
  otherwise `HashSet` and `HashMap` misbehave.
- **Trying to extend two classes.** `class C extends A, B` does not compile. Extend one
  class and implement interfaces.
- **Inheriting just to reuse code.** `Car extends Engine` or `BookStack extends
  ArrayList<String>` compile, but they model the world wrongly and expose methods that
  should not exist. Prefer has-a.

## Summary

- Inheritance models an "is-a" relationship: `class Student extends Person` means every
  `Student` is a `Person` with extra fields and methods.
- A subclass inherits public and protected members. Private fields exist in the
  subclass object but are reached only through the superclass's methods; constructors
  are never inherited.
- `super(...)` must be the first statement of a constructor; if you omit it, the
  compiler inserts `super()`. Constructor calls go up to `Object`, and the bodies run
  from the top of the hierarchy down.
- Java supports single, multilevel and hierarchical inheritance of classes, but a class
  can extend only one class, which avoids the diamond problem.
- Multiple inheritance of type comes from interfaces: a class can extend one class and
  implement many interfaces (`SmartPhone extends Device implements Camera,
  MusicPlayer`).
- Overriding replaces or extends an inherited method with the same signature; mark it
  with `@Override` and use `super.method()` to reuse the inherited version.
- `protected` means visible in the package and to subclasses; prefer private fields
  with protected or public methods.
- A `final` method cannot be overridden and a `final` class cannot be extended.
- Every class descends from `Object`. Override `toString()` for readable output, and
  override `equals()` and `hashCode()` together when objects should be equal by
  content.
- Use composition ("has-a") when the relationship is not a permanent "is-a", or when
  inheriting would expose methods the new class should not have.
