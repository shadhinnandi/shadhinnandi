# Chapter 14: Multithreaded Programming

Every program you have written so far did one thing at a time: one statement, then the
next. Real programs often need to do several things at once: download files while the
screen stays responsive, or split a big calculation across the cores of your CPU. Java
lets one program run several *threads* at the same time. This chapter shows how to
create threads, how to wait for them, and how to keep shared data correct when several
threads touch it.

**In this chapter you will learn:**

- the difference between a process and a thread
- why programs use more than one thread
- how to create threads with `Thread` and with `Runnable`, and why `Runnable` is preferred
- why `start()` creates a thread and `run()` does not
- the thread lifecycle: NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED
- how `sleep()` and `join()` work, and who decides the order threads run in
- what a race condition is, and how `synchronized` prevents lost updates
- how to protect a shared resource such as a bank account used by two ATMs
- `AtomicInteger` for simple thread-safe counters
- thread pools with `ExecutorService`, and getting results with `Callable` and `Future`
- how to handle `InterruptedException` correctly, and basic good practices

## 1. Concept Explanation

### One thing at a time

A normal Java program has one path of execution. `main` starts, calls methods, and
each statement waits for the previous one to finish.

```text
main:  read input --> compute --> compute --> compute --> print
       (one step at a time, on one path)
```

This is simple and predictable. But if one step is slow (waiting for a network
download, or a long calculation), everything after it must wait too.

### Process vs thread

A **process** is a running program. The operating system (OS) gives each process its
own memory. When you run `java BankDemo`, the JVM runs as one process.

A **thread** is one path of execution *inside* a process. A process can have many
threads. All threads of a process share the same heap (the objects) and the same
static fields, but each thread has its own call stack (its own local variables and
method calls).

```text
+---------------- Process: java CanteenApp ------------------+
|                                                            |
|  Shared by all threads: heap (objects), static fields      |
|                                                            |
|  +--------------+  +--------------+  +--------------+      |
|  | Thread: main |  | Thread: T1   |  | Thread: T2   |      |
|  |--------------|  |--------------|  |--------------|      |
|  | own stack    |  | own stack    |  | own stack    |      |
|  | (locals,     |  | (locals,     |  | (locals,     |      |
|  |  calls)      |  |  calls)      |  |  calls)      |      |
|  +--------------+  +--------------+  +--------------+      |
+------------------------------------------------------------+
```

| | Process | Thread |
|---|---|---|
| What it is | A running program | A path of execution inside a process |
| Memory | Own, separate memory | Shares heap with other threads of the process |
| Cost to create | Higher | Lower |
| Talking to others | Needs OS help (files, pipes, network) | Can share objects directly |
| Danger | A crash usually stays inside it | One thread can corrupt data another uses |

The last row is the important one. Sharing objects is what makes threads useful, and
it is also what makes them tricky.

### Why multithreading?

- **Responsiveness.** A music player keeps the buttons working while a song downloads.
  One thread handles the screen; another does the slow work.
- **Doing several things at once.** A server handles many students logging in at the
  same time, one thread (or task) per request.
- **Using multiple cores.** Your laptop CPU probably has 4 to 16 cores. A program with
  one thread uses only one core. Splitting a big calculation into parts lets several
  cores work at the same time.

> **Coming from C?** Standard C (before C11) had no threads in the language; you used
> an OS library such as POSIX threads. Java has had threads built in from the start:
> the `Thread` class, the `synchronized` keyword and the `java.util.concurrent` package.

### The main thread

You have been using a thread all along. When the JVM starts your program, it creates a
thread named `main` and runs your `main` method on it. Every new thread you create runs
*next to* the main thread.

```java
String name = Thread.currentThread().getName();   // "main" inside main()
```

`Thread.currentThread()` returns the `Thread` object for the thread that is executing
that line right now.

### Describing the work: Thread and Runnable

A thread needs two things: the **work** to do, and a **thread** to do it. Java gives
you two ways to describe the work.

1. **Extend `Thread`** and override its `run()` method. The object *is* a thread.
2. **Implement `Runnable`** (an interface with one method, `void run()`), then give
   the `Runnable` object to a `new Thread(...)`. The object *is a task*; the `Thread`
   runs it.

| Extending `Thread` | Implementing `Runnable` |
|---|---|
| Uses up your one superclass | Your class can still extend another class |
| Mixes "what to do" with "how it runs" | Separates the task from the thread |
| Can only run on a `Thread` | The same task can run on a `Thread` or in a thread pool |

**Prefer `Runnable`.** Remember the question from Chapter 04: *should this be a class?*
A piece of work ("sum this range", "process this order") is a good class. A worker
that runs that work is a different job, and Java already provides it: `Thread` or a
thread pool.

### `start()` vs `run()`

This is the most common beginner mistake with threads.

- `t.start()` asks the JVM to create a **new thread**. That new thread then calls
  `run()`. `start()` returns immediately, so the calling thread keeps going.
- `t.run()` is an **ordinary method call**. It runs the code on the *current* thread,
  and the caller waits until it finishes. No new thread is created.

```text
t.run():    main: ---[ run() body ]---> continue      (one thread)

t.start():  main: ---start()---> continue ------------>
                         \
            new thread:   +---[ run() body ]---> ends  (two threads)
```

You may call `start()` only once per `Thread` object. Calling it twice throws
`IllegalThreadStateException`.

### Thread lifecycle

A thread moves through states. `t.getState()` returns the current one as a
`Thread.State` enum value.

```text
            +---------+
            |   NEW   |  Thread object created, not started
            +---------+
                 |
                 | start()
                 v
            +----------+  wants a lock that   +-----------+
            |          |  another thread has  |  BLOCKED  |
            |          | -------------------> |           |
            |          | <------------------- +-----------+
            |          |     gets the lock
            |          |  join(), wait()      +-----------+
            | RUNNABLE | -------------------> |  WAITING  |
            |          | <------------------- +-----------+
            |          |  other thread ends
            |          |  sleep(ms), join(ms) +---------------+
            |          | -------------------> | TIMED_WAITING |
            |          | <------------------- +---------------+
            +----------+     time is up
                 |
                 | run() finishes
                 v
            +------------+
            | TERMINATED |
            +------------+
```

| State | Meaning |
|---|---|
| `NEW` | Created with `new`, `start()` not called yet |
| `RUNNABLE` | Running, or ready to run and waiting for a CPU core |
| `BLOCKED` | Waiting to enter `synchronized` code whose lock another thread holds |
| `WAITING` | Waiting with no time limit, e.g. in `join()` |
| `TIMED_WAITING` | Waiting with a time limit, e.g. in `sleep(50)` |
| `TERMINATED` | `run()` has finished; the thread cannot be started again |

Java uses one state, `RUNNABLE`, for both "running right now" and "ready, waiting for
a core". Which ready thread actually runs is the scheduler's decision.

### Scheduling: who decides the order?

The JVM and the operating system's **scheduler** decide which thread runs on which
core, and for how long. You do not control it, and it can change from run to run.

```text
One core, two threads A and B (one possible schedule):
  core:   [A][A][B][A][B][B][B][A][B][A]   --> time

Two cores (another possible schedule):
  core 1: [A][A][A][A][A]
  core 2: [B][B][B][B][B]
```

So if two threads both print without any coordination, the lines can come out in any
order. Run it twice, and you may see two different outputs. **Never write a program
whose correctness depends on the scheduler choosing a particular order.** Thread
priorities (`setPriority`) are only hints and do not fix this.

In this course, every program whose output is shown prints in a fixed order. We do it
by waiting for threads to finish (`join()`) and then printing their results from
`main`.

### Waiting: `sleep()` and `join()`

- `Thread.sleep(ms)` pauses the **current** thread for about `ms` milliseconds (state
  `TIMED_WAITING`). It is a static method: it always puts the calling thread to sleep.
  We use it to simulate slow work such as a download.
- `t.join()` makes the **current** thread wait until thread `t` has finished (state
  `WAITING`). After `join()` returns, everything `t` wrote into shared objects is
  visible to the waiting thread.

```text
main:    start(T1) start(T2) join(T1)....... join(T2)... print results
T1:              [ work ...........]
T2:                        [ work ..................]
```

`join()` is the simplest tool for deterministic output: start all threads, join all
threads, then print.

### Race conditions

When two threads read and write the same variable at the same time, the result can
depend on the exact timing. This is a **race condition**.

The classic example is a shared counter. `count++` looks like one step, but the CPU
does three:

1. **read** the current value of `count`
2. **add** 1 to it (in a register)
3. **write** the new value back

If two threads do this at the same time, the steps can interleave like this:

| Step | Thread A | Thread B | `count` in memory |
|---|---|---|---|
| 1 | reads `count` (0) | | 0 |
| 2 | | reads `count` (0) | 0 |
| 3 | adds 1, gets 1 | | 0 |
| 4 | | adds 1, gets 1 | 0 |
| 5 | writes 1 | | 1 |
| 6 | | writes 1 | 1 |

Two increments happened, but `count` is 1. Thread B's write overwrote Thread A's. This
is a **lost update**. If each of two threads increments 100,000 times, the final count
is usually *less* than 200,000, and it changes from run to run. Worked Example 3 shows
this.

Another common race is **check-then-act**: "if the balance is enough, withdraw". Two
threads can both check, both see enough money, and both withdraw.

### `synchronized`: one thread at a time

Every Java object has a built-in **lock** (also called a monitor). Think of a single
key to a small room: only the person holding the key can be inside.

- A `synchronized` instance method locks `this` while it runs.
- A `synchronized (someObject) { ... }` block locks `someObject` while the block runs.

When thread A holds the lock, thread B that wants the same lock must wait (`BLOCKED`)
until A leaves. So the read-add-write of `count++` can no longer interleave.

```text
Thread A: [lock][read add write][unlock]
Thread B:        ...waits (BLOCKED)...  [lock][read add write][unlock]
```

The code protected by a lock is called a **critical section**. Leaving a
`synchronized` method or block also makes the changes visible to the next thread that
takes the same lock.

Important: the lock only helps if **every** access to the shared data uses the **same**
lock. A synchronized `deposit` and an unsynchronized `withdraw` on the same balance is
still broken.

### Shared resources: one account, two ATMs

Imagine Nusrat and her brother share a bank account with Tk 1,000. At the same moment,
Nusrat withdraws Tk 800 at ATM 1 and her brother withdraws Tk 800 at ATM 2.

| Step | ATM 1 thread | ATM 2 thread | balance |
|---|---|---|---|
| 1 | checks 1000 >= 800: OK | | 1000 |
| 2 | | checks 1000 >= 800: OK | 1000 |
| 3 | balance = 1000 - 800 | | 200 |
| 4 | | balance = 200 - 800 | -600 |

The account is overdrawn although each ATM checked the rule. The fix is to make the
whole "check, then withdraw" one critical section by declaring `withdraw`
`synchronized`. Then ATM 2 checks only after ATM 1 has finished, sees Tk 200 and
refuses. Worked Example 4 builds this.

This is also why encapsulation (Chapter 05) matters even more with threads: if the
balance is `private` and every method that touches it is `synchronized`, there is no
way for outside code to bypass the lock.

### Basic thread safety

A class is **thread-safe** if its objects behave correctly when several threads use
them at the same time, without the caller adding extra locks. Simple ways to get there:

| Strategy | Idea | Example |
|---|---|---|
| Do not share | Each thread works on its own objects and local variables | Each worker sums its own range into its own field |
| Share only immutable data | Objects that never change cannot be corrupted | `String`; an array that no thread modifies after the threads start (`final` alone does not make it immutable) |
| Lock | Guard every access to shared mutable data with the same lock | `synchronized` methods of `BankAccount` |
| Atomic classes | Use a class whose operations are already indivisible | `AtomicInteger` counter |

The first strategy is the best when you can use it: split the work, let each thread
keep its own result, and combine the results in `main` after `join()`.

### A note on deadlock

Locks have their own danger. If thread A holds lock X and waits for lock Y, while
thread B holds lock Y and waits for lock X, both wait forever. This is a **deadlock**.

```text
Thread A: holds X ----wants----> Y
Thread B: holds Y ----wants----> X      (nobody can continue)
```

Beginners can avoid it by keeping critical sections small, not calling unknown code
while holding a lock, and, when a thread needs two locks, always taking them in the
same order (for example, the account with the smaller ID first).

### `AtomicInteger`

`java.util.concurrent.atomic.AtomicInteger` is an `int` wrapper whose operations, such
as `incrementAndGet()` and `addAndGet(n)`, happen as one indivisible step. Two threads
calling `incrementAndGet()` can never lose an update, and you do not need
`synchronized`. It is ideal for a single counter. When several fields must change
together (for example balance *and* transaction count), use `synchronized` instead.

### Thread pools: `ExecutorService`

Creating a new `Thread` for every small job is wasteful, and with thousands of jobs it
can overload the machine. A **thread pool** keeps a few worker threads alive and gives
them tasks from a queue, like a canteen with three cooks serving a long line of orders.

```text
 main submits tasks           task queue              worker threads
 ------------------>  [t5][t4][t3]  ------->  pool-1-thread-1 runs t1
                                    ------->  pool-1-thread-2 runs t2
                                    ------->  pool-1-thread-3 (waiting)
```

- `Executors.newFixedThreadPool(3)` creates a pool with 3 worker threads.
- `pool.submit(task)` puts a task in the queue and returns at once.
- `pool.shutdown()` says "no more tasks"; tasks already submitted still run.
- `pool.awaitTermination(timeout, unit)` waits until all tasks have finished (or the
  timeout passes). Like `join()`, but for the whole pool.

Always shut a pool down. Its worker threads keep the JVM alive, so a program that
forgets `shutdown()` may never end.

### `Callable` and `Future`

`Runnable.run()` returns nothing. When a task should produce a value, implement
`Callable<V>`, whose method `V call()` returns a result (and may throw checked
exceptions).

`pool.submit(callable)` returns a `Future<V>`: a "receipt" for a result that may not
exist yet. Calling `future.get()` waits until the task has finished and then returns
its value. If the task threw an exception, `get()` throws an `ExecutionException` that
wraps it (`getCause()` gives the original).

Keeping the futures in a `List` in submission order and calling `get()` in that order
gives deterministic output, even though the tasks may finish in any order.

### `InterruptedException`

Another thread can ask a thread to stop what it is doing by calling `t.interrupt()`.
This does not kill the thread. It sets the thread's **interrupt flag**, and if the
thread is sleeping or waiting (`sleep`, `join`, `wait`), that method wakes up early and
throws `InterruptedException`.

`InterruptedException` is a checked exception, so every call to `sleep()` or `join()`
must handle it. The two correct choices are:

1. **Declare it**: `public static void main(String[] args) throws InterruptedException`.
   Good for `main` and for methods that just pass the problem up.
2. **Catch it and restore the flag**: catching the exception clears the interrupt
   flag, so call `Thread.currentThread().interrupt()` to set it again, then stop the
   work. This is the usual choice inside `run()`, which cannot declare checked
   exceptions.

Never catch it and do nothing. That hides the stop request from everyone else.

### Good practices

- Minimize shared mutable state. Give each thread its own data and combine results
  at the end.
- Make shared objects encapsulated, and guard every access with the same lock.
- Keep critical sections small: do slow work (calculations, sleeping, printing)
  outside the lock when you can.
- Prefer `Runnable`/`Callable` tasks and an `ExecutorService` over raw threads for
  many jobs.
- Always `join()` your threads or `shutdown()` and `awaitTermination()` your pools.
- Never rely on the scheduler's order. If output order matters, collect results and
  print them from one thread.
- Handle `InterruptedException` properly: declare it or restore the flag.

## 2. Syntax

In a real project each public class lives in its own file; here we keep each program in
one file so you can compile it with one command.

### Extending `Thread`

```java
class DownloadThread extends Thread {
    DownloadThread(String name) {
        super(name);                   // thread name, shown by getName()
    }

    @Override
    public void run() {                // the work of the new thread
        System.out.println("Downloading in " + getName());
    }
}

DownloadThread t = new DownloadThread("downloader");
t.start();                             // creates the thread, which calls run()
```

### Implementing `Runnable`

```java
class ReportTask implements Runnable {
    @Override
    public void run() {
        System.out.println("Building the report");
    }
}

Thread t = new Thread(new ReportTask());              // default name "Thread-0"
Thread named = new Thread(new ReportTask(), "report"); // with a name
t.start();
```

The task object is ordinary: it can have fields (its input) and a field for its result.

### Lambda expressions for `Runnable`

`Runnable` has exactly one abstract method, so Java lets you write a short anonymous
implementation called a **lambda expression**:

```java
Runnable task = () -> System.out.println("Hello from a task");

Runnable longer = () -> {
    for (int i = 1; i <= 3; i++) {
        System.out.println("step " + i);
    }
};
```

Read `() -> { ... }` as "a `run()` method with no parameters whose body is `{ ... }`".
It means the same as writing a small class that implements `Runnable`. A lambda may use
local variables of the surrounding method only if they are never reassigned
("effectively final").

### `start()`, `sleep()`, `join()`

```java
Thread worker = new Thread(task, "worker-1");
System.out.println(worker.getState());   // NEW
worker.start();                          // new thread begins run()
Thread.sleep(20);                        // the CURRENT thread sleeps 20 ms
worker.join();                           // the current thread waits for worker
System.out.println(worker.getState());   // TERMINATED
System.out.println(worker.isAlive());    // false
```

`sleep` and `join` throw `InterruptedException`, so the method that calls them must
catch it or declare it.

### Starting many threads and joining them all

```java
Thread[] workers = new Thread[4];
for (int i = 0; i < workers.length; i++) {
    workers[i] = new Thread(tasks[i]);
    workers[i].start();                  // start ALL first ...
}
for (int i = 0; i < workers.length; i++) {
    workers[i].join();                   // ... then wait for all
}
```

If you wrote `start(); join();` inside the same loop, each thread would finish before
the next one starts, and nothing would run in parallel.

### `synchronized` methods

```java
class Counter {
    private int count;

    synchronized void increment() {      // locks "this"
        count++;
    }

    synchronized int get() {             // reads need the lock too
        return count;
    }
}
```

### `synchronized` blocks

```java
class Canteen {
    private final Object lock = new Object();   // a private lock object
    private int orders;
    private int revenue;

    void placeOrder(int price) {
        String receipt = "Order of Tk " + price; // no shared data: outside the lock
        synchronized (lock) {                    // only the shared part is locked
            orders++;
            revenue += price;
        }
        System.out.println(receipt);
    }
}
```

A block lets you lock less code than a whole method, and lets you choose which object
is the lock. A `private final` lock object cannot be locked by outside code by mistake.

### `AtomicInteger`

```java
import java.util.concurrent.atomic.AtomicInteger;

AtomicInteger visits = new AtomicInteger();   // starts at 0
visits.incrementAndGet();                     // +1, returns the new value
visits.addAndGet(5);                          // +5, returns the new value
int now = visits.get();                       // read the value
```

### `ExecutorService`

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

ExecutorService pool = Executors.newFixedThreadPool(3);
pool.submit(task1);                           // Runnable or Callable
pool.submit(task2);
pool.shutdown();                              // accept no new tasks
pool.awaitTermination(5, TimeUnit.SECONDS);   // wait for running tasks
```

### `Callable` and `Future`

```java
import java.util.concurrent.Callable;
import java.util.concurrent.Future;

class SquareTask implements Callable<Integer> {
    private final int n;

    SquareTask(int n) {
        this.n = n;
    }

    @Override
    public Integer call() {                   // returns a value
        return n * n;
    }
}

Future<Integer> future = pool.submit(new SquareTask(7));
int result = future.get();                    // waits, then gives 49
```

`future.get()` throws `InterruptedException` and `ExecutionException` (both checked).

### Handling `InterruptedException`

```java nocompile
// Option 1: declare it (fine for main)
public static void main(String[] args) throws InterruptedException {
    worker.join();
}

// Option 2: inside run(), catch it and restore the interrupt flag
@Override
public void run() {
    try {
        Thread.sleep(50);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();   // keep the stop request visible
        return;                               // stop this task
    }
}
```

## 3. Worked Examples

### Example 1: start() Versus run()

**Problem:** Show, by printing the name of the executing thread, that calling `run()`
directly does not create a thread while `start()` does. Use one class that extends
`Thread` and one task that implements `Runnable`, and print each thread's state before
starting and after it finishes.

- `Thread.currentThread().getName()` tells us which thread executes a line.
- After every `start()`, `main` immediately calls `join()` and prints nothing in
  between, so the output order is fixed.

```java
class Bell extends Thread {
    Bell(String name) {
        super(name);
    }

    @Override
    public void run() {
        System.out.println("  Bell rings, executed by: "
                + Thread.currentThread().getName());
    }
}

class Announcement implements Runnable {
    @Override
    public void run() {
        System.out.println("  Announcement read, executed by: "
                + Thread.currentThread().getName());
    }
}

public class StartVersusRun {
    public static void main(String[] args) throws InterruptedException {
        Bell bell = new Bell("bell-thread");
        System.out.println("bell state: " + bell.getState());

        System.out.println("Calling bell.run():");
        bell.run();                  // ordinary call: runs on main
        System.out.println("Calling bell.start():");
        bell.start();                // new thread runs run()
        bell.join();
        System.out.println("bell state: " + bell.getState());

        Thread speaker = new Thread(new Announcement(), "speaker-thread");
        System.out.println("Calling speaker.start():");
        speaker.start();
        speaker.join();
        System.out.println("speaker alive? " + speaker.isAlive());
    }
}
```

**Output:**

```text
bell state: NEW
Calling bell.run():
  Bell rings, executed by: main
Calling bell.start():
  Bell rings, executed by: bell-thread
bell state: TERMINATED
Calling speaker.start():
  Announcement read, executed by: speaker-thread
speaker alive? false
```

**Why it works:** `bell.run()` is just a method call, so the `main` thread executes
the body. `bell.start()` creates a new thread named `bell-thread`, and that thread
calls `run()`. The `Runnable` version works the same way: the `Thread` object is the
worker, `Announcement` is the work. `join()` makes `main` wait, so by the time it
prints the state, the thread is `TERMINATED` and no longer alive.

### Example 2: Parallel Sum Over Ranges

**Problem:** Compute 1 + 2 + ... + 1,000,000 using 4 threads. Each thread sums one
quarter of the range. Print each thread's range and partial sum, then the total, and
compare it with the formula n(n + 1) / 2.

Design:

- `RangeSum` is a task (`Runnable`) with its own input (`from`, `to`) and its own
  result field `sum`. No two threads share a variable, so there is no race.
- `main` starts all threads, joins all threads, and only then reads the results and
  prints them in index order.
- Sums are `long`: the total is about 5 * 10^11, too big for `int`.

```java
class RangeSum implements Runnable {
    private final long from;
    private final long to;
    private long sum;              // written only by this task's thread

    RangeSum(long from, long to) {
        this.from = from;
        this.to = to;
    }

    @Override
    public void run() {
        long total = 0;
        for (long i = from; i <= to; i++) {
            total += i;
        }
        sum = total;
    }

    long getFrom() {
        return from;
    }

    long getTo() {
        return to;
    }

    long getSum() {
        return sum;
    }
}

public class ParallelSum {
    public static void main(String[] args) throws InterruptedException {
        long n = 1000000;
        int threadCount = 4;
        long chunk = n / threadCount;

        RangeSum[] tasks = new RangeSum[threadCount];
        Thread[] threads = new Thread[threadCount];
        for (int i = 0; i < threadCount; i++) {
            long from = i * chunk + 1;
            long to = (i == threadCount - 1) ? n : (i + 1) * chunk;
            tasks[i] = new RangeSum(from, to);
            threads[i] = new Thread(tasks[i]);
            threads[i].start();
        }
        for (int i = 0; i < threadCount; i++) {
            threads[i].join();
        }

        long total = 0;
        for (int i = 0; i < threadCount; i++) {
            System.out.printf("Thread %d: %d..%d = %d%n", i + 1,
                    tasks[i].getFrom(), tasks[i].getTo(), tasks[i].getSum());
            total += tasks[i].getSum();
        }
        System.out.println("Total   : " + total);
        System.out.println("Formula : " + n * (n + 1) / 2);
    }
}
```

**Output:**

```text
Thread 1: 1..250000 = 31250125000
Thread 2: 250001..500000 = 93750125000
Thread 3: 500001..750000 = 156250125000
Thread 4: 750001..1000000 = 218750125000
Total   : 500000500000
Formula : 500000500000
```

**Why it works:** The four threads may finish in any order, but nobody prints until
all four `join()` calls have returned. After `join()`, the value each thread wrote into
its own `sum` field is visible to `main`. Printing from `main` in a loop over the array
makes the output order fixed. The last range ends at `n`, so the program would still
be correct if `n` were not divisible by the number of threads.

### Example 3: Lost Updates and the synchronized Fix

**Problem:** Two threads each record 100,000 card taps at the library gate on one
shared counter. Show the race condition, then fix it with `synchronized`.

First, the broken version. The two threads share one `UnsafeCounter`, and
`increment()` is not synchronized. Both tasks are written as lambdas.

```java
class UnsafeCounter {
    private int count;

    void increment() {
        count++;                   // read, add, write: not one step!
    }

    int get() {
        return count;
    }
}

public class LostUpdates {
    public static void main(String[] args) throws InterruptedException {
        UnsafeCounter taps = new UnsafeCounter();
        Runnable gate = () -> {
            for (int i = 0; i < 100000; i++) {
                taps.increment();
            }
        };
        Thread gateA = new Thread(gate);
        Thread gateB = new Thread(gate);
        gateA.start();
        gateB.start();
        gateA.join();
        gateB.join();
        System.out.println("Expected: 200000");
        System.out.println("Counted : " + taps.get());
    }
}
```

This program has no fixed output, so none is shown. Run it several times. You will
often see a count below 200,000, such as `Counted : 113874`, and a different number on
the next run. Sometimes, by luck, you may even see 200,000. That is what makes race
conditions dangerous: the bug does not appear every time. The interleaving table in
Section 1 shows how one update overwrites another.

Now the fix. The only change is the word `synchronized` on both methods.

```java
class SafeCounter {
    private int count;

    synchronized void increment() {
        count++;
    }

    synchronized int get() {
        return count;
    }
}

public class NoLostUpdates {
    public static void main(String[] args) throws InterruptedException {
        SafeCounter taps = new SafeCounter();
        Runnable gate = () -> {
            for (int i = 0; i < 100000; i++) {
                taps.increment();
            }
        };
        Thread gateA = new Thread(gate);
        Thread gateB = new Thread(gate);
        gateA.start();
        gateB.start();
        gateA.join();
        gateB.join();
        System.out.println("Expected: 200000");
        System.out.println("Counted : " + taps.get());
    }
}
```

**Output:**

```text
Expected: 200000
Counted : 200000
```

**Why it works:** A `synchronized` method takes the lock of the object (`taps`) before
it runs. While gate A is inside `increment()`, gate B must wait, so the
read-add-write steps of the two threads can no longer interleave. Every increment is
kept, so the count is exactly 200,000 on every run. Note that the lambda `gate` uses
the local variable `taps`, which is allowed because `taps` is never reassigned.

### Example 4: One Account, Two ATMs

**Problem:** A shared account opens with Tk 5,000. Two ATM threads each try to
withdraw Tk 500 six times (Tk 6,000 requested in total). Withdrawals that would make
the balance negative must be refused. Print how many withdrawals were approved and
refused, and the final balance.

Design:

- `BankAccount` keeps `balance` and the approved/refused counts `private`. Every method
  that touches them is `synchronized`, so "check, then withdraw" is one critical
  section.
- `Atm` is a `Runnable` task that knows which account to use and what to withdraw.
- Which ATM gets which approval depends on the scheduler, so we print only the totals,
  which are the same in every run: 10 withdrawals of Tk 500 fit in Tk 5,000.

```java
class BankAccount {
    private int balance;
    private int approved;
    private int refused;

    BankAccount(int openingBalance) {
        balance = openingBalance;
    }

    synchronized boolean withdraw(int amount) {
        if (amount <= balance) {       // check ...
            balance -= amount;         // ... then act, under the same lock
            approved++;
            return true;
        }
        refused++;
        return false;
    }

    synchronized int getBalance() {
        return balance;
    }

    synchronized int getApproved() {
        return approved;
    }

    synchronized int getRefused() {
        return refused;
    }
}

class Atm implements Runnable {
    private final BankAccount account;
    private final int amount;
    private final int times;

    Atm(BankAccount account, int amount, int times) {
        this.account = account;
        this.amount = amount;
        this.times = times;
    }

    @Override
    public void run() {
        for (int i = 0; i < times; i++) {
            account.withdraw(amount);
        }
    }
}

public class TwoAtms {
    public static void main(String[] args) throws InterruptedException {
        BankAccount shared = new BankAccount(5000);
        Thread atm1 = new Thread(new Atm(shared, 500, 6), "ATM-1");
        Thread atm2 = new Thread(new Atm(shared, 500, 6), "ATM-2");
        atm1.start();
        atm2.start();
        atm1.join();
        atm2.join();

        System.out.println("Approved withdrawals: " + shared.getApproved());
        System.out.println("Refused withdrawals : " + shared.getRefused());
        System.out.println("Final balance       : Tk " + shared.getBalance());
    }
}
```

**Output:**

```text
Approved withdrawals: 10
Refused withdrawals : 2
Final balance       : Tk 0
```

**Why it works:** Without `synchronized`, both ATMs could check `500 <= 500` at the
same time when only Tk 500 is left, both withdraw, and the balance would become
Tk -500. With the lock, the second ATM checks only after the first has finished its
withdrawal, sees Tk 0, and refuses. The getters are synchronized too, so `main` reads
values written under the same lock (after `join()` this would also be safe, but
synchronizing every access is the simple rule to remember).

### Example 5: Counting Visitors with AtomicInteger

**Problem:** Three entrance gates of the central library count visitors on one shared
counter. Each gate records 10,000 entries. Use `AtomicInteger` instead of
`synchronized`, and name the gate threads.

```java
import java.util.concurrent.atomic.AtomicInteger;

public class LibraryVisitors {
    public static void main(String[] args) throws InterruptedException {
        AtomicInteger visitors = new AtomicInteger();
        int perGate = 10000;

        Runnable gateWork = () -> {
            for (int i = 0; i < perGate; i++) {
                visitors.incrementAndGet();
            }
        };

        Thread[] gates = new Thread[3];
        for (int i = 0; i < gates.length; i++) {
            gates[i] = new Thread(gateWork, "gate-" + (i + 1));
            gates[i].start();
        }
        for (int i = 0; i < gates.length; i++) {
            gates[i].join();
            System.out.println(gates[i].getName() + " finished");
        }
        System.out.println("Visitors today: " + visitors.get());
    }
}
```

**Output:**

```text
gate-1 finished
gate-2 finished
gate-3 finished
Visitors today: 30000
```

**Why it works:** `incrementAndGet()` performs read-add-write as one indivisible
operation, so no increment is lost even though three threads use the same counter at
once. The "finished" lines are printed by `main` after each `join()`, in array order,
so their order is fixed even if gate 3 actually finished first.

### Example 6: Section Averages with a Thread Pool

**Problem:** A course has three sections with different marks. Compute each section's
average in a separate task using a pool of 2 threads, then print the averages in
section order and the overall average of the three sections.

Design:

- `SectionAverage implements Callable<Double>`: a task that *returns* its result.
- `main` submits the tasks and keeps the `Future` objects in a list, in submission
  order. `get()` on each future waits for that task.
- Three tasks share a pool of two threads, so one task waits in the queue until a
  worker is free. The program does not care which thread runs which task.

```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.Callable;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;

class SectionAverage implements Callable<Double> {
    private final int[] marks;

    SectionAverage(int[] marks) {
        this.marks = marks;
    }

    @Override
    public Double call() {
        int sum = 0;
        for (int mark : marks) {
            sum += mark;
        }
        return (double) sum / marks.length;
    }
}

public class SectionReport {
    public static void main(String[] args)
            throws InterruptedException, ExecutionException {
        String[] sections = {"A", "B", "C"};
        int[][] marks = {
            {78, 85, 90, 66},
            {55, 72, 81},
            {91, 88, 79, 95, 70}
        };

        ExecutorService pool = Executors.newFixedThreadPool(2);
        List<Future<Double>> results = new ArrayList<>();
        for (int i = 0; i < sections.length; i++) {
            results.add(pool.submit(new SectionAverage(marks[i])));
        }

        double sumOfAverages = 0;
        for (int i = 0; i < sections.length; i++) {
            double average = results.get(i).get();   // waits for task i
            System.out.printf("Section %s average: %.2f%n", sections[i], average);
            sumOfAverages += average;
        }
        System.out.printf("Average of sections: %.2f%n",
                sumOfAverages / sections.length);

        pool.shutdown();
        if (pool.awaitTermination(5, TimeUnit.SECONDS)) {
            System.out.println("Pool shut down cleanly");
        }
    }
}
```

**Output:**

```text
Section A average: 79.75
Section B average: 69.33
Section C average: 84.60
Average of sections: 77.89
Pool shut down cleanly
```

**Why it works:** `submit` returns at once with a `Future`. The loop that calls
`get()` visits the futures in submission order, so section A is printed first even if
section B's task finished earlier. `shutdown()` stops the pool from accepting tasks and
lets the workers end once the queue is empty (so the JVM can exit), and
`awaitTermination` waits until they have.

### Example 7: Cancelling a Task with interrupt()

**Problem:** A hostel backup task waits one minute before it runs. The warden changes
her mind and cancels it right away. Show how the task notices the interrupt, restores
the interrupt flag, and ends cleanly.

```java
class BackupTask implements Runnable {
    @Override
    public void run() {
        try {
            Thread.sleep(60000);       // wait one minute before backing up
            System.out.println("Backup: copying files");
        } catch (InterruptedException e) {
            // Catching the exception cleared the flag; set it again.
            Thread.currentThread().interrupt();
            System.out.println("Backup: cancelled before it started");
            System.out.println("Backup: interrupt flag is "
                    + Thread.currentThread().isInterrupted());
        }
    }
}

public class CancelBackup {
    public static void main(String[] args) throws InterruptedException {
        Thread backup = new Thread(new BackupTask(), "backup");
        System.out.println("Main: starting backup thread");
        backup.start();
        backup.interrupt();            // ask the thread to stop waiting
        backup.join();
        System.out.println("Main: backup thread is " + backup.getState());
    }
}
```

**Output:**

```text
Main: starting backup thread
Backup: cancelled before it started
Backup: interrupt flag is true
Main: backup thread is TERMINATED
```

**Why it works:** `interrupt()` sets the backup thread's interrupt flag. If the thread
is already sleeping, `sleep` wakes up and throws `InterruptedException`; if it has not
reached `sleep` yet, `sleep` throws immediately because the flag is already set. Either
way, the program does not wait a minute. Because `run()` cannot declare
`throws InterruptedException`, it catches the exception, restores the flag with
`Thread.currentThread().interrupt()` and finishes. `main` declares the exception
because it only passes it on.

## Common Mistakes

- **Calling `run()` instead of `start()`.** The code runs, but on the current thread.
  Nothing happens in parallel.
- **Starting and joining in the same loop.** `start(); join();` in one loop runs the
  threads one after another. Start all first, then join all.
- **Reading results before `join()`.** A worker's result field may still be 0 (or
  half-updated) until the worker has finished and you have joined it.
- **Expecting a fixed output order from unsynchronized threads.** The scheduler
  decides. Collect results and print them from `main`.
- **Synchronizing only some methods.** If `deposit` is `synchronized` but `withdraw`
  is not, the balance is still unsafe. Every access to shared data needs the same lock.
- **Locking on different objects.** Each object has its own lock. Two threads that
  synchronize on two different `Counter` objects do not exclude each other.
- **Huge critical sections.** Sleeping or doing long calculations while holding a lock
  makes all other threads wait and removes the benefit of threads.
- **Swallowing `InterruptedException`.** An empty `catch` block hides the stop
  request. Restore the flag with `Thread.currentThread().interrupt()` or declare it.
- **Forgetting `shutdown()`.** The pool's threads keep running and the program never
  ends.
- **Calling `start()` twice.** A `Thread` can be started only once; create a new
  `Thread` (or submit the task to a pool again) to run the work again.

## Summary

- A process is a running program with its own memory; a thread is a path of execution
  inside it. Threads share the heap but each has its own stack.
- Create threads by extending `Thread` or, preferably, by giving a `Runnable` task to
  a `Thread`. `start()` creates the new thread; calling `run()` directly does not.
- A thread moves through NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING and
  TERMINATED. `sleep()` pauses the current thread; `join()` waits for another thread.
- The scheduler decides the order threads run in. Never depend on it; join the threads
  and print their results from one place.
- A race condition happens when threads read and write shared data without
  coordination. `count++` and "check, then act" can lose updates.
- `synchronized` methods and blocks let only one thread at a time into a critical
  section guarded by the same lock. Keep critical sections small.
- `AtomicInteger` gives thread-safe counters without `synchronized`.
- `ExecutorService` runs tasks on a pool of threads; always `shutdown()` and
  `awaitTermination()`. `Callable` tasks return values through `Future.get()`.
- Handle `InterruptedException` by declaring it or by catching it and calling
  `Thread.currentThread().interrupt()`.
- The safest shared data is no shared data: give each thread its own work and result,
  and combine results after the threads finish.
