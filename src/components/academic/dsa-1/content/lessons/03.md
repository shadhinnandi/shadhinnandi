## Intuition: a recipe a machine can follow

An algorithm is a recipe so precise that a machine can follow it without judgement. "Add salt to taste" is not algorithmic; "add 5 g of salt" is. Designing an algorithm means turning an informal goal ("find the cheapest flight") into unambiguous steps that always finish with the right answer.

Two separate questions apply to every algorithm:

1. **Is it correct?** Does it produce the right output for *every* valid input?
2. **Is it efficient?** Does it finish within the time and memory the constraints allow?

A fast wrong answer is worthless, and a correct answer that takes a year is useless. Keep both questions in mind, but answer them separately.

## Definitions and terminology

| Property | Meaning | Violated by |
|---|---|---|
| **Input** | Zero or more well-defined inputs | "Use some data" |
| **Output** | At least one output related to the input | A procedure that computes but never reports |
| **Finiteness** | Terminates after a finite number of steps on every valid input | A loop whose condition never becomes false |
| **Definiteness** | Every step is precise and unambiguous | "Pick a good element" |
| **Effectiveness** | Every step is basic enough to be carried out exactly | "Find the largest prime number" |

Other terms:

| Term | Meaning |
|---|---|
| **Pseudocode** | Structured, language-independent description of steps |
| **Flowchart** | A diagram of steps (boxes) and decisions (diamonds) connected by arrows |
| **Dry run** | Executing an algorithm by hand on a small input |
| **Tracing table** | A table of variable values after each step of a dry run |
| **Edge case** | A valid input at the boundary of the specification (empty, one element, maximum value) |
| **Paradigm** | A general design strategy: brute force, divide and conquer, greedy, … |

## Algorithm design and problem decomposition

A reliable design process:

1. **Understand the problem.** Restate it, identify the input, the output and the constraints. Work two examples by hand.
2. **Decompose.** Split the task into sub-tasks you already know how to solve (read input → process → output; or "find X, then use X to find Y").
3. **Choose a strategy.** Start with the simplest correct idea (often brute force); improve it if the constraints demand.
4. **Write pseudocode**, then code.
5. **Dry-run** on the examples and on edge cases.
6. **Analyse** correctness (why it works) and efficiency (how fast it is).

## Pseudocode, flowcharts and implementation

Problem: find the largest value in a non-empty list.

```text
FIND-MAX(A[0..n-1])          // precondition: n >= 1
    best ← A[0]
    for i ← 1 to n - 1
        if A[i] > best
            best ← A[i]
    return best
```

```text
        +-------------+
        |    start    |
        +------+------+
               v
      +-----------------+
      | best = A[0]     |
      | i = 1           |
      +--------+--------+
               v
         /-----------\   no
        <   i < n ?   >--------> [ output best ] --> ( end )
         \-----------/
               | yes
               v
         /-------------\  yes   +-------------+
        < A[i] > best ? >------>| best = A[i] |
         \-------------/        +------+------+
               | no                    |
               v                       |
          +---------+ <----------------+
          | i = i+1 |
          +----+----+
               |
               +----> back to the test "i < n ?"
```

```cpp
#include <iostream>
#include <vector>
using namespace std;

long long findMax(const vector<long long>& a) {    // precondition: !a.empty()
    long long best = a[0];
    for (size_t i = 1; i < a.size(); ++i)
        if (a[i] > best) best = a[i];
    return best;
}

int main() {
    vector<long long> a = {3, -1, 8, 8, 2};
    cout << findMax(a) << '\n';
}
```

**Output:**

```text
8
```

All three describe the same algorithm. Pseudocode is best for reasoning, flowcharts for showing control flow to non-programmers, and code for running.

## Iterative versus recursive solutions

Many problems can be solved either way. Factorial:

```cpp
#include <iostream>
using namespace std;

long long factorialIter(int n) {          // loop: O(n) time, O(1) space
    long long result = 1;
    for (int i = 2; i <= n; ++i) result *= i;
    return result;
}

long long factorialRec(int n) {           // recursion: O(n) time, O(n) stack
    if (n <= 1) return 1;                 // base case
    return n * factorialRec(n - 1);       // smaller instance
}

int main() {
    cout << factorialIter(20) << ' ' << factorialRec(20) << '\n';
}
```

**Output:**

```text
2432902008176640000 2432902008176640000
```

| | Iterative | Recursive |
|---|---|---|
| Expresses | Repetition with a loop | A problem in terms of smaller instances |
| Extra memory | Usually O(1) | One stack frame per active call |
| Risk | Off-by-one loop bounds | Missing base case; stack overflow on deep recursion |
| Natural for | Scanning arrays | Trees, divide and conquer, backtracking |

A naive recursive Fibonacci, `fib(n) = fib(n−1) + fib(n−2)`, is correct but recomputes the same values exponentially many times; the iterative version is O(n). Recursion is a way of *expressing* an algorithm; its cost depends on how many calls it makes.

## Three introductory design strategies

### Brute force

Try every candidate and keep the best. Simple and obviously correct, often too slow. Example: to find whether two numbers in an array sum to K, check all n(n−1)/2 pairs: O(n²).

### Divide and conquer

1. **Divide** the problem into smaller subproblems of the same kind.
2. **Conquer** them recursively.
3. **Combine** their answers.

Binary search (search half the sorted array), merge sort (sort halves, merge) and quick sort follow this pattern. Modules 05, 06 and 16 analyse them.

### Greedy

Build the answer step by step, always taking the choice that looks best *now*, and never undoing it. Fast, but correct only when the problem has the right structure, which must be proved.

- Works: giving change with taka notes 1, 2, 5, 10, 20, 50, 100, 200, 500, 1000 by always taking the largest note that fits.
- Fails: with coins {1, 3, 4} and amount 6, greedy takes 4 + 1 + 1 (three coins), but 3 + 3 uses two.

| Strategy | Idea | Typical cost | Correctness |
|---|---|---|---|
| Brute force | Try everything | Often exponential or high polynomial | Easy to argue |
| Divide and conquer | Split, solve, combine | Often O(n log n) | By induction on size |
| Greedy | Best local choice | Often O(n log n) (after sorting) | Needs a proof (exchange argument) |

## Dry runs, tracing tables and edge cases

Dry-run `FIND-MAX` on A = [3, −1, 8, 8, 2]:

| i | A[i] | A[i] > best? | best |
|---|---|---|---|
| (init) | | | 3 |
| 1 | −1 | no | 3 |
| 2 | 8 | yes | 8 |
| 3 | 8 | no | 8 |
| 4 | 2 | no | 8 |

Edge cases to test: one element (loop never runs), all equal, all negative (initialising `best = 0` would be wrong), maximum at the first or last position.

## Complexity analysis

| Algorithm in this module | Time | Extra space |
|---|---|---|
| Find maximum | O(n) | O(1) |
| Factorial (iterative / recursive) | O(n) | O(1) / O(n) stack |
| Brute-force pair sum | O(n²) | O(1) |
| Greedy change (k note types) | O(k) | O(1) |
| Naive recursive Fibonacci | O(φ^n) ≈ O(1.618^n) | O(n) stack |

Module 04 makes these statements precise.

## Correctness reasoning

For `FIND-MAX`, the key fact is: *after processing positions 0..i, `best` equals the maximum of A[0..i]*. It is true initially (i = 0), each iteration keeps it true, and when the loop ends i = n − 1, so `best` is the maximum of the whole array. This is a **loop invariant**; Module 05 turns this style of argument into formal proofs.

## Common mistakes and edge cases

- **Confusing "it worked on the sample" with correctness.** Test edge cases deliberately.
- **Initialising with a magic value** (`best = 0`, `best = INT_MIN` with overflowing arithmetic later). Initialise from the data.
- **Non-terminating loops**: make sure something changes towards the exit condition every iteration.
- **Trusting greedy without proof**: find a counterexample or prove the choice is safe.
- **Deep recursion** on large inputs (n = 10^6 frames): use iteration.

## Applications

- Every program is built from algorithms; decomposition is how large software is designed.
- Brute force is the reference solution used to test faster ones (stress testing).
- Divide and conquer underlies sorting, searching and fast arithmetic; greedy underlies scheduling, compression (Huffman) and minimum spanning trees.

## Comparison with related concepts

| | Algorithm | Program | Data structure |
|---|---|---|---|
| What it is | A precise procedure | An algorithm written in a programming language | A way to organise data |
| Must terminate? | Yes (finiteness) | Not necessarily (servers run forever) | Not applicable |
| Example | Binary search | `std::lower_bound` | A sorted array |

## Key takeaways

- An algorithm has inputs, outputs, and finite, definite, effective steps.
- Design: understand, decompose, choose a strategy, write pseudocode, dry-run, analyse.
- Iteration and recursion are two ways to express repetition; recursion costs stack space.
- Brute force is simple, divide and conquer splits the work, greedy commits to local choices and needs a proof.
- Correctness and efficiency are separate requirements; check both.
