## Intuition: a contract, not a container

When you use `std::stack`, you never think about how it stores elements: you push, pop and look at the top. That list of operations and their promised behaviour is the **abstract data type**. The code that actually stores the elements (an array, a linked list) is the **data structure**.

A good analogy is a vending machine: the interface is "insert money, choose an item, receive it". Whether the inside uses springs or a robot arm is an implementation detail you can change without retraining customers.

## Definitions and terminology

| Term | Meaning |
|---|---|
| **Abstract data type (ADT)** | A set of values plus operations on them, defined by *behaviour*, not by storage |
| **Interface** | The operations a user may call, with their signatures and meaning |
| **Implementation** | The concrete code and memory layout that provides the interface |
| **Data structure** | A concrete way of organising data in memory (array, linked list, tree, hash table) |
| **Precondition** | What must be true before an operation is called (e.g. `pop` needs a non-empty stack) |
| **Postcondition** | What the operation guarantees afterwards (e.g. size decreased by one) |
| **Invariant** | A property that holds before and after *every* operation (e.g. `0 ≤ size ≤ capacity`) |
| **Encapsulation** | Hiding the implementation so users can only reach the data through the interface |

### ADT versus data structure

| | ADT | Data structure |
|---|---|---|
| Answers | *What* operations, with what behaviour? | *How* is the data stored, and at what cost? |
| Example | Stack: push, pop, top, empty | A dynamic array with a `top` index |
| Many-to-many | One ADT, several implementations | One structure can implement several ADTs |
| Costs | Not part of the definition | O(·) of each operation |

A dynamic array can implement a List, a Stack or a Queue; a Set can be implemented by a sorted array, a hash table or a balanced tree.

## Specifying an ADT

Here is the Stack ADT specified formally:

| Operation | Precondition | Postcondition |
|---|---|---|
| `push(x)` | none (or size < capacity if bounded) | x is the new top; size increases by 1 |
| `pop()` | stack not empty | the top element is removed; size decreases by 1 |
| `top()` | stack not empty | returns the most recently pushed element still present; no change |
| `empty()` | none | returns true iff size = 0 |

**Invariant:** elements leave in the reverse order of arrival (last in, first out), and size ≥ 0.

Calling an operation whose precondition is false is a **bug in the caller**. An implementation may detect it (throw an exception, return an error) or document it as undefined, as `std::stack::pop` on an empty stack does.

| **Stack** | push, pop, top (LIFO) | dynamic array, linked list | 09 |
| **Queue** | enqueue, dequeue, front (FIFO) | circular array, linked list | 10 |

## Interface versus implementation in C++

The program below defines a Stack interface with a pure virtual class, two implementations (array-based and linked), and one client function that works with either. The client never sees how elements are stored.

```cpp
#include <iostream>
#include <memory>
#include <stdexcept>
#include <vector>
using namespace std;

// The ADT: what a stack of ints can do.
class IntStack {
public:
    virtual ~IntStack() = default;
    virtual void push(int x) = 0;
    virtual void pop() = 0;              // precondition: !empty()
    virtual int top() const = 0;         // precondition: !empty()
    virtual bool empty() const = 0;
};

// Implementation 1: contiguous storage.
class ArrayStack : public IntStack {
    vector<int> data;                    // invariant: data.back() is the top
public:
    void push(int x) override { data.push_back(x); }
    void pop() override {
        if (data.empty()) throw underflow_error("pop on empty stack");
        data.pop_back();
    }
    int top() const override {
        if (data.empty()) throw underflow_error("top on empty stack");
        return data.back();
    }
    bool empty() const override { return data.empty(); }
};

// Implementation 2: linked nodes.
class LinkedStack : public IntStack {
    struct Node {
        int value;
        unique_ptr<Node> below;
    };
    unique_ptr<Node> head;               // invariant: head is the top (nullptr if empty)
public:
    void push(int x) override { head = make_unique<Node>(Node{x, std::move(head)}); }
    void pop() override {
        if (!head) throw underflow_error("pop on empty stack");
        head = std::move(head->below);
    }
    int top() const override {
        if (!head) throw underflow_error("top on empty stack");
        return head->value;
    }
    bool empty() const override { return head == nullptr; }
};

// Client code depends only on the interface.
void reversePrint(IntStack& s, const vector<int>& values) {
    for (int v : values) s.push(v);
    while (!s.empty()) {
        cout << s.top() << ' ';
        s.pop();
    }
    cout << '\n';
}

int main() {
    ArrayStack a;
    LinkedStack b;
    reversePrint(a, {1, 2, 3});
    reversePrint(b, {4, 5, 6});
    try {
        a.pop();                          // violates the precondition
    } catch (const underflow_error& e) {
        cout << "error: " << e.what() << '\n';
    }
}
```

**Output:**

```text
3 2 1 
6 5 4 
error: pop on empty stack
```

`reversePrint` would not change at all if a third implementation were added. That is the practical value of an ADT: code written against the interface survives changes of implementation.

## Choosing an implementation

Start from the operations the program performs most, then pick the structure that makes them cheap:

| Need | Good choice | Why |
|---|---|---|
| Fast access by index, mostly appends | dynamic array (`vector`) | O(1) access, O(1) amortised append |
| Many insertions/deletions in the middle at known positions | linked list | O(1) relinking |
| LIFO only | stack on a `vector` | simplest and cache-friendly |
| FIFO | circular array or `deque` | O(1) at both ends |
| Membership tests, no order needed | hash set (`unordered_set`) | O(1) expected |
| Membership plus sorted order or range queries | balanced BST (`set`) | O(log n) and in-order iteration |
| Repeatedly take the largest/smallest | binary heap (`priority_queue`) | O(log n) insert and extract |

## Complexity analysis

The ADT itself has no complexity; each implementation does:

| Operation | Stack on dynamic array | Stack on linked list | Set on sorted array | Set on hash table | Set on balanced BST |
|---|---|---|---|---|---|
| insert / push | O(1) amortised | O(1) | O(n) | O(1) expected | O(log n) |
| erase / pop | O(1) | O(1) | O(n) | O(1) expected | O(log n) |
| search / top | O(1) top | O(1) top | O(log n) | O(1) expected | O(log n) |
| ordered iteration | not applicable | not applicable | O(n) | not ordered | O(n) |

## Correctness: invariants

An implementation is correct if (1) every constructor establishes the invariant, (2) every operation, assuming its precondition and the invariant, preserves the invariant and achieves its postcondition. For `ArrayStack`: the empty vector satisfies "the back is the top"; `push_back` makes x the back; `pop_back` removes the back, exposing the previous top. Checking each operation in isolation is enough, which is why invariants make code easier to reason about.

## Dry run

`reversePrint(b, {4, 5, 6})` with `LinkedStack`:

| Step | Operation | head → … |
|---|---|---|
| 1 | push 4 | 4 |
| 2 | push 5 | 5 → 4 |
| 3 | push 6 | 6 → 5 → 4 |
| 4 | top, pop | prints 6; 5 → 4 |
| 5 | top, pop | prints 5; 4 |
| 6 | top, pop | prints 4; empty |

## Common mistakes and edge cases

- **Leaking the implementation**: returning a reference to the internal `vector` lets callers break the invariant.
- **Ignoring preconditions**: calling `top()` on an empty `std::stack` is undefined behaviour, not an exception.
- **Choosing by habit**: using a `vector` and `find` for frequent membership tests is O(n) per test; a set is O(log n) or O(1).
- **Confusing an ADT with one implementation**: "a queue is an array" is wrong; an array is one way to build a queue.
- **Forgetting the invariant after an error**: an operation that throws midway must leave the object valid.

## Applications

- Libraries (the C++ STL, Java Collections) are organised as ADTs with interchangeable implementations.
- Undo stacks, print queues, task schedulers (priority queues), symbol tables (maps), and caches (map + list).
- Interviews often ask you to *design* an ADT: "implement an LRU cache", "a stack with O(1) minimum".

## Key takeaways

- An ADT is *what* (operations and behaviour); a data structure is *how* (storage and costs).
- Specify operations with preconditions and postconditions; keep an invariant true at all times.
- One ADT has many implementations; choose by the operations you need most.
- Write client code against the interface so the implementation can change.
